DAY 1 · MON

Loading related data: Include, ThenInclude, filtered Include, explicit and lazy loading

GoalExtend last week's StoreDb with customers and orders, then load related data on purpose — eagerly, explicitly or lazily — and read the SQL each choice produces.

Key definitions

Navigation property
A property that points to related entities: a reference (Order.Customer) or a collection (Customer.Orders).
Related data
Rows in other tables reached through foreign keys. EF Core does not load it unless you ask.
Eager loading
Loading related data in the same query with Include / ThenInclude.
Include
Adds one navigation to the query: Orders.Include(o => o.Customer). Translates to a JOIN.
ThenInclude
Continues an include path one level deeper: Include(o => o.Lines).ThenInclude(l => l.Product).
Filtered Include
EF Core 5+: Include(c => c.Orders.Where(...).OrderBy(...).Take(n)) loads only some children. Allowed operators: Where, OrderBy(Descending), ThenBy(Descending), Skip, Take.
Explicit loading
Loading a navigation later, on demand, for an entity already in memory: db.Entry(c).Collection(x => x.Orders).LoadAsync().
Lazy loading
Navigations load automatically the first time code reads them. Needs proxies (Microsoft.EntityFrameworkCore.Proxies) or an injected ILazyLoader.
Proxy
A runtime-generated subclass of your entity that overrides virtual navigations to trigger loading.
Relationship fix-up
EF Core automatically connects tracked entities to each other via their keys, even if you never included the navigation.
IsLoaded
db.Entry(e).Collection(...).IsLoaded — whether EF thinks a navigation has been fully loaded.
Required vs optional navigation
Required (non-nullable FK) produces INNER JOIN; optional (nullable FK) produces LEFT JOIN.
ToQueryString()
EF Core 5+: returns the SQL a LINQ query will run, without running it. Ideal for learning and debugging.
Quick notes
  • No Include = navigation stays null (reference) or empty (collection) — unless fix-up or lazy loading fills it.
  • Every Include of a collection multiplies rows in a single query. Two collections = rows of A × rows of B (Tuesday).
  • Filtered Include filters only the included children, never the parent rows.
  • Explicit loading is a deliberate extra query. Lazy loading is a hidden extra query — that's the danger.
  • Read the SQL for every new query you write: LogTo or ToQueryString().
  • Prefer async (ToListAsync, LoadAsync) in apps; sync versions exist but block a thread.

2. Eager loading: Include and ThenInclude

Without Include, EF Core loads only the columns of the entity you queried. Navigations stay empty — this surprises everyone once.

LoadingDemo.cs
await using var db = Db.Create();

var plain = await db.Orders.FirstAsync(o => o.Id == 1);
Console.WriteLine(plain.Customer is null);      // True  — not loaded (no Include, nothing tracked yet)
Console.WriteLine(plain.Lines.Count);           // 0     — empty list from the initialiser, NOT "no lines"

var order = await db.Orders
    .Include(o => o.Customer)                    // reference navigation
    .Include(o => o.Lines)                       // collection navigation
        .ThenInclude(l => l.Product)             // one level deeper, from each line
            .ThenInclude(p => p.Category)        // and deeper again
    .FirstAsync(o => o.Id == 1);

Console.WriteLine($"{order.Customer.Name}, {order.Customer.City}");    // Asha Rao, Pune
foreach (var l in order.Lines)
    Console.WriteLine($"  {l.Product.Name} ({l.Product.Category.Name}) × {l.Quantity} @ ₹{l.UnitPrice}");
//   Basmati Rice 5kg (Grocery) × 2 @ ₹649.00
//   Steel Water Bottle (Home) × 1 @ ₹399.00

Note: by the time we run the second query, order 1 is already tracked from the first query, and EF reuses that same instance — Include fills in its navigations. That is relationship fix-up at work.

To include two separate paths from the same collection, repeat the Include:

var orders = await db.Orders
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .Include(o => o.Lines).ThenInclude(l => l.Order)       // second path, starts again at Lines
    .ToListAsync();

// String-based include works too (handy when building paths dynamically):
var same = await db.Orders.Include("Lines.Product").ToListAsync();

       [c].[Id], [c].[City], [c].[Email], [c].[Name],

LEFT JOIN (
    SELECT [l].[Id], [l].[OrderId], [l].[ProductId], [l].[Quantity], [l].[UnitPrice],
           [p].[Id] AS [Id0], [p].[CategoryId], [p].[Name], [p].[Price], [p].[Sku], [p].[Stock]
    FROM [OrderLines] AS [l]
    INNER JOIN [Products] AS [p] ON [l].[ProductId] = [p].[Id]
) AS [s] ON [o].[Id] = [s].[OrderId]                                    -- collection → LEFT JOIN
WHERE [o].[Id] = 1
ORDER BY [o].[Id], [c].[Id], [s].[Id]                                   -- keys, so EF can stitch rows back
What you wroteWhat SQL Server sees
Include of a required referenceINNER JOIN
Include of an optional referenceLEFT JOIN
Include of a collectionLEFT JOIN (orders with no lines must still appear) + ORDER BY keys
ThenInclude inside a collectionA subquery joined in, as above
Several collection IncludesSeveral LEFT JOINs → row multiplication (Tuesday: split queries)
Tip. The trailing ORDER BY on keys is how EF Core turns one flat, repeated result set back into an object graph: it reads rows in key order and starts a new Order object whenever o.Id changes.

3. Filtered Include (EF Core 5+)

Load customers with only their last three paid orders, newest first:

var customers = await db.Customers
    .Where(c => c.City == "Pune")
    .Include(c => c.Orders
        .Where(o => o.Status == OrderStatus.Paid)
        .OrderByDescending(o => o.OrderDateUtc)
        .Take(3))
    .ToListAsync();

foreach (var c in customers)
    Console.WriteLine($"{c.Name}: {c.Orders.Count} recent paid orders");
// Asha Rao: 3 recent paid orders
// Kiran Patil: 1 recent paid orders     ← customers with no matching orders are still returned
Gotcha. Filtered Include filters the children, never the parents — customers without paid orders still come back with an empty list. To filter parents, add a normal Where(c => c.Orders.Any(...)).
Gotcha. With a tracking query, fix-up can add children you filtered out: if an earlier query in the same context already loaded Asha's cancelled orders, they appear in c.Orders too. Use a fresh context or AsNoTracking() when the filtered collection must be exact. You also can't apply two different filters to the same navigation in one query.

4. Explicit loading

Load the entity first, decide later whether you need its relations. Useful when the decision depends on the data (e.g. only load lines for high-value orders), or for a single entity in a detail screen.

ExplicitLoading.cs
var customer = await db.Customers.SingleAsync(c => c.Email == "ravi.kumar@example.in");

// Collection navigation
await db.Entry(customer).Collection(c => c.Orders).LoadAsync();
Console.WriteLine(customer.Orders.Count);                                   // 3

// Reference navigation
var anOrder = customer.Orders[0];
await db.Entry(anOrder).Reference(o => o.Customer).LoadAsync();              // already loaded → no SQL sent?
Console.WriteLine(db.Entry(anOrder).Reference(o => o.Customer).IsLoaded);    // True

// Query() lets you filter or aggregate WITHOUT loading the whole collection
int pending = await db.Entry(customer)
    .Collection(c => c.Orders)
    .Query()                                                    // IQueryable<Order> for this customer only
    .CountAsync(o => o.Status == OrderStatus.Pending);
Console.WriteLine($"Pending: {pending}");                       // Pending: 1  → SELECT COUNT(*) ... WHERE CustomerId = @p

// Load only some children into the navigation
await db.Entry(customer).Collection(c => c.Orders).Query()
    .Where(o => o.OrderDateUtc >= new DateTime(2026, 1, 1))
    .Include(o => o.Lines)
    .LoadAsync();

About the reference line: anOrder.Customer was already connected by fix-up when we loaded the orders, so IsLoaded is true. Load on a navigation that's already marked loaded does nothing; on one that isn't, it always sends SQL.

5. Lazy loading — and why most teams turn it off

With lazy-loading proxies, reading a navigation triggers a query automatically. Setup:

dotnet add Store.Data package Microsoft.EntityFrameworkCore.Proxies
Lazy loading setup (fragment)
// 1) Turn it on
var options = new DbContextOptionsBuilder<StoreDbContext>()
    .UseLazyLoadingProxies()
    .UseSqlServer(Db.ConnectionString)
    .Options;

// 2) Every navigation must be virtual, and entity classes public and NOT sealed
public class Customer
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public required string Email { get; set; }
    public string City { get; set; } = "";
    public virtual List<Order> Orders { get; set; } = [];
}

public class Order
{
    public int Id { get; set; }
    public int CustomerId { get; set; }
    public virtual Customer Customer { get; set; } = null!;
    public virtual List<OrderLine> Lines { get; set; } = [];
    // ...
}
await using var db = new StoreDbContext(options);
var customers = await db.Customers.ToListAsync();        // 1 query

foreach (var c in customers)
{
    // Each access to c.Orders silently runs: SELECT ... FROM Orders WHERE CustomerId = @p
    Console.WriteLine($"{c.Name}: {c.Orders.Count} orders");
}
// 50 customers → 1 + 50 = 51 round trips. This is the N+1 problem (Tuesday).
RiskWhat happens
Hidden N+1 queriesLoops over entities fire one query per item; fine on 5 dev rows, painful on 5,000 production rows.
Disposed contextTouching a navigation after the DbContext is disposed: EF can't load it. By default this is reported as an error (an InvalidOperationException from the LazyLoadOnDisposedContextWarning).
Serialization stormsReturning entities from a Web API: the JSON serializer walks every navigation → loads the whole graph, or loops on cycles.
Sync I/OLazy loads are synchronous database calls, even inside async methods.
Design constraintsEvery navigation virtual, classes unsealed; proxies are a different runtime type (Castle.Proxies.CustomerProxy).

Without proxies, an entity can take an ILazyLoader in its constructor and call loader.Load(this, ref _orders) in the getter — same behaviour, more plumbing, and your domain class now references EF Core. Rarely worth it.

Common mistakes

  • Expecting order.Customer to be filled without an Include — then "fixing" the NullReferenceException with lazy loading.
  • Reading order.Lines.Count == 0 as "no lines" when the collection was simply never loaded.
  • Including whole graphs "just in case" — every Include adds JOINs and columns.
  • Assuming filtered Include filters the parent rows.
  • Turning on lazy loading in a Web API and returning entities directly from controllers.

Self-check questions

Why might order.Lines be empty even though the order has lines in the database?EF Core doesn't load navigations unless asked. Without Include, explicit or lazy loading (or fix-up from earlier queries in the same context), the collection is just the empty list from the property initialiser.
What does filtered Include filter?Only the included child collection. The parent rows are unaffected; use a separate Where on the parent query to filter parents.
What two things does lazy loading with proxies require on your entity classes?Navigation properties must be virtual and the classes must be public and not sealed, so Castle can generate a subclass that overrides them. You also need the Proxies package and UseLazyLoadingProxies().

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat are the three ways to load related data in EF Core?
Eager loading with Include/ThenInclude in the same query; explicit loading with context.Entry(e).Collection(...)/Reference(...).Load() later on demand; and lazy loading, where reading a navigation triggers a query automatically via proxies or ILazyLoader. A fourth common option is projecting with Select, which pulls related columns without loading entities.
BasicWhat SQL does Include produce?
A JOIN in the same statement: INNER JOIN for a required reference, LEFT JOIN for optional references and collections. For collections EF also adds ORDER BY on the keys so it can rebuild the object graph from the flat rows.
IntermediateWhat is filtered Include and what are its limitations?
Since EF Core 5 you can write Include(c => c.Orders.Where(...).OrderBy(...).Take(n)). Only Where, OrderBy/ThenBy (and Descending), Skip and Take are allowed. It filters children, not parents; the same navigation can't be included with two different filters; and in tracking queries, fix-up can add already-tracked children that don't match the filter.
IntermediateWhy do many teams disable lazy loading?
It hides database calls behind property access, so loops cause N+1 queries, it fails after the context is disposed, serializers trigger loading of entire graphs, and the loads are synchronous. Eager loading or projections make the data access explicit and reviewable.
IntermediateWhat is relationship fix-up?
When entities are tracked by the same DbContext, EF Core connects their navigations automatically using foreign keys. If you load orders and, separately, their customers, each order.Customer gets set even though you never included it. It's useful, but it can also make navigations look 'loaded' unexpectedly.
IntermediateHow would you count a customer's pending orders without loading all their orders?
Explicit loading's Query(): db.Entry(customer).Collection(c => c.Orders).Query().CountAsync(o => o.Status == OrderStatus.Pending), which sends a single SELECT COUNT(*) ... WHERE CustomerId = @p AND Status = .... Or simply db.Orders.CountAsync(o => o.CustomerId == id && ...).
DAY 2 · TUE

N+1, AsNoTracking, projections to DTOs, AsSplitQuery vs single query

GoalSpot and fix N+1 queries, reduce memory with no-tracking reads, project only the columns you need, and decide when to split a multi-collection query.

Key definitions

N+1 problem
A query that returns N rows, then fires one more query per row to load a navigation — 1 + N round trips instead of 1.
LogTo
DbContextOptionsBuilder.LogTo(Console.WriteLine, ...) routes EF's log to the console so you can count SQL statements.
AsNoTracking
Instructs EF Core not to add entities to the change tracker. Faster and uses less memory for read-only queries.
AsNoTrackingWithIdentityResolution
Like AsNoTracking but still de-duplicates objects: the same Customer row in multiple Order rows becomes one C# object.
Identity resolution
EF's guarantee that one database row maps to exactly one object instance in a tracking query.
Projection
A Select(x => new Dto { ... }) that asks the database for only the columns you name, skipping navigation loading entirely.
DTO (Data Transfer Object)
A plain class or record carrying only the data needed by a caller — no navigations, no change tracker.
AsSplitQuery
EF Core 5+: Tells EF to run one SELECT per included collection instead of one big JOIN, avoiding cartesian explosion.
Cartesian explosion
When a query joins two or more collections and the row count multiplies: an order with 5 lines and 5 tags yields 25 rows per order.
UseQueryTrackingBehavior
A context-level default for tracking; override per-query with AsTracking() or AsNoTracking().
Quick notes
  • Run every new query through LogTo and count the SQL statements — the number should not surprise you.
  • AsNoTracking skips snapshot creation; benchmarks typically show 2–5× less memory and 10–30% faster reads for read-only paths.
  • Projection to a DTO usually beats Include: it generates a narrower SELECT and returns no tracked objects to dispose.
  • AsSplitQuery fixes cartesian explosion but adds round trips — still better than millions of duplicate rows.
  • The global default for AsSplitQuery can be set in OnConfiguring; override per-query with AsSingleQuery().

1. Spotting N+1 with LogTo

The pattern is easy to miss because each query looks innocent:

N+1Demo.cs
await using var db = Db.Create(logSql: true);   // LogTo is active

var customers = await db.Customers.ToListAsync();     // 1 query: SELECT * FROM Customers
foreach (var c in customers)
{
    // ❌ Each iteration fires: SELECT * FROM Orders WHERE CustomerId = @p
    Console.WriteLine($"{c.Name} has {c.Orders.Count} orders");
}
// With 50 customers → 1 + 50 = 51 queries. Console shows them all.
Tip. Turn on LogTo during development. The right number of SQL statements for a list page is almost always 1 (or 2 with AsSplitQuery).

Fix: Include

var customers = await db.Customers
    .Include(c => c.Orders)
    .ToListAsync();
// 1 query. EF joins Orders in and populates c.Orders from the result set.

Fix: projection (often better)

var summaries = await db.Customers
    .Select(c => new {{ c.Name, c.City, OrderCount = c.Orders.Count }})
    .ToListAsync();
// 1 query:
// SELECT c.Name, c.City, (SELECT COUNT(*) FROM Orders WHERE CustomerId = c.Id) AS OrderCount
// FROM Customers AS c
// No navigation loaded at all.

2. AsNoTracking — faster read-only queries

NoTracking.cs
await using var db = Db.Create(logSql: false);

// ✓ No tracking: entities are not added to the ChangeTracker snapshot
var orders = await db.Orders
    .AsNoTracking()
    .Include(o => o.Customer)
    .Where(o => o.Status == OrderStatus.Paid)

var withId = await db.Orders

    .Include(o => o.Customer)
    .Where(o => o.Status == OrderStatus.Paid)
    .ToListAsync();
// Now orders[0].Customer == orders[1].Customer if they share the same CustomerId ✓

4. Cartesian explosion and AsSplitQuery

When you Include two or more collections on the same entity, EF joins them all in one SELECT. The result set has one row for every combination of children:

// Suppose an Order has 5 Lines and 5 Tags.
// A single query returns 5 × 5 = 25 rows per order — the data is repeated 5× each.
// With 100 orders: 2,500 rows on the wire, most of them duplicates.
var orders = await db.Orders
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .Include(o => o.Tags)                              // second collection → explosion
    .ToListAsync();

Fix: AsSplitQuery

SplitQuery.cs
var orders = await db.Orders
    .Include(o => o.Lines).ThenInclude(l => l.Product)
    .Include(o => o.Tags)
    .AsSplitQuery()          // EF runs: 1 SELECT for Orders+Lines+Products, 1 for Tags
    .ToListAsync();
// 2 round trips, but far fewer bytes and no duplicate data.

// Apply globally in OnConfiguring:

GoalDrop below LINQ when you need control: parameterised raw SQL, bulk mutations without loading entities, stored procedures, and compiled queries for hot paths.

Key definitions

FromSql
db.Products.FromSql($"...") — executes raw SQL that returns entity columns; maps the results to tracked entities. The $ interpolated string is automatically parameterised.
FromSqlRaw
db.Products.FromSqlRaw("...{0}", value) — raw SQL with explicit positional parameters. Use when the SQL is not a C# interpolated string.
SqlQuery
db.Database.SqlQuery<T>() (EF Core 7+) — returns arbitrary scalar/DTO types from raw SQL, not entity types.
ExecuteUpdate
db.Products.Where(...).ExecuteUpdate(s => s.SetProperty(p => p.Stock, 0)) — bulk UPDATE without loading or tracking entities (EF Core 7+).
ExecuteDelete
db.Products.Where(...).ExecuteDelete() — bulk DELETE without loading entities (EF Core 7+).
Stored procedure
Pre-compiled SQL stored in the database, executed with FromSql or Database.ExecuteSqlRaw.
Output parameter
A SqlParameter with Direction = Output; used to get scalar values back from a stored proc.
Compiled query

Inserting malicious SQL via user input. Never concatenate user strings into SQL; always parameterise.

C#'s type for interpolated strings: $"...{value}". EF's FromSql accepts it and uses the holes as parameters, not string concatenation.
Quick notes
  • FromSql with an interpolated string is safe — EF parameterises the holes. FromSqlRaw with string concatenation is not.
  • FromSql must SELECT all entity columns (or at least the ones mapped); you can compose further LINQ on top.
  • ExecuteUpdate / ExecuteDelete bypass the change tracker and do not trigger interceptors or SaveChanges.
  • Compiled queries pay off only on very high-frequency paths (thousands per second); measure first.
  • Stored procedures that return a result set map nicely to FromSql; those that don't return rows use ExecuteSqlRaw.

Optimistic concurrency, transactions and execution strategies

GoalHandle concurrent edits with rowversion, recover from DbUpdateConcurrencyException, and manage transactions — including how execution strategies interact with explicit transactions.

Key definitions

Optimistic concurrency
Assumes conflicts are rare: let two users read the same row, but detect and reject a second save if the first already changed it.
rowversion
A SQL Server 8-byte binary column (ROWVERSION / TIMESTAMP) auto-incremented by the engine on every UPDATE. EF Core maps it with [Timestamp].
ConcurrencyToken
Any column marked [ConcurrencyCheck] or via Fluent API IsConcurrencyToken(); EF adds its current value to the WHERE clause of every UPDATE/DELETE.
DbUpdateConcurrencyException
Thrown when no row was affected by an UPDATE/DELETE because another writer changed the row first. Its Entries property gives the conflicting entities.
Reload strategy
Discard your changes and reload from the database — "last writer wins, but you're the loser".
Client-wins strategy
Keep your proposed values and overwrite the database — use only when you're certain this is correct.
Merge strategy
Read the current DB values and re-apply your changes where there's no overlap — most sophisticated.
Implicit transaction
Every SaveChanges call runs inside its own transaction automatically.
BeginTransaction
db.Database.BeginTransactionAsync() opens an explicit transaction for multiple SaveChanges calls.
Execution strategy
A retry policy (EnableRetryOnFailure) that re-runs the whole operation on transient errors — connection drops, SQL Server restart, Azure SQL throttling.
Idempotent operation
An operation that can run multiple times and produce the same result — required when execution strategies retry.
Quick notes
  • Every UPDATE/DELETE with a rowversion adds WHERE RowVersion = @orig; 0 rows affected = exception.
  • Entries[0].GetDatabaseValues() costs one extra round trip — do it only when you need to merge.
  • Always catch DbUpdateConcurrencyException in a retry loop, not just once; two users may both fail and retry.
  • Implicit transactions wrap a single SaveChanges; for "all or nothing" across two SaveChanges calls, use an explicit transaction.
  • You can't use db.Database.BeginTransaction() inside an execution strategy — wrap the whole retry in strategy.ExecuteAsync.

2. Detecting and handling the conflict

ConcurrencyDemo.cs
// Two users both load order 1 at the same time
await using var db1 = Db.Create(logSql: false);
await using var db2 = Db.Create(logSql: false);

var order1 = await db1.Orders.SingleAsync(o => o.Id == 1);
var order2 = await db2.Orders.SingleAsync(o => o.Id == 1);

// User 1 ships the order and saves
order1.Status = OrderStatus.Shipped;
await db1.SaveChangesAsync();      // succeeds; RowVersion bumped by SQL Server

// User 2 (db2) now tries to cancel — but the row changed
order2.Status = OrderStatus.Cancelled;
try
{
    await db2.SaveChangesAsync();   // ❌ DbUpdateConcurrencyException: 0 rows affected
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var dbValues = await entry.GetDatabaseValuesAsync();   // 1 extra round trip
    if (dbValues is null)
    {
        Console.WriteLine("Order was deleted by another user.");
        return;
    }

    var dbStatus = (OrderStatus)dbValues[nameof(Order.Status)]!;
    Console.WriteLine($"Conflict: DB has Status={dbStatus}, you wanted Cancelled");

    // ---- Strategy 1: Reload (discard local changes) ----
    // entry.OriginalValues.SetValues(dbValues);   // update original so EF no longer sees a conflict
    // entry.CurrentValues.SetValues(dbValues);    // discard local changes

    // ---- Strategy 2: Client wins (force your values over the DB) ----
    // entry.OriginalValues.SetValues(dbValues);   // update rowversion so the next save succeeds

    // ---- Strategy 3: Merge (combine non-conflicting fields) ----
    var currentValues = entry.CurrentValues;
    foreach (var prop in dbValues.Properties)
    {{
        var dbVal     = dbValues[prop];
        var clientVal = currentValues[prop];
        var origVal   = entry.OriginalValues[prop];
        // Keep client value only if neither we nor the other writer changed it
        currentValues[prop] = Equals(clientVal, origVal) ? dbVal : clientVal;
    }}
    entry.OriginalValues.SetValues(dbValues);   // accept new rowversion

    await db2.SaveChangesAsync();               // retry
}

Common mistakes

Self-check questions

What is an owned type and when would you use it?An entity whose identity depends on its owner — it has no DbSet, no primary key of its own, and maps to the owner's table (OwnsOne) or a dependent table (OwnsMany). Use it for value objects: Address, Money, GeoCoordinate.
What does IgnoreQueryFilters do?It tells EF to skip all global HasQueryFilter predicates for that specific query — useful for admin screens, includes of soft-deleted children, or seeding checks.
Why can't you set navigation properties in HasData?HasData works at the migration level where EF serialises property values into SQL INSERTs. Navigation properties are EF runtime concepts, not column values, so they can't be represented.

BasicWhat is a global query filter and how is it applied to Include?
A predicate added with HasQueryFilter that EF appends automatically to every query on that entity type. When a filtered type is loaded via Include, the filter applies to the children too — only children matching the filter are included.
BasicOwned type vs a separate entity — when would you choose each?

IntermediateHow do shadow properties work and what are they useful for?
Shadow properties exist in the EF model and map to a database column, but have no corresponding C# property on the class. Useful for cross-cutting columns (CreatedAt, UpdatedAt, TenantId, IsDeleted) that you don't want on every entity class. Set them in a SaveChanges override and query them with EF.Property<T>.
IntermediateWhat are the limitations of value conversions?
Conversions run in memory, not in the database. If EF can't translate a LINQ expression that uses the unconverted type, the query falls back to client-side evaluation or throws. Keep converters simple; test complex ones with ToQueryString() to verify they translate correctly.
IntermediateHasData vs custom seeding — when is each appropriate?
HasData is best for stable reference data (categories, roles, country codes) that ships with the app and changes rarely; it's tracked in migrations, so changes generate UPDATE/DELETE SQL. Custom seeding is better for large data sets, data with relationships, or anything that changes between environments — seed it at startup with an idempotent check.
IntermediateHow does the enum-to-string value conversion affect migrations?
The column type changes from int to nvarchar(N). Migration 'down' scripts need to handle the reverse. With enum-to-string the column is human-readable and survives reordering of enum members; with int storage, inserting a new member before existing ones breaks all existing rows.

Data/Interceptors/AuditAndSoftDeleteInterceptor.cs
using Core.Interfaces;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Diagnostics;

namespace Data.Interceptors;

public sealed class AuditAndSoftDeleteInterceptor(ICurrentUserService currentUser) : SaveChangesInterceptor
{{
    // Called synchronously
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData, InterceptionResult<int> result)
    {{
        Intercept(eventData.Context);
        return base.SavingChanges(eventData, result);
    }}

    // Called by SaveChangesAsync
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result,
        CancellationToken cancellationToken = default)
    {{
        Intercept(eventData.Context);
        return base.SavingChangesAsync(eventData, result, cancellationToken);
    }}

    private void Intercept(DbContext? context)
    {{
        if (context is null) return;
        var now  = DateTime.UtcNow;
        var user = currentUser.UserName;

        foreach (var entry in context.ChangeTracker.Entries())
        {{
            // ── Soft delete ──────────────────────────────────────────────
            if (entry.State == EntityState.Deleted && entry.Entity is ISoftDeletable sd)
            {{
                entry.State = EntityState.Modified;    // turn DELETE into UPDATE
                sd.IsDeleted  = true;
                sd.DeletedAt  = now;
                sd.DeletedBy  = user;

                // Don't stamp audit fields for a soft delete — treat it as the final update
                continue;
            }}

            // ── Audit fields ─────────────────────────────────────────────
            if (entry.Entity is IAuditable auditable)
            {{
                auditable.UpdatedAt = now;
                auditable.UpdatedBy = user;
                if (entry.State == EntityState.Added)
                {{
                    auditable.CreatedAt = now;
                    auditable.CreatedBy = user;
                }}
            }}
        }}
    }}
}}

namespace Data;

public class AppDbContext : DbContext
{{
    public DbSet<Product> Products => Set<Product>();

    private readonly AuditAndSoftDeleteInterceptor _interceptor;

    public AppDbContext(DbContextOptions<AppDbContext> options,
                        AuditAndSoftDeleteInterceptor interceptor) : base(options)
    {{
        _interceptor = interceptor;
    }}

    protected override void OnConfiguring(DbContextOptionsBuilder options)
    {{
        options.AddInterceptors(_interceptor);
    }}

    protected override void OnModelCreating(ModelBuilder model)
    {{
        // Apply soft-delete filter to every ISoftDeletable entity
        foreach (var entityType in model.Model.GetEntityTypes())
        {{
            if (typeof(ISoftDeletable).IsAssignableFrom(entityType.ClrType))
                model.Entity(entityType.ClrType)
                     .HasQueryFilter(BuildIsDeletedFilter(entityType.ClrType));
        }}
    }}

    private static System.Linq.Expressions.LambdaExpression BuildIsDeletedFilter(Type type)
    {{
        var param = System.Linq.Expressions.Expression.Parameter(type, "e");
        var prop  = System.Linq.Expressions.Expression.Property(param, nameof(ISoftDeletable.IsDeleted));
        var body  = System.Linq.Expressions.Expression.Not(prop);
        return System.Linq.Expressions.Expression.Lambda(body, param);
    }}
}}

BasicWhat is the purpose of a SaveChangesInterceptor?
It runs code just before SaveChanges flushes to the database, letting you inspect and modify tracked entries — set audit timestamps, turn deletes into soft-deletes, validate business rules, or raise domain events.
BasicWhy convert EntityState.Deleted to EntityState.Modified in a soft-delete interceptor?

IntermediateHow do you apply a global query filter dynamically to all entities that implement an interface?
Iterate modelBuilder.Model.GetEntityTypes(), check if each entity's ClrType implements the interface, and call modelBuilder.Entity(clrType).HasQueryFilter(lambdaExpression). The lambda is built at runtime with Expression.Lambda to match the entity's type.
IntermediateWhat is the relationship between the interceptor and the implicit transaction?
The interceptor runs before EF flushes to the database, inside the implicit transaction. If SaveChanges fails (e.g. a constraint violation) the transaction rolls back, undoing the interceptor's mutations as well — there is no partial state.

Q1. How many SQL statements does this code send? 
await using var db = Db.Create(logSql: false);
var customers = await db.Customers.ToListAsync();
int total = 0;
foreach (var c in customers)
    total += c.Orders.Count;
Console.WriteLine(total);
1 + N (where N = number of customers). c.Orders is not loaded; each access returns the empty list (0), so total is always 0 — but only because tracking is on and the Orders property was never loaded. If lazy loading were enabled it would fire N queries. Fix: Include(c => c.Orders) or project to a count DTO.
Q2. Does this compile and what does it do? 
await db.Products.Where(p => p.Name.StartsWith("B"))
                 .ExecuteUpdateAsync(s =>
                     s.SetProperty(p => p.Stock, p => p.Stock - 1));
Yes, compiles and runs. Sends one SQL: UPDATE Products SET Stock = Stock - 1 WHERE Name LIKE 'B%' AND IsDeleted = 0. No entities are loaded. The global query filter still applies (adds the IsDeleted check).
Q3. What exception type is thrown and why? 
await using var db1 = Db.Create();
await using var db2 = Db.Create();
var o1 = await db1.Orders.FindAsync(1);
var o2 = await db2.Orders.FindAsync(1);

await db2.SaveChangesAsync();   // ?
DbUpdateConcurrencyException. db1's save bumps the rowversion. db2's UPDATE WHERE RowVersion = @orig finds 0 rows; EF detects this and throws.
Q4. What does the global filter add to this query? 
var products = await db.Products
    .Where(p => p.Price > 500)
    .OrderBy(p => p.Name)
    .ToListAsync();
WHERE Price > 500 AND IsDeleted = 0 (or whatever the filter predicate is). EF ANDs the global filter onto every query automatically.

var order = await db.Orders.AsNoTracking().FirstAsync();

await db.SaveChangesAsync();

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat does ToQueryString() return?
The SQL string the LINQ query will execute, without actually running it. Available on IQueryable. Great for learning and debugging — paste the output into SSMS to see the execution plan.
BasicName three signs of an EF performance problem in the logs.
(1) Multiple SELECT ... WHERE ForeignKeyId = @p statements in a loop — N+1. (2) SELECT with no WHERE on a large table — full table scan. (3) Very large result set with many duplicate columns — cartesian explosion from multiple collection Includes.
IntermediateWhy does SaveChanges return 0 for an AsNoTracking entity?
AsNoTracking entities are not registered in the ChangeTracker. SaveChanges only flushes tracked entries in Added, Modified or Deleted state. An untracked entity has no state, so SaveChanges has nothing to do — silent no-op.
IntermediateHow does the soft-delete interceptor interact with ExecuteDelete?
SaveChangesInterceptor only fires for changes tracked by the ChangeTracker (entries going through SaveChanges). ExecuteDelete bypasses the ChangeTracker and runs a SQL DELETE directly — the interceptor is never called. Use ExecuteUpdate to soft-delete in bulk: set IsDeleted = true, DeletedAt = now explicitly.
