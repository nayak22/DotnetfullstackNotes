DAY 1 · MON

Stored procedures: parameters, OUTPUT, RETURN and EXEC

GoalWrite, alter and call stored procedures with input parameters, defaults, OUTPUT parameters and return codes — and pick up the habits (SET NOCOUNT ON, no sp_ prefix) that mark production-quality T-SQL.

Key definitions

Stored procedure
A named, precompiled batch of T-SQL saved in the database, called with EXEC. Can take parameters, return result sets, OUTPUT values and an integer return code.
Batch
A set of statements sent to SQL Server as one unit. In scripts, GO (a client-tool word, not T-SQL) separates batches.
CREATE OR ALTER
Creates the procedure if missing, otherwise replaces its body while keeping permissions. SQL Server 2016 SP1+.
Input parameter
A typed value passed into the proc: @DepartmentId INT. Parameters are the only safe way to pass user input (no string concatenation).
Default parameter
A parameter with a declared default (@Top INT = 10) that the caller may omit or pass as DEFAULT.
OUTPUT parameter
A parameter the proc writes back to the caller. Marked OUTPUT in the proc and at the call site.
RETURN code
An integer the proc hands back with RETURN n; by convention 0 = success, non-zero = a status/error code. Captured with EXEC @rc = proc.
EXEC / EXECUTE
Runs a procedure (or a string — dynamic SQL, used sparingly). Parameters can be positional or named.
SCOPE_IDENTITY()
The last identity value generated in the current scope — the right way to grab a new row's id inside a proc.
SET NOCOUNT ON
Suppresses the "(n rows affected)" message per statement, cutting network chatter. First line of almost every proc.
Plan cache
Where SQL Server keeps compiled execution plans. A proc's plan is compiled on first execution and reused.
Parameter sniffing
At first compile, SQL Server "sniffs" the actual parameter values and optimises the plan for them — great until a very different value reuses the same plan.
sp_ prefix
Reserved by convention for system procedures in master. User procs named sp_… cost an extra lookup and risk name collisions — use usp_ or none.
OBJECT_DEFINITION
Returns a module's source: SELECT OBJECT_DEFINITION(OBJECT_ID('dbo.usp_X')). sys.procedures lists all procs.
Quick notes
  • A proc gives you: one place for logic, parameterisation (no SQL injection), a cached plan, and a security boundary (grant EXECUTE, not table access).
  • CREATE OR ALTER beats DROP + CREATE: permissions and dependencies survive.
  • Call with named parameters: EXEC usp_X @DepartmentId = 2 — positional calls break silently when parameters are reordered.
  • OUTPUT must appear in both places: the parameter declaration and the call site, or the value is silently not copied back.
  • RETURN can only carry an int. Data belongs in result sets or OUTPUT parameters.
  • Start every proc with SET NOCOUNT ON; and never name it sp_….

1. Why stored procedures?

So far you've sent ad-hoc SELECTs from a query window. In a real system the application calls named, parameterised procedures instead:

BenefitWhy it matters
One definitionThe "employees by department" query lives in one place, not pasted into five C# files.
ParameterisationValues travel as typed parameters — SQL injection through string concatenation becomes impossible.
Plan reuseThe plan is compiled once and cached; later calls skip compilation.
Security boundaryGrant users EXECUTE on procs and no direct table access at all.
Less network trafficMulti-statement logic runs server-side in one round trip.
first-proc.sql
CREATE OR ALTER PROCEDURE dbo.usp_GetEmployeesByDepartment
    @DepartmentId INT
AS
BEGIN
    SET NOCOUNT ON;

    SELECT EmployeeId, FirstName, LastName, Salary
    FROM dbo.Employees
    WHERE DepartmentId = @DepartmentId
      AND IsActive = 1
    ORDER BY LastName;
END
GO

EXEC dbo.usp_GetEmployeesByDepartment @DepartmentId = 2;
-- Example output (your Week 11 seed data decides the rows)
EmployeeId  FirstName   LastName    Salary
----------- ----------- ----------- -----------
4           Divya       Kulkarni    58000.00
2           Rahul       Mehta       72500.00
Tip. The body between AS and the end of the batch is the proc. Wrapping it in BEGIN … END is optional but makes the boundary explicit — always do it.

2. Default parameters and optional filters

search-employees.sql
CREATE OR ALTER PROCEDURE dbo.usp_SearchEmployees
    @Search       NVARCHAR(50)  = NULL,     -- NULL means "don't filter on this"
    @DepartmentId INT           = NULL,
    @MinSalary    DECIMAL(10,2) = 0
AS
BEGIN
    SET NOCOUNT ON;

    SELECT e.EmployeeId, e.FirstName, e.LastName, d.Name AS Department, e.Salary
    FROM dbo.Employees e
    JOIN dbo.Departments d ON d.DepartmentId = e.DepartmentId
    WHERE (@Search IS NULL OR e.FirstName LIKE N'%' + @Search + N'%'
                           OR e.LastName  LIKE N'%' + @Search + N'%')
      AND (@DepartmentId IS NULL OR e.DepartmentId = @DepartmentId)
      AND e.Salary >= @MinSalary
      AND e.IsActive = 1
    ORDER BY e.LastName;
END
GO

EXEC dbo.usp_SearchEmployees;                                    -- all defaults: everyone
EXEC dbo.usp_SearchEmployees @DepartmentId = 2;                  -- named (recommended)
EXEC dbo.usp_SearchEmployees N'ra', 2, 50000;                    -- positional: fragile
EXEC dbo.usp_SearchEmployees @Search = DEFAULT, @MinSalary = 60000;  -- explicit default
Note. The (@p IS NULL OR col = @p) "catch-all" pattern is handy but produces one plan for very different searches — a classic parameter-sniffing victim. For now add OPTION (RECOMPILE) to the SELECT if it gets slow; Week 14 explains why.

3. OUTPUT parameters

Use OUTPUT when the caller needs a scalar back in addition to (or instead of) a result set — a new id, a count, a total.

hire-employee.sql
CREATE OR ALTER PROCEDURE dbo.usp_HireEmployee
    @FirstName     NVARCHAR(50),
    @LastName      NVARCHAR(50),
    @Email         NVARCHAR(100),
    @DepartmentId  INT,
    @Salary        DECIMAL(10,2),
    @NewEmployeeId INT OUTPUT                 -- marked OUTPUT here...
AS
BEGIN
    SET NOCOUNT ON;

    INSERT dbo.Employees (FirstName, LastName, Email, DepartmentId, Salary, HireDate)
    VALUES (@FirstName, @LastName, @Email, @DepartmentId, @Salary, CAST(GETDATE() AS DATE));

    SET @NewEmployeeId = SCOPE_IDENTITY();    -- identity from THIS scope, not a trigger's
END
GO

DECLARE @id INT;
EXEC dbo.usp_HireEmployee
     @FirstName = N'Kavya', @LastName = N'Reddy', @Email = N'kavya.reddy@lnw-demo.in',
     @DepartmentId = 2, @Salary = 61000,
     @NewEmployeeId = @id OUTPUT;             -- ...and OUTPUT again here
SELECT @id AS NewEmployeeId;
NewEmployeeId
-------------
11
Gotcha. Forget OUTPUT at the call site and the call still succeeds — but @id stays NULL. No error, just a silently missing value. This is one of the most common proc bugs.

Prefer SCOPE_IDENTITY() over @@IDENTITY: @@IDENTITY returns the last identity in the session, which can be a different table's id if a trigger inserted somewhere.

4. RETURN codes

return-codes.sql
CREATE OR ALTER PROCEDURE dbo.usp_DeactivateEmployee
    @EmployeeId INT
AS
BEGIN
    SET NOCOUNT ON;

    IF NOT EXISTS (SELECT 1 FROM dbo.Employees WHERE EmployeeId = @EmployeeId)
        RETURN 1;                 -- not found
    IF EXISTS (SELECT 1 FROM dbo.Employees WHERE EmployeeId = @EmployeeId AND IsActive = 0)
        RETURN 2;                 -- already inactive

    UPDATE dbo.Employees SET IsActive = 0 WHERE EmployeeId = @EmployeeId;
    RETURN 0;                     -- success (also the default when you fall off the end)
END
GO

DECLARE @rc INT;
EXEC @rc = dbo.usp_DeactivateEmployee @EmployeeId = 999;

6. Habits: SET NOCOUNT ON, naming, and the sniffing teaser

  • SET NOCOUNT ON — without it every statement sends a "rows affected" message to the client; chatty and occasionally confuses old data-access layers that mistake the message for a result.
  • Never sp_ — SQL Server first looks for sp_… names in master, so you pay a lookup detour, and a future system proc with your name wins. Use usp_ (user stored procedure) like this course, or a clean verb-noun name.
  • Schema-qualify — write dbo.usp_X when creating and calling; it avoids resolution ambiguity and helps plan reuse.
  • One proc, one purpose — a proc that takes 14 optional parameters and 6 modes is five procs in a trench coat.

Parameter sniffing in one paragraph: the first call's parameter values shape the cached plan. EXEC usp_SearchEmployees @DepartmentId = 7 (3 employees) compiles a plan ideal for 3 rows; when the next call asks for department 1 (4,000 employees) it reuses that tiny-result plan and crawls. Fixes — OPTION (RECOMPILE), OPTIMIZE FOR, rewriting catch-all filters — are a Week 14 topic. Today, just be able to name the phenomenon.

Common mistakes

  • Calling with positional parameters, then reordering the parameter list later — silent wrong results.
  • Forgetting OUTPUT at the call site (the proc runs; the variable stays NULL).
  • Using @@IDENTITY instead of SCOPE_IDENTITY().
  • Naming user procs sp_….
  • Building the WHERE clause by concatenating strings instead of using parameters — SQL injection and no plan reuse.

Self-check questions

What does SET NOCOUNT ON actually suppress?The DONE_IN_PROC "(n rows affected)" messages sent after each statement. Result sets and errors still flow normally; you just drop the chatter.
Why is the sp_ prefix an anti-pattern?Names starting with sp_ are searched in the master database first, costing an extra lookup, and may collide with current or future system procedures that would then take precedence.
How do you get a new identity value out of an insert proc, and why that function?SET an OUTPUT parameter to SCOPE_IDENTITY() right after the INSERT. It returns the last identity generated in the current scope, unlike @@IDENTITY which can return a value generated by a trigger on another table.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat are the advantages of stored procedures over ad-hoc SQL from the application?
Centralised logic (one definition to fix or tune), enforced parameterisation (no injection via concatenation), execution plan reuse, a security boundary (grant EXECUTE without table permissions), and fewer round trips for multi-statement operations.
BasicWhat is the difference between an OUTPUT parameter and a RETURN value?
RETURN carries exactly one int, conventionally 0 for success, and can't be skipped — every proc returns one. OUTPUT parameters carry any number of typed scalars (ids, totals, strings) and must be marked OUTPUT both in the signature and at the call site.
BasicWhat does CREATE OR ALTER do and when is it available?
Since SQL Server 2016 SP1 it creates the module if absent or alters it in place if present — unlike DROP + CREATE it keeps existing permissions, and unlike plain ALTER it doesn't fail on first deployment. It works for procs, views, functions and triggers.
IntermediateWhat is parameter sniffing?
When a proc is first compiled, the optimiser uses the actual parameter values to estimate row counts and choose the plan. The plan is cached and reused for later calls with very different values, which can make it badly wrong (e.g. a plan built for 3 rows scanning for 4 million). Mitigations: OPTION (RECOMPILE), OPTIMIZE FOR, dynamic SQL per shape, or splitting the proc.
IntermediateHow would you lock down a database so applications can only use procs?
Create a role, GRANT EXECUTE ON SCHEMA::dbo (or per proc) to it, add the app login's user to the role, and grant no SELECT/INSERT/UPDATE/DELETE on tables. Ownership chaining lets dbo-owned procs touch dbo-owned tables without the caller holding table permissions.
IntermediateCan a stored procedure return multiple result sets? How does a caller consume them?
Yes — each SELECT that reaches the client adds a result set, in order. ADO.NET readers walk them with SqlDataReader.NextResult(); Dapper uses QueryMultiple; EF Core needs raw ADO.NET or stitching. Keep the order and shapes stable: callers bind by position.
DAY 2 · TUE

Error handling: TRY/CATCH, THROW vs RAISERROR, XACT_STATE

GoalCatch and report T-SQL errors properly: TRY/CATCH with the ERROR_* functions, THROW for raising and rethrowing, and XACT_ABORT + XACT_STATE so failures never leave a transaction half-open.

Key definitions

TRY…CATCH
BEGIN TRY … END TRY BEGIN CATCH … END CATCH. A runtime error (severity > 10) inside TRY jumps to CATCH instead of aborting the batch.
ERROR_NUMBER()
In CATCH: the error's number. System errors are < 50000; your THROWn errors are ≥ 50000.
ERROR_MESSAGE()
In CATCH: the full error text, with substituted values.
ERROR_SEVERITY() / ERROR_STATE()
Severity (how bad) and state (where/why variant) of the caught error.
ERROR_LINE() / ERROR_PROCEDURE()
Line number and module name where the error happened — gold for logging.
Severity
0–10 informational (not catchable), 11–16 user-correctable errors, 17–19 resource errors, 20–25 fatal (connection killed, not catchable in that session).
THROW
Modern (2012+) way to raise an error: THROW 50001, N'msg', 1; — or bare THROW; inside CATCH to rethrow the original. Always severity 16; always terminates the batch.
RAISERROR
Older raise mechanism with printf-style formatting, chooseable severity, WITH LOG / NOWAIT. Does not honour XACT_ABORT and does not abort the batch by default.
Rethrow pattern
CATCH: roll back if needed, log, then bare THROW; so the caller sees the original error, number, and line.
XACT_STATE()
1 = open, committable transaction; -1 = open but doomed (only ROLLBACK allowed); 0 = no transaction.
SET XACT_ABORT ON
Makes (almost) any runtime error abort the batch and roll back the transaction automatically. The safety net for transactional procs.
Doomed transaction
A transaction that can no longer commit (XACT_STATE() = -1); any attempt to COMMIT or to write throws error 3930.
@@ERROR
Legacy: the previous statement's error number, reset by every statement. Pre-2005 code checks it after each statement — don't write new code this way.
sys.messages
Catalogue of error messages. sp_addmessage registers custom numbered messages RAISERROR can use.
Quick notes
  • Severity ≤ 10 (PRINT-like warnings) never enters CATCH; severity ≥ 20 kills the connection before CATCH can run.
  • ERROR_* functions only have values inside a CATCH block (or a proc it calls) — read them immediately.
  • THROW; (bare, in CATCH) preserves the original error. Raising a NEW error loses the original — log it first.
  • Always terminate the statement before THROW with a semicolon; the parser can otherwise swallow THROW as a name.
  • In CATCH, check @@TRANCOUNT / XACT_STATE() and roll back before doing anything that writes.
  • SET XACT_ABORT ON; at the top of every proc that opens a transaction — Thursday's and Sunday's code depends on it.

1. Life before TRY/CATCH: @@ERROR

legacy-error.sql
-- Legacy style you will still meet in old codebases: check after EVERY statement
UPDATE dbo.Employees SET Salary = Salary * 1.05 WHERE DepartmentId = 2;
IF @@ERROR <> 0
BEGIN
    PRINT 'Update failed';
    RETURN;
END
-- One statement later, @@ERROR has already been reset to 0 by the IF itself!

@@ERROR resets after every statement, so old procs are littered with IF @@ERROR <> 0 checks — easy to forget one. Since SQL Server 2005, TRY/CATCH replaces all of it.

2. TRY/CATCH basics

try-catch.sql
BEGIN TRY
    DECLARE @perHead DECIMAL(10,2) = 180000 / 0;   -- divide by zero: error 8134, severity 16
    PRINT 'never reached';
END TRY
BEGIN CATCH
    PRINT 'Caught: ' + ERROR_MESSAGE();
END CATCH;
-- Caught: Divide by zero error encountered.

What CATCH does not catch:

  • Severity ≤ 10: informational messages (e.g. RAISERROR(... , 10, 1)) sail straight past CATCH.
  • Severity ≥ 20: the connection is terminated; nothing in this session runs after it.
  • Compile/binding errors in the same scope — e.g. referencing a missing table in this batch. An outer caller's CATCH does see them, which is one more reason application-facing logic belongs in procs.
  • KILL / client timeouts (attention events): the batch just stops; CATCH never runs. This is why Sunday's proc also sets XACT_ABORT ON.

3. The ERROR_* functions and an error log

error-log.sql
CREATE TABLE dbo.ErrorLog (
    ErrorLogId   INT IDENTITY PRIMARY KEY,
    LoggedAt     DATETIME2(0)  NOT NULL DEFAULT SYSDATETIME(),

END TRY

    INSERT dbo.ErrorLog (ErrorNumber, Severity, State, ProcName, ErrorLine, Message)
    VALUES (ERROR_NUMBER(), ERROR_SEVERITY(), ERROR_STATE(),
            ERROR_PROCEDURE(), ERROR_LINE(), ERROR_MESSAGE());

Avoid. Logging the error and then swallowing it (-- THROW commented out) is how systems end up "succeeding" with half the data missing. Log and rethrow unless this layer can genuinely recover.

5. The rethrow pattern

rethrow-pattern.sql
CREATE OR ALTER PROCEDURE dbo.usp_GiveRaiseSafe
    @EmployeeId INT,
    @Percent    DECIMAL(5,2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    IF @Percent NOT BETWEEN 0 AND 50
        THROW 50002, N'@Percent must be between 0 and 50.', 1;

    BEGIN TRY
        BEGIN TRANSACTION;

        UPDATE dbo.Employees
        SET Salary = Salary * (1 + @Percent / 100.0)
        WHERE EmployeeId = @EmployeeId;

        IF @@ROWCOUNT = 0
            THROW 50003, N'Employee does not exist.', 1;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;   -- clean up OUR transaction...

        -- (optionally log to dbo.ErrorLog here)

        THROW;                                     -- ...then rethrow the ORIGINAL error
    END CATCH;
END

Why bare THROW;? The caller gets the original number, message and line — exactly like C#'s throw; vs throw ex; from Week 3. Raising a fresh error instead would be T-SQL's throw ex: context lost.

Gotcha. Write ROLLBACK TRANSACTION; with the semicolon. Without it, ROLLBACK TRANSACTION THROW parses THROW as a transaction name and your rethrow never happens — a famous, real-world bug.

6. XACT_ABORT and XACT_STATE

xact-state.sql
-- XACT_STATE() answers: "can I still commit?"
--   1  = open transaction, committable
--   0  = no transaction
--  -1  = open but DOOMED: only ROLLBACK is allowed
BEGIN CATCH
    IF XACT_STATE() = -1
        ROLLBACK TRANSACTION;          -- doomed: the only legal move
    ELSE IF XACT_STATE() = 1
        ROLLBACK TRANSACTION;          -- our policy: a caught error voids the whole unit
    THROW;
END CATCH;
  • SET XACT_ABORT ON turns most runtime errors into "doom the transaction and abort the batch". With it, a client timeout mid-transaction rolls back instead of leaving locks held by an open, orphaned transaction.
  • With XACT_ABORT ON inside TRY, control still reaches CATCH — but the transaction is usually doomed (XACT_STATE() = -1), so roll back before any further writes.
  • Microsoft's own guidance for procs that modify data: SET NOCOUNT ON; SET XACT_ABORT ON; as the opening lines. That's the house style for the rest of this course.

Common mistakes

  • Relying on @@ERROR two statements after the failure (it's already reset).
  • Expecting CATCH to see severity-10 RAISERROR messages or severity-20+ fatal errors.
  • Raising a brand-new generic error in CATCH instead of logging and rethrowing with THROW;.
  • Missing semicolon before THROW (especially after ROLLBACK TRANSACTION).
  • COMMITting in CATCH when XACT_STATE() is -1 — error 3930, the transaction was doomed.

Self-check questions

What three values can XACT_STATE() return and what do they mean?1: an open transaction that can still commit. 0: no open transaction. -1: an open but doomed transaction — you can only roll it back; COMMIT throws error 3930.
Why is bare THROW; in CATCH better than raising a new error?It rethrows the original error with its number, severity, state, message and line, so the caller (and your logs) see where it really happened — the T-SQL equivalent of C#'s throw; preserving the stack trace.

BasicHow does TRY/CATCH work in T-SQL and what can't it catch?
Errors with severity 11–19 inside TRY transfer control to CATCH. It cannot catch: severity ≤ 10 messages, severity ≥ 20 errors that kill the connection, compile/name-resolution errors raised in the same scope (an outer scope's CATCH can see those), or attention events like KILL and client timeouts.
BasicWhich functions give you error details in a CATCH block?
ERROR_NUMBER, ERROR_MESSAGE, ERROR_SEVERITY, ERROR_STATE, ERROR_LINE and ERROR_PROCEDURE. They keep their values anywhere inside the CATCH block (including procs called from it), unlike @@ERROR which resets after every statement.
BasicTHROW vs RAISERROR — key differences?
THROW (2012+) is the modern choice: always severity 16, always terminates the batch, honours XACT_ABORT, and bare THROW rethrows the original error. RAISERROR offers printf formatting, selectable severity, sys.messages integration and WITH NOWAIT, but can't rethrow and doesn't trigger XACT_ABORT behaviour.
IntermediateDescribe a robust CATCH block for a proc that writes data.
Check @@TRANCOUNT/XACT_STATE and roll back if a transaction is open (mandatory when XACT_STATE() = -1), optionally write a log record after the rollback, then rethrow with bare THROW so callers aren't fooled into thinking the operation succeeded.
IntermediateWhat is a doomed transaction and how do you end up with one?
A transaction in XACT_STATE() = -1: still open (holding locks) but unable to commit. You typically get one when an error occurs with SET XACT_ABORT ON, or certain severe errors inside TRY. Any work attempted before ROLLBACK fails with error 3930.
IntermediateWhy do teams set XACT_ABORT ON even though TRY/CATCH exists?
TRY/CATCH never runs for attention events — a client timeout mid-transaction leaves the transaction open and its locks held, blocking everyone. XACT_ABORT ON rolls back automatically in exactly those cases, so the two mechanisms cover each other.

Transactions, @@TRANCOUNT, savepoints and isolation levels

GoalGroup statements into all-or-nothing transactions, understand why "nested transactions" are a myth, and reason about the five isolation levels through the three classic anomalies.

Key definitions

Transaction
A unit of work that either fully commits or fully rolls back — never half-applies.
ACID
Atomicity (all or nothing), Consistency (constraints hold before and after), Isolation (concurrent transactions don't trample each other), Durability (committed = survives a crash, via the write-ahead log).
Autocommit
SQL Server's default: every single statement is its own transaction. An UPDATE hitting 10,000 rows is still atomic on its own.
Explicit transaction
BEGIN TRANSACTION … COMMIT / ROLLBACK: you decide the unit of work.
@@TRANCOUNT
Current transaction nesting depth. BEGIN TRAN adds 1; COMMIT subtracts 1 (only the last one really commits); ROLLBACK zeroes it.
Nested transactions
A myth: inner BEGIN TRAN/COMMIT pairs only move the counter. There is exactly one real transaction — the outermost.
Savepoint
SAVE TRANSACTION name: a marker you can roll back to without abandoning the whole transaction.
Isolation level
How much a transaction is protected from others' concurrent changes; a trade between correctness and concurrency.
Dirty read
Reading data another transaction has modified but not yet committed — it may be rolled back and have "never happened".
Non-repeatable read
Reading the same row twice in one transaction and getting different values, because someone committed an update in between.
Phantom read
Re-running the same range query and seeing new rows, because someone committed an insert matching your WHERE clause.
READ COMMITTED
The default: no dirty reads; readers take shared locks briefly (or read versions under RCSI).
SNAPSHOT isolation
Transaction sees a consistent version of the data as of its start, via row versions in tempdb; writers don't block readers. Update conflicts raise error 3960.
RCSI
READ_COMMITTED_SNAPSHOT: READ COMMITTED semantics, but each statement reads the latest committed version instead of waiting on locks. Default on Azure SQL Database.
Version store
The area in tempdb that keeps old row versions for SNAPSHOT/RCSI readers.
Quick notes
  • Autocommit already makes each statement atomic; explicit transactions are for multi-statement invariants (debit + credit, order + lines + stock).
  • COMMIT when @@TRANCOUNT > 1 commits nothing — it just decrements the counter. Only the outermost COMMIT writes.
  • ROLLBACK anywhere rolls back everything and sets @@TRANCOUNT to 0 — exiting a proc with a different @@TRANCOUNT than it entered with raises error 266.
  • Never wait for user/application input while a transaction is open: you're holding locks.
  • Anomaly ladder: READ UNCOMMITTED allows dirty + non-repeatable + phantom; READ COMMITTED blocks dirty; REPEATABLE READ also blocks non-repeatable; SERIALIZABLE blocks all three.
  • SNAPSHOT/RCSI take a different route: versions instead of reader locks — readers never block writers and vice versa.

1. BEGIN / COMMIT / ROLLBACK and ACID

A bonus payout must update the salary and write the ledger row. One without the other is corruption:

bonus-transaction.sql

2. @@TRANCOUNT and the nested-transaction myth

trancount.sql
SELECT @@TRANCOUNT AS tc;      -- 0
BEGIN TRANSACTION;
SELECT @@TRANCOUNT AS tc;      -- 1
    BEGIN TRANSACTION;         -- "nested"... but no new transaction starts
    SELECT @@TRANCOUNT AS tc;  -- 2
    COMMIT;                    -- commits NOTHING — just decrements the counter
    SELECT @@TRANCOUNT AS tc;  -- 1
ROLLBACK;                      -- rolls back EVERYTHING since the first BEGIN TRAN
SELECT @@TRANCOUNT AS tc;      -- 0

There is only ever one real transaction. Inner COMMITs are bookkeeping; any ROLLBACK (at any depth) undoes the lot. This bites when a proc that opens its own transaction is called from inside a caller's transaction:

proc-in-transaction.sql
-- A proc that works standalone AND inside a caller's transaction
CREATE OR ALTER PROCEDURE dbo.usp_PayBonus
    @EmployeeId INT, @Amount DECIMAL(10,2)
AS
BEGIN
    SET NOCOUNT ON; SET XACT_ABORT ON;
    DECLARE @startedHere BIT = 0;

    BEGIN TRY
        IF @@TRANCOUNT = 0
        BEGIN
            BEGIN TRANSACTION;          -- only open one if nobody did yet
            SET @startedHere = 1;
        END

        UPDATE dbo.Employees SET Salary = Salary + @Amount WHERE EmployeeId = @EmployeeId;
        IF @@ROWCOUNT = 0 THROW 50010, N'Employee does not exist.', 1;
        INSERT dbo.BonusLedger (EmployeeId, Amount) VALUES (@EmployeeId, @Amount);

        IF @startedHere = 1 COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @startedHere = 1 AND @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;      -- if the caller owns the transaction, the caller decides to roll back
    END CATCH;
END
Rule. A proc must leave @@TRANCOUNT exactly as it found it, or SQL Server raises error 266 ("Transaction count after EXECUTE indicates a mismatching number of BEGIN and COMMIT statements"). The @startedHere pattern above guarantees that.

3. Savepoints

savepoint.sql
BEGIN TRANSACTION;

INSERT dbo.BonusLedger (EmployeeId, Amount) VALUES (2, 1000);   -- must succeed

SAVE TRANSACTION OptionalPart;                                   -- marker

BEGIN TRY
    INSERT dbo.BonusLedger (EmployeeId, Amount) VALUES (4, 500); -- nice-to-have
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION OptionalPart;   -- undo ONLY the optional part
END CATCH;                                -- @@TRANCOUNT is still 1 here

COMMIT TRANSACTION;                       -- the first insert (and the second, if it worked) commit

ROLLBACK TRANSACTION savepoint_name does not decrement @@TRANCOUNT — the transaction stays open. Savepoints are rare in practice (usually you want all-or-nothing), but they shine for "mandatory core + optional extras" units.

Locking, blocking, deadlocks — and triggers

GoalSee which locks SQL Server takes and how to find who's blocking whom; understand, provoke and retry deadlocks; and write set-based triggers while knowing why business logic rarely belongs in them.

Key definitions

Lock
An in-memory marker that gives a session rights over a resource (row, page, table) and makes others wait for incompatible access.
Shared lock (S)
Taken to read. Compatible with other S locks; blocks X.
Exclusive lock (X)
Taken to modify. Compatible with nothing — one writer at a time per resource.
Update lock (U)
"Intending to write": taken while locating rows to update. Compatible with S, not with other U — which prevents a classic deadlock between two updaters.
Intent lock (IS/IX)
Placed on the page and table to advertise row-level locks below, so a table-level request can be checked without scanning every row lock.
Granularity
The size of the locked resource: KEY (row in an index), RID (heap row), PAGE, HOBT/TABLE. Finer = more concurrency, more overhead.
Lock escalation
When one statement holds ~5,000 locks on an object, SQL Server trades them for a single table lock — cheaper, but suddenly everyone waits.
Blocking
Normal lock waiting: session B needs a lock session A holds. Resolves itself when A commits — unless A is idle holding a transaction open.
Deadlock
A cycle: A holds what B wants and B holds what A wants. Nobody can ever proceed, so SQL Server kills one.
Deadlock victim
The transaction SQL Server chooses to kill (usually the cheapest to roll back) — it gets error 1205 and should be retried.
Deadlock graph
An XML/visual report of the cycle: which sessions, which resources, which statements. Captured automatically by the system_health session.
Trigger
T-SQL attached to a table that runs automatically on INSERT/UPDATE/DELETE — AFTER (post-check) or INSTEAD OF (replaces the action).
inserted / deleted
Virtual tables inside a trigger: the new row versions and the old ones. An UPDATE populates both.
UPDATE(col)
Trigger function: true when the column appeared in the SET/insert list (even if set to the same value).
sp_whoisactive
A free, widely used community proc (Adam Machanic) that shows running sessions, blockers and wait info far more readably than sp_who2.
Quick notes
  • Readers block writers and writers block readers (under plain READ COMMITTED) — but readers never block readers.
  • Blocking is normal and brief; a problem only when transactions are long or idle-but-open. Deadlocks are always a bug-shaped smell.
  • SQL Server detects deadlocks in seconds, kills the cheapest victim with error 1205 — the fix is to retry, and to stop the cycle forming.
  • Cycle prevention rule #1: every transaction touches shared tables in the same order.
  • Triggers fire once per statement, not per row — always join inserted/deleted as sets.
  • Keep triggers for auditing and denormalised bookkeeping; put business rules in procs/services where they're visible and testable.

3. Deadlocks: making one on purpose

deadlock-demo.sql
-- Session A                                 | -- Session B
BEGIN TRANSACTION;                           | BEGIN TRANSACTION;
UPDATE dbo.Employees                         | UPDATE dbo.Departments
SET Salary += 1 WHERE EmployeeId = 2;        | SET Name = Name WHERE DepartmentId = 2;
                                             |
-- step 3: now wants Departments...          | -- step 4: now wants Employees...

4. Preventing and surviving deadlocks

  • Order resources consistently. If every transaction updates Employees before Departments, the A-waits-B-waits-A cycle cannot form. Agree an order (e.g. parent then child, or alphabetical) and enforce it in code review.
  • Keep transactions short. Do reads, calculations and validations first; open the transaction for the writes only.
  • Index your WHERE clauses and foreign keys. A missing index turns a 1-row update into a scan that locks everything it touches.
  • Take the strongest lock first. Sunday's stock check reads with UPDLOCK precisely so check-then-update can't deadlock with a twin.
  • Retry the victim. Error 1205 is transient by design; 2–3 retries with a tiny delay absorb almost all of them.
retry-skeleton.sql
-- Retry skeleton (Sunday's project ships a full version)
DECLARE @attempts INT = 0;
retry:
BEGIN TRY
    SET @attempts += 1;
    EXEC dbo.usp_PayBonus @EmployeeId = 2, @Amount = 500;
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() = 1205 AND @attempts < 3
    BEGIN
        WAITFOR DELAY '00:00:00.200';   -- small backoff
        GOTO retry;
    END;
    THROW;
END CATCH;

Pull deadlock graphs from system_health to see the exact statements and resources in the cycle. Typical fixes: make all code paths touch tables in the same order, shorten transactions (writes last), add missing indexes so updates don't scan, consider RCSI to take readers out of the picture, and add 1205 retry logic as a safety net.
IntermediateAFTER vs INSTEAD OF triggers?
AFTER runs post-statement (per statement, with constraints already checked) — right for auditing and bookkeeping. INSTEAD OF replaces the triggering action entirely — the base operation only happens if the trigger performs it; used for soft deletes and making multi-table views updatable. Only one INSTEAD OF trigger per action per table.
IntermediateWhy do most teams keep business logic out of triggers?
Triggers are invisible at the call site, hard to unit test, fire per statement (inviting multi-row bugs), add cost to every write, can cascade into other triggers, and their ordering is only partly controllable. Auditing and sync duties stay; decisions and workflows move to procedures or services where they're explicit.
DAY 5 · FRI

Table-valued parameters, temp tables vs table variables, SELECT INTO

GoalPass whole tables into procedures with TVPs (from T-SQL and from C#), choose correctly between #temp tables and @table variables, and use SELECT INTO for quick materialisation.

Key definitions

Table-valued parameter (TVP)
A procedure parameter whose type is a user-defined table type — the clean way to pass many rows in one call.
Table type
CREATE TYPE x AS TABLE (…): a saved table definition (columns, PK, CHECK) that TVPs and variables can use.
READONLY
Mandatory keyword on TVP parameters: the proc may read and join the TVP but never modify it.
Temp table (#t)
A real table created in tempdb, visible to the creating session (and procs it calls), dropped when the session/scope ends.
Global temp table (##t)
Visible to all sessions; dropped when the creator disconnects and no one else is using it. Rare; mostly for debugging.
Table variable (@t)
A variable holding rows, also stored in tempdb, scoped to the batch/proc. Not affected by ROLLBACK.
tempdb
The shared scratch database where temp tables, table variables, version stores and spills live. One per instance — a common bottleneck.
Statistics
Histograms about column values the optimiser uses to estimate row counts. Temp tables have them; table variables don't.
Recompile
Re-optimisation of a statement. Temp-table changes can trigger recompiles (cost, but fresher plans); table variables avoid them (stale guesses instead).
Deferred compilation
SQL Server 2019+: statements referencing table variables compile when first executed, using the variable's actual row count instead of a guess of 1.
SELECT INTO
Creates a brand-new table from a query's shape and rows in one statement: SELECT … INTO #t FROM ….
SqlDbType.Structured
The ADO.NET parameter type for TVPs — pass a DataTable (or DbDataReader / IEnumerable of SqlDataRecord) and name the server-side table type.
STRING_SPLIT
2016+ function turning 'a,b,c' into rows; 2022 adds an ordinal column. The budget alternative when a TVP is overkill.
Quick notes
  • One proc call with a 500-row TVP beats 500 single-row calls — fewer round trips, one transaction, one plan.
  • A table type can't be ALTERed while anything references it: create TypeName_v2, migrate procs, drop the old one. Design types small and stable.
  • TVP parameters are READONLY — to modify the data, copy it into a temp table first.
  • #temp tables: statistics, indexes, parallel plans, rolled back with transactions. @table variables: no stats, survive ROLLBACK, fewer recompiles.
  • Default: temp table when rows are many or the query is complex; table variable for a handful of rows or when ROLLBACK-survival is the point (e.g. error logging).
  • SELECT INTO copies column names/types (and IDENTITY) but no constraints, defaults or indexes.

1. The problem: passing a list to SQL

csv-hack.sql
-- The old hacks, before TVPs:
-- 1) CSV string + STRING_SPLIT (2016+). Works, but everything is a string:

FROM dbo.Employees e

-- 2) One call per id from the app: N round trips, N plans, no shared transaction.
-- 3) Dynamic SQL: 'WHERE EmployeeId IN (' + @csv + ')' -- injection + plan-cache pollution.

All three lose typing, performance or safety. A TVP keeps all three: the client sends rows, typed, in one go.

4. Temp tables (#t) vs table variables (@t)

temp-vs-var.sql
-- Both live in tempdb; behaviour differs where it matters:
CREATE TABLE #Big (Id INT PRIMARY KEY, Amount DECIMAL(10,2));
DECLARE @Small TABLE (Id INT PRIMARY KEY, Amount DECIMAL(10,2));

BEGIN TRANSACTION;

Common mistakes

  • Trying to UPDATE a TVP parameter inside the proc (it's READONLY — copy to a temp table if you must).
  • Using a table variable for 100k rows and getting a 1-row-estimate plan (pre-2019 especially).
  • Expecting @table variable contents to disappear on ROLLBACK (they survive).
  • ALTERing a table type — impossible; plan versioned types instead.
  • Rebuilding the same #temp table shape in ten procs instead of one shared definition (or a TVP type).

Self-check questions

Why must a TVP parameter be READONLY?SQL Server requires it: TVPs are passed by reference to row data the engine doesn't copy per call, so modification isn't supported. The proc can read and join the TVP; to change the data it must copy rows into a temp table or table variable.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is a table-valued parameter and why use one?
A proc parameter typed by a user-defined table type, letting a caller send many typed rows in a single call — one round trip, one transaction, one plan — instead of CSV strings, XML or N separate calls. It must be declared READONLY.
BasicHow do you pass a TVP from .NET?
Create a parameter with SqlDbType.Structured, set TypeName to the server-side table type (e.g. dbo.IntList), and set Value to a DataTable, DbDataReader or IEnumerable<SqlDataRecord> whose columns match the type's definition, then execute the command as a stored procedure.
BasicWhen would you pick a table variable over a temp table?
For small row counts where plan quality can't suffer much, inside functions (temp tables aren't allowed there), and when you need data to survive a ROLLBACK — e.g. capturing diagnostics before rolling back. Otherwise temp tables are the safer default for big or complex intermediates.
IntermediateWhy can table variables produce terrible query plans?
They have no statistics; before SQL Server 2019 the optimiser assumed 1 row regardless of contents, choosing nested-loop plans that explode on 100k rows. 2019's deferred compilation uses the actual row count at first execution, but there are still no histograms, so value-distribution estimates stay crude.
IntermediateA proc builds a huge intermediate result used by three later queries. Temp table or CTE, and why?
A temp table: it materialises once, gets statistics (and optionally an index), and the three queries reuse it. A CTE is just inline query text — each reference re-expands and may re-execute the work. Materialise when reused or when stats will change join choices; stay inline for single-use.
IntermediateHow do TVPs interact with statistics and plans?
Like table variables, TVPs carry no statistics — the optimiser uses a fixed low estimate for them. For typical small TVPs that's fine; for large ones, copy the TVP into a #temp table inside the proc (gaining stats and indexes) before heavy joins, or accept OPTION (RECOMPILE) on the affected statement.

Step 3 — usp_MonthlySalesSummary (OUTPUT totals)

03_report_procs.sql — part 1
CREATE OR ALTER PROCEDURE Sales.usp_MonthlySalesSummary
    @Year         INT,
    @Month        INT,
    @OrderCount   INT           OUTPUT,
    @TotalRevenue DECIMAL(12,2) OUTPUT
AS
BEGIN
    SET NOCOUNT ON;

    IF @Month NOT BETWEEN 1 AND 12
        THROW 50001, N'@Month must be between 1 and 12.', 1;
    IF @Year NOT BETWEEN 2000 AND 2100
        THROW 50002, N'@Year must be between 2000 and 2100.', 1;

    DECLARE @From DATE = DATEFROMPARTS(@Year, @Month, 1);
    DECLARE @To   DATE = DATEADD(MONTH, 1, @From);    -- half-open range [From, To)

    SELECT @OrderCount   = COUNT(DISTINCT o.OrderId),
           @TotalRevenue = COALESCE(SUM(ol.LineTotal), 0)
    FROM Sales.Orders o
    JOIN Sales.OrderLines ol ON ol.OrderId = o.OrderId
    WHERE o.OrderDate >= @From AND o.OrderDate < @To
      AND o.Status <> N'Cancelled';

    -- Breakdown result set: who bought how much this month
    SELECT c.Name AS Customer,
           COUNT(DISTINCT o.OrderId) AS Orders,
           SUM(ol.LineTotal)         AS Revenue
    FROM Sales.Orders o
    JOIN Sales.Customers  c  ON c.CustomerId = o.CustomerId
    JOIN Sales.OrderLines ol ON ol.OrderId   = o.OrderId
    WHERE o.OrderDate >= @From AND o.OrderDate < @To
      AND o.Status <> N'Cancelled'
    GROUP BY c.Name
    ORDER BY Revenue DESC;
END
Tip. The half-open range >= first-of-month AND < first-of-next-month works for DATE, DATETIME2 and any precision — no BETWEEN edge cases at 23:59:59.997.

Step 4 — usp_TopCustomers (pagination)

CREATE OR ALTER PROCEDURE Sales.usp_TopCustomers
    @PageNumber INT = 1,
    @PageSize   INT = 3
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageNumber < 1               THROW 50003, N'@PageNumber must be >= 1.', 1;
    IF @PageSize NOT BETWEEN 1 AND 100 THROW 50004, N'@PageSize must be 1-100.', 1;

    SELECT c.CustomerId, c.Name, c.City,
           COUNT(DISTINCT o.OrderId) AS Orders,
           SUM(ol.LineTotal)         AS TotalSpend,
           COUNT(*) OVER ()          AS TotalCustomers   -- same on every row: rank size
    FROM Sales.Customers c
    JOIN Sales.Orders o      ON o.CustomerId = c.CustomerId AND o.Status <> N'Cancelled'
    JOIN Sales.OrderLines ol ON ol.OrderId   = o.OrderId
    GROUP BY c.CustomerId, c.Name, c.City
    ORDER BY TotalSpend DESC, c.CustomerId          -- deterministic tiebreak!
    OFFSET (@PageNumber - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
Note. Pagination without a deterministic ORDER BY (unique tiebreak column) can show the same customer on two pages or skip one. And OFFSET still reads all skipped rows — fine here, a real cost at page 10,000 (keyset paging fixes that; Week 14).

BasicWhy copy UnitPrice into OrderLines instead of joining to Products for totals?
Catalogue prices change; invoices must not. Copying the price at sale time makes each order line a historical fact — reports and totals stay stable, and the CHECK/computed LineTotal is self-contained. Joining to Products would silently rewrite old revenue whenever a price is updated.
BasicHow does a .NET caller read usp_CustomerStatement's three result sets?
ExecuteReader returns the first set; reader.NextResult() advances to the next, in the exact order the proc SELECTed them. Dapper's QueryMultiple wraps the same mechanism. Result-set order and shape are part of the proc's contract — changing them breaks callers.
IntermediateWhen totals are needed by the app, OUTPUT parameters or another result set?
OUTPUT parameters are cheapest for a few scalars and read naturally in ADO.NET after the reader closes. A result set is better when the "totals" are really rows (per-group totals) or when the client API makes extra result sets easier than parameter plumbing. Avoid returning the same numbers both ways — one source of truth.
IntermediateWhat are the pitfalls of OFFSET/FETCH pagination?
It requires a deterministic ORDER BY (add a unique tiebreak) or pages can overlap/skip; the engine still reads and discards all skipped rows, so deep pages get slower linearly; and concurrent inserts shift rows between pages. Keyset (seek-based) pagination — WHERE (SpendRank, Id) > last-seen — fixes the depth cost for infinite-scroll patterns.

usp_PlaceOrder: an all-or-nothing order pipeline

GoalFinish the project: a transactional order-placing procedure fed by a TVP — stock validation, atomic insert + decrement, XACT_ABORT + TRY/CATCH, a deadlock-retry wrapper, and tests that prove failures change nothing. Budget: about 4 hours.

Key definitions

All-or-nothing
The order header, its lines and the stock decrements commit together or not at all — the week's transaction skills, applied.
UPDLOCK hint
Read rows taking update locks instead of shared ones: "I will write these rows" — two sessions can't both pass the stock check.
HOLDLOCK hint
Hold the locks to end of transaction (serializable semantics for those rows) — the gap between check and update stays protected.
Oversell
Selling more stock than exists — exactly what the check-then-act race produces without proper locking.
Retry policy
Re-running a transaction that failed transiently (deadlock 1205, snapshot conflict 3960) a bounded number of times with a delay.
Quick notes
  • SET XACT_ABORT ON + TRY/CATCH + bare THROW; — Tuesday's template, now in production shape.
  • The TVP's PRIMARY KEY on ProductId means duplicate lines are rejected before the proc even runs.
  • Stock is checked with UPDLOCK inside the transaction — checking before the transaction would be a race.
  • Every failure path must leave zero traces: no order row, no lines, unchanged stock. The tests prove it.
  • Deadlock retries wrap the whole transaction, never a statement inside it.

Step 1 — Table type and the procedure

05_place_order.sql
USE HR;
GO
CREATE TYPE Sales.OrderLineInput AS TABLE
(
    ProductId INT NOT NULL PRIMARY KEY,    -- PK: no duplicate products per order
    Qty       INT NOT NULL CHECK (Qty > 0)
);
GO
CREATE OR ALTER PROCEDURE Sales.usp_PlaceOrder
    @CustomerId INT,
    @Lines      Sales.OrderLineInput READONLY,
    @OrderId    INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;      -- timeouts/severe errors roll back instead of leaking locks

    -- Cheap validations first, outside the transaction
    IF NOT EXISTS (SELECT 1 FROM Sales.Customers WHERE CustomerId = @CustomerId)
        THROW 50020, N'Customer does not exist.', 1;

    IF NOT EXISTS (SELECT 1 FROM @Lines)
        THROW 50021, N'An order needs at least one line.', 1;

    IF EXISTS (SELECT 1 FROM @Lines l
               WHERE NOT EXISTS (SELECT 1 FROM Sales.Products p
                                 WHERE p.ProductId = l.ProductId))
        THROW 50022, N'One or more product ids do not exist.', 1;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- Stock check WITH LOCKS: UPDLOCK reserves the rows we'll update,
        -- HOLDLOCK keeps that reservation until COMMIT. Without these, two
        -- concurrent orders could both pass the check and oversell.
        IF EXISTS (SELECT 1
                   FROM Sales.Products p WITH (UPDLOCK, HOLDLOCK)
                   JOIN @Lines l ON l.ProductId = p.ProductId
                   WHERE p.StockQty < l.Qty)
            THROW 50023, N'Insufficient stock for one or more products.', 1;

        INSERT Sales.Orders (CustomerId) VALUES (@CustomerId);
        SET @OrderId = SCOPE_IDENTITY();

        INSERT Sales.OrderLines (OrderId, ProductId, Qty, UnitPrice)
        SELECT @OrderId, l.ProductId, l.Qty, p.UnitPrice     -- price at sale time
        FROM @Lines l
        JOIN Sales.Products p ON p.ProductId = l.ProductId;

        UPDATE p
        SET p.StockQty = p.StockQty - l.Qty
        FROM Sales.Products p
        JOIN @Lines l ON l.ProductId = p.ProductId;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        SET @OrderId = NULL;     -- never hand back an id that was rolled back
        THROW;
    END CATCH;
END

Note the order inside the transaction: lock + check, then header, then lines, then stock. Every caller that touches Products and Orders in this same sequence can block briefly but never deadlock with a twin of itself — Thursday's resource-ordering rule.

Step 4 — Deadlock-retry wrapper

07_place_order_retry.sql
-- How the application (or a job) should call usp_PlaceOrder:
DECLARE @lines Sales.OrderLineInput;
INSERT @lines (ProductId, Qty) VALUES (6, 1);

DECLARE @orderId  INT,
        @attempt  INT = 1,
        @maxTries INT = 3;

WHILE @attempt <= @maxTries
BEGIN
    BEGIN TRY
        EXEC Sales.usp_PlaceOrder @CustomerId = 6, @Lines = @lines, @OrderId = @orderId OUTPUT;
        PRINT CONCAT('Order ', @orderId, ' placed on attempt ', @attempt);
        BREAK;                                   -- success: leave the loop
    END TRY
    BEGIN CATCH
        IF ERROR_NUMBER() IN (1205, 3960)        -- deadlock victim / snapshot conflict
           AND @attempt < @maxTries
        BEGIN
            PRINT CONCAT('Transient error ', ERROR_NUMBER(), ' — retrying...');
            WAITFOR DELAY '00:00:00.200';        -- small backoff before retry
            SET @attempt += 1;
        END
        ELSE
            THROW;    -- business errors (50020-50023) or retries exhausted: fail loudly
    END CATCH;
END

Only transient errors are retried; business errors like insufficient stock would fail identically every time. In the .NET weeks this same policy moves into C# (Polly) — the shape stays: bounded attempts, backoff, retry the whole unit of work.

    THROW
END CATCH;
No rethrow — it parses as ROLLBACK TRANSACTION THROW. THROW isn't a reserved keyword, so it's taken as a transaction/savepoint name; you get "Cannot roll back THROW…" (and the original error is masked). Terminate the statement: ROLLBACK TRANSACTION; THROW;

BasicWalk through how usp_PlaceOrder guarantees all-or-nothing.
Validations THROW before any write. The writes run inside one explicit transaction under SET XACT_ABORT ON; any error enters CATCH, which rolls back and rethrows — so header, lines and stock decrements exist together or not at all. XACT_ABORT also covers client timeouts that TRY/CATCH never sees.
IntermediateWhy does the stock check read with UPDLOCK and HOLDLOCK?
Plain shared locks would let two sessions both pass the check for the last unit, then both decrement — overselling. UPDLOCK makes the check take update locks (mutually exclusive between checkers), and HOLDLOCK keeps them until COMMIT, closing the gap between check and update. The second session waits, re-reads the decremented stock, and correctly fails.
IntermediateWhere should deadlock retry logic live, and what must it never do?
Around the whole transaction — in the calling layer (T-SQL wrapper or application code), because error 1205 rolls back the entire transaction, so retrying a single statement is meaningless. It must never retry non-transient business errors, never retry unboundedly, and should back off briefly between attempts.
IntermediateWhy a TVP for the order lines rather than JSON or repeated calls?
A TVP arrives typed and set-oriented: the proc joins it like a table, the type's PK/CHECK reject bad shapes before execution, and the whole basket travels in one call inside one transaction. JSON needs parsing and validation in the proc; N calls per line lose atomicity unless the app manages the transaction, plus N round trips.
