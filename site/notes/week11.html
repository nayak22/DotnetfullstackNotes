DAY 1 · MON

SQL Server 2022 setup, databases, schemas and data types

GoalGet SQL Server 2022 Developer running in Docker, connect to it, create your first database and table, and choose the right data type for every column.

Key definitions

RDBMS
Relational Database Management System: stores data in tables (rows and columns) related by keys, and enforces rules about that data.
SQL Server
Microsoft's RDBMS. The free Developer edition has every feature of Enterprise but is licensed for non-production use only.
T-SQL
Transact-SQL: Microsoft's dialect of SQL. Standard SQL plus extensions like TOP, IDENTITY, variables and procedures.
Instance
One running SQL Server service. It listens on a port (default 1433) and hosts many databases.
Database
A named container of schemas, tables, views and procedures with its own files. You'll have one per application.
System databases
master (instance config), model (template for new DBs), msdb (jobs/history), tempdb (scratch space, rebuilt on every restart).
Data file / log file
Each database has at least one .mdf data file (the tables) and one .ldf transaction log file (every change, for recovery).
Filegroup
A named group of data files. Tables are created on a filegroup (default PRIMARY); big systems use extra filegroups to spread I/O. Awareness is enough for now.
Schema
A namespace inside a database that groups objects: hr.employees, sales.orders. The default schema is dbo.
Table
A set of rows sharing the same typed columns. Rows have no inherent order.
Data type
The kind of value a column stores — INT, DECIMAL(18,2), NVARCHAR(100), DATE… It controls storage, validation and comparison.
NULL
The absence of a value — not zero, not an empty string. A column declared NOT NULL rejects it.
IDENTITY
A column property that auto-generates sequential numbers per table: IDENTITY(100,1) starts at 100, steps by 1.
Sequence
A standalone number generator (CREATE SEQUENCE) usable across tables, with control over cache, cycle and restart.
Collation
The rules for sorting and comparing text. SQL Server's defaults are usually case-insensitive (_CI_), so 'ASHA' = 'asha' is true.
Quick notes
  • Developer edition is free and full-featured — perfect for this whole phase. Never use it in production.
  • The SA password must be 8+ characters with three of: uppercase, lowercase, digits, symbols — or the container silently dies.
  • Use NVARCHAR for anything a human types (names in any script); VARCHAR is fine for codes, emails, GSTINs.
  • Money is always DECIMAL(18,2) (or similar precision) — never FLOAT/REAL, which are approximate.
  • Prefer DATE and DATETIME2 over the legacy DATETIME (3.33 ms rounding, min year 1753).
  • Always write two-part names: hr.employees, not employees.

4. Schemas: dbo and your own

Schemas group related tables and let you secure them as a unit. If you don't specify one, you get dbo (“database owner”).

02_schemas.sql
CREATE SCHEMA hr AUTHORIZATION dbo;      -- must be the only statement in its batch
GO
CREATE SCHEMA sales AUTHORIZATION dbo;
GO
-- Same table name can exist in two schemas without clashing:
-- hr.contacts (employees' emergency contacts) vs sales.contacts (leads)
  • hr.employees reads as “the employees table in the hr schema” — schema first, then object.
  • Group by business area (hr, sales, billing), not by type (“tables”, “views”).
  • Permissions can be granted per schema: give the reporting team SELECT on sales only.
  • Always schema-qualify in code. Unqualified names make SQL Server check your default schema first — slower plan reuse and ambiguous code.

GO
SELECT NEXT VALUE FOR hr.badge_seq;      -- 5000
SELECT NEXT VALUE FOR hr.badge_seq;      -- 5001 (each call consumes a number)

CREATE TABLE hr.badges
(

Self-check questions

What's the difference between an instance and a database?An instance is the running SQL Server service (one port, one set of logins, one tempdb). It hosts many databases, each a self-contained set of schemas, tables and files.
Why NVARCHAR for names but VARCHAR for emails?Names can contain any script, so they need Unicode (2 bytes/char). Email addresses are ASCII by common convention, so VARCHAR halves the storage. (A UTF-8 collation can blur this line, but the NVARCHAR habit is the safe default.)
What does IDENTITY(100,5) do?Auto-generates values for that column starting at 100, stepping by 5: 100, 105, 110… The values are per-table and assigned at insert time.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is the difference between SQL and T-SQL?
SQL is the standard query language (SELECT, INSERT, UPDATE, DELETE, DDL). T-SQL is Microsoft's implementation plus extensions: variables, control flow, TRY/CATCH, TOP, OUTPUT, IDENTITY, stored procedures. Core queries are portable; the extensions are not.
BasicName the system databases and their roles.
master holds instance-level configuration, logins and the locations of other databases; model is the template every new database is copied from; msdb backs SQL Agent jobs, alerts and backup history; tempdb is shared scratch space for sorts, temp tables and versioning, rebuilt at every restart.
BasicNULL vs an empty string vs zero?
NULL means 'no value / unknown' and is a state, not a value: it fails every = comparison and needs IS NULL. An empty string is a real VARCHAR value of length 0; zero is a real number. A phone column that's NULL means 'we don't have it'; '' would mean 'we have it and it's empty', which is usually nonsense — so model missing data as NULL.
IntermediateWhy is DECIMAL preferred over FLOAT and MONEY for currency?
FLOAT is binary floating point: 0.1 has no exact representation, so totals drift — unacceptable for accounts. MONEY is exact but fixed at 4 decimal places and loses precision in intermediate multiplication/division. DECIMAL(p,s) is exact, with precision you choose, and behaves predictably in arithmetic.
IntermediateDATETIME vs DATETIME2 — why does the new type exist?
DATETIME stores to 1/300th of a second (values round to .000/.003/.007), starts at year 1753, and takes 8 bytes. DATETIME2 has up to 100 ns precision, dates from year 1, configurable precision and takes 6–8 bytes. Microsoft recommends DATETIME2 for all new work; DATETIME survives for compatibility.
IntermediateWhen would you use a SEQUENCE instead of IDENTITY?
When several tables must share one number series, when you need the value before inserting (to use in related rows or return to the caller), when you need to restart or re-step the series, or when inserts come from code that wants to pre-allocate ranges. For a plain surrogate key, IDENTITY is simpler. Both can leave gaps.
DAY 2 · TUE

Keys, constraints, ER diagrams and normalization

GoalMake the database enforce your business rules with keys and constraints, read ER diagrams, and normalize a messy orders table to 3NF — then know when to stop.

Key definitions

Primary key (PK)
The column(s) that uniquely identify each row. One per table; implies NOT NULL and unique; gets the clustered index by default.
Candidate key
Any column set that could serve as the PK (e.g. employee email AND employee id). The ones not chosen can become UNIQUE constraints.
Surrogate key
An artificial identifier with no business meaning, usually INT IDENTITY. The common choice for PKs.
Natural key
A real-world identifier (PAN, email, ISBN). Risky as a PK: they change, have exceptions, and are wide.
Composite key
A key of more than one column, e.g. (order_id, product_id) in an order-items table.
Foreign key (FK)
Column(s) in one table that must match a PK/UNIQUE value in another (or be NULL). Creates the relationship.
Referential integrity
The guarantee that FKs always point at existing rows — no orphan order for a deleted customer.
Referential action
What happens to child rows when the parent is deleted/updated: NO ACTION (default, error), CASCADE, SET NULL, SET DEFAULT.
UNIQUE constraint
No two rows may share this value (one NULL is allowed, unlike PK which allows none).
CHECK constraint
A boolean rule every row must satisfy: CHECK (salary > 0).
DEFAULT constraint
The value used when an INSERT doesn't supply the column.
ER diagram
Entity-Relationship diagram: boxes for tables, lines for FKs, with symbols showing cardinality (one-to-many etc.).
Normalization
Structuring tables to remove redundancy, so each fact is stored once. Done in steps called normal forms.
Functional dependency
“Column B is determined by column A”: product name depends on product id, not on the order it appears in.
Denormalization
Deliberately re-introducing redundancy (copied or computed columns) to make reads faster — a conscious trade, not an accident.
Quick notes
  • A table without a primary key is almost always a design bug.
  • Name your constraints (PK_orders, FK_orders_customers, CK_orders_amount) — auto-generated names make later ALTERs painful.
  • The FK column must match the referenced column's type exactly.
  • ON DELETE CASCADE is great for true parent-child (order → order items), dangerous elsewhere.
  • Normalize to 3NF by default; denormalize only with a measured reason.
  • Every CHECK/FK is one less bug class in your C# code — let the database be the last line of defence.

The same error protects the other direction: deleting a customer who has orders fails — unless you choose a different referential action:

ActionOn deleting the parentTypical use
NO ACTION (default)Error 547 if children existMost relationships — force explicit cleanup

CREATE TABLE sales.order_items
(
    order_id   INT NOT NULL
        CONSTRAINT FK_order_items_orders REFERENCES sales.orders (order_id)
        ON DELETE CASCADE,                       -- delete the order → its lines go too
    product_id INT NOT NULL,
    quantity   INT NOT NULL,
    unit_price DECIMAL(12,2) NOT NULL,
    CONSTRAINT PK_order_items PRIMARY KEY (order_id, product_id)
);
-- ON UPDATE CASCADE exists too (parent key value changes ripple down),
-- but with IDENTITY surrogate keys the parent key never changes, so it's rarely used.
Careful. Chained cascades delete more than you think, and SQL Server rejects designs where a table could be cascaded from two paths (error 1785, “may cause cycles or multiple cascade paths”). Keep CASCADE for one level of true ownership; elsewhere delete children explicitly.

3. UNIQUE, CHECK and DEFAULT

03_check_unique.sql
ALTER TABLE sales.customers
    ADD CONSTRAINT UQ_customers_email UNIQUE (email);

ALTER TABLE sales.customers
    ADD CONSTRAINT CK_customers_gstin
    CHECK (gstin IS NULL OR LEN(gstin) = 15);         -- optional, but if present must be 15 chars

ALTER TABLE sales.orders
    ADD CONSTRAINT CK_orders_amount CHECK (amount > 0);

-- A multi-column CHECK: discounts can't exceed the amount
ALTER TABLE sales.orders ADD discount DECIMAL(12,2) NOT NULL
    CONSTRAINT DF_orders_discount DEFAULT 0;
ALTER TABLE sales.orders
    ADD CONSTRAINT CK_orders_discount CHECK (discount >= 0 AND discount <= amount);

INSERT INTO sales.orders (customer_id, amount) VALUES (2, -50);    -- fails CK_orders_amount
INSERT INTO sales.customers (full_name, email, city)
VALUES (N'Asha Again', 'asha@example.in', N'Pune');                -- fails UQ_customers_email
  • UNIQUE differs from PK: a table can have many UNIQUE constraints, and a UNIQUE column may allow one NULL row.
  • CHECK sees one row at a time. “Total of all orders < credit limit” is not expressible as a CHECK — that's for triggers, procedures or application code.
  • A CHECK that evaluates to NULL (because a column is NULL) passes — NULL is “unknown”, not “false”. That's why the gstin check spells out IS NULL OR … for clarity.
  • DEFAULT applies only when the column is omitted from the INSERT (or with the keyword DEFAULT) — inserting an explicit NULL does not trigger it.

1NF — atomic values, no repeating groups

2NF — no partial dependencies on a composite key

With key (order_id, product_id): product_name depends on product_id alone, and ordered_on/customer columns on order_id alone. Each partial dependency moves to its own table:

  • products(product_id PK, product_name, unit_price)
  • orders(order_id PK, ordered_on, customer_name, customer_phone, customer_city)
  • order_items(order_id FK, product_id FK, qty) — only what depends on the full key stays

3NF — no transitive dependencies

In orders, phone and city depend on who the customer is, not on the order: order_id → customer → phone/city. Asha's phone is stored twice and can disagree with itself (an update anomaly). Extract the customer:

  • customers(customer_id PK, full_name, phone, city)
  • orders(order_id PK, customer_id FK, ordered_on)
  • products(product_id PK, product_name, unit_price)
  • order_items(order_id FK, product_id FK, qty, unit_price_at_sale)

Memory hook for 3NF: every non-key column depends on “the key, the whole key, and nothing but the key”. (Insert, update and delete anomalies all trace back to a column that breaks this.)

Tip. Why does order_items keep unit_price_at_sale when products has a price? Because the catalogue price changes and an old invoice must not. That's not a normalization failure — the price at the moment of sale is a genuine fact about the order line. Historical snapshots are correct design.

Self-check questions

Why can a UNIQUE column hold a NULL when a PK can't?A PK identifies rows, so every row must have a real, unique value. UNIQUE merely forbids duplicates among the values present; SQL Server permits exactly one NULL row in a UNIQUE index (stricter than the SQL standard, which allows many).
What does ON DELETE SET NULL require of the child column?It must be nullable — otherwise there is nothing valid to set, and the constraint is rejected when you create it.
A CHECK constraint evaluates to NULL for a row. Is the row rejected?No. CHECK rejects only rows where the condition is FALSE; NULL ('unknown') passes. That's why CHECK (discount <= amount) doesn't reject rows where discount is NULL.

Interview questions

BasicWhat is the difference between a primary key and a unique constraint?
Both enforce uniqueness via an index. A table has one PK, which allows no NULLs and is the default clustered index and FK target. UNIQUE constraints can be many per table, allow one NULL (in SQL Server), and typically guard natural keys like email while a surrogate PK identifies the row.
BasicWhat is a foreign key and what problem does it solve?
A column (or columns) constrained to match a PK/UNIQUE value in a referenced table, or be NULL. It guarantees referential integrity: no order can point at a customer that doesn't exist, and a referenced customer can't be deleted (unless a cascade rule says otherwise). It turns 'dangling reference' bugs into immediate, loud errors.
BasicExplain 1NF, 2NF and 3NF in one line each.
1NF: atomic column values, no repeating groups, and a key. 2NF: 1NF plus no column depending on only part of a composite key. 3NF: 2NF plus no column depending on another non-key column (no transitive dependencies). Shorthand: the key, the whole key, nothing but the key.
IntermediateSurrogate vs natural keys — which do you choose and why?
Default to a surrogate (INT IDENTITY): compact, stable, meaningless, so it never changes when business data does. Keep the natural key (email, PAN, ISBN) as a UNIQUE constraint so its uniqueness is still enforced. Natural keys as PKs cause pain when they change (cascading updates) or turn out not to be unique in the real world.
IntermediateWhat are insert, update and delete anomalies?
Symptoms of under-normalized tables. Insert anomaly: you can't record a product until someone orders it. Update anomaly: a customer's phone stored on 50 order rows must be changed 50 times, and a miss leaves contradictions. Delete anomaly: deleting the last order of a customer erases the customer's details too. Normalization removes the duplication that causes all three.
IntermediateWhen is denormalization justified?
When a measured read pattern is too slow or complex and the duplication has a defined sync strategy: precomputed totals maintained transactionally, reporting tables refreshed on a schedule, or point-in-time snapshots like price-at-sale (which is really historical accuracy, not redundancy). It's a performance trade accepted consciously — never the starting design.

Key definitions

The statement that reads data. You list columns (the projection) and where they come from.

4. NULL and three-valued logic

BasicExplain the logical order of query processing and why it matters.

BasicWhat LIKE wildcards does SQL Server support?

BasicHow do you test for NULL and why doesn't = NULL work?

IntermediateWhat's the difference between ISNULL and COALESCE?

Prefer COALESCE for portability and multi-fallback chains.
IntermediateHow do you implement stable paging in SQL Server?
ORDER BY a deterministic key (add the PK as a tiebreaker), then OFFSET (page-1)*size ROWS FETCH NEXT size ROWS ONLY. Note that big offsets still read and discard all skipped rows, so very deep paging is better served by keyset pagination: WHERE key > last-seen-key ORDER BY key.
IntermediateWhat does TOP (1) WITH TIES do?
It returns the first row per the ORDER BY plus any further rows whose sort-key values equal the last returned row's. TOP (1) WITH TIES ... Key definitions

DML
Data Manipulation Language: INSERT, UPDATE, DELETE, MERGE (SELECT reads). DDL is CREATE/ALTER/DROP.
INSERT … VALUES
Adds rows; one VALUES clause can carry many rows separated by commas.
INSERT … SELECT
Inserts the result of a query — copying or transforming existing data.
SELECT … INTO

The last IDENTITY value generated in your scope — the standard way to get a new row's id.

6. MERGE: upserts, and why to be careful

Classic job: a nightly stock feed arrives; update products we know, insert ones we don't.

05_merge.sql
CREATE TABLE dbo.stock_feed            -- what the warehouse sent tonight
(
    product_id INT NOT NULL PRIMARY KEY,
    counted    INT NOT NULL
);
INSERT INTO dbo.stock_feed VALUES (1, 140), (5, 60), (10, 25);

MERGE dbo.products WITH (HOLDLOCK) AS target
USING dbo.stock_feed AS src
    ON target.product_id = src.product_id
WHEN MATCHED THEN
    UPDATE SET target.stock = src.counted
WHEN NOT MATCHED BY TARGET THEN
    INSERT (product_id, name, category, price, stock, discontinued, launched)
    VALUES (src.product_id, N'(pending catalogue entry)', N'Uncategorised',
            0.01, src.counted, 0, CAST(SYSDATETIME() AS DATE))
OUTPUT $action, inserted.product_id, inserted.stock;
$action  product_id  stock
-------- ----------- ------
UPDATE   1           140
UPDATE   5           60
UPDATE   10          25
-- (all three ids exist in products, so no INSERT branch fired this run)

There's also WHEN NOT MATCHED BY SOURCE THEN DELETE — “remove target rows the feed no longer mentions” — which makes MERGE a full table synchroniser.

Caveats. MERGE caveats, worth repeating in interviews: (1) without HOLDLOCK/SERIALIZABLE two concurrent MERGEs can race and hit duplicate-key errors; (2) it has a long history of edge-case bugs (many fixed, reputation earned); (3) the source must not match one target row twice or you get error 8672; (4) complex MERGEs are hard to read and review. A plain transaction with UPDATE then INSERT … WHERE NOT EXISTS is often the clearer, safer upsert.

Common mistakes

  • Running UPDATE/DELETE without WHERE — no confirmation dialog exists; the statement just runs.
  • Using SCOPE_IDENTITY() after a multi-row insert and losing all ids but the last.
  • Assuming TRUNCATE works on a parent table — any referencing FK blocks it.
  • UPDATE…FROM with a one-to-many join silently picking an arbitrary value.
  • Trusting @@ROWCOUNT after another statement has run in between — read it immediately.

Self-check questions

Why does OUTPUT beat SCOPE_IDENTITY for multi-row inserts?SCOPE_IDENTITY returns only the single last identity value in scope. OUTPUT inserted.* streams every inserted row — all ids, in one round trip, and it also works for UPDATE and DELETE.
Can TRUNCATE be rolled back?Yes, inside an explicit transaction — it's minimally logged, not unlogged; SQL Server logs the page deallocations and can undo them. The 'TRUNCATE can't be rolled back' line is a myth (true in some other databases).
What does $action give you in a MERGE's OUTPUT?A string per affected row — 'INSERT', 'UPDATE' or 'DELETE' — telling you which branch handled it. Handy for logging what a sync actually did.

Interview questions

BasicWhat's the difference between DELETE and TRUNCATE?
DELETE removes rows one at a time, honours WHERE, fires triggers, keeps the identity counter, fully logs each row, and needs DELETE permission. TRUNCATE removes all rows by deallocating pages — much faster on large tables — takes no WHERE, fires no triggers, resets IDENTITY to the seed, needs ALTER permission, and is refused when any foreign key references the table. Both are transactional and can be rolled back.
BasicWhat is the OUTPUT clause?
A DML clause that returns the affected rows via the inserted and deleted pseudo-tables: new values for INSERT, old for DELETE, both for UPDATE. It can return to the client or INTO a table variable/table, which makes it perfect for capturing generated ids and writing audit rows in the same statement.
BasicHow do you insert the result of a query into a table?
INSERT INTO target (cols) SELECT … for an existing table — column count and types must line up. SELECT … INTO new_table FROM … creates a fresh table from the query's shape, copying names, types and rows but not constraints, defaults or indexes.
IntermediateHow do you update one table from another in T-SQL?
UPDATE alias SET alias.col = src.col FROM target AS alias JOIN source AS src ON … — T-SQL's UPDATE…FROM extension. Verify the join matches at most one source row per target row, because multiple matches silently apply an arbitrary one. The portable form is UPDATE target SET col = (SELECT … correlated subquery), which errors on multiple matches instead.
IntermediateWhat are the known problems with MERGE?
Race conditions under concurrency unless you add HOLDLOCK/SERIALIZABLE hints (two sessions can both see 'not matched' and collide); error 8672 when the source matches a target row more than once; a documented history of bugs around triggers, filtered indexes and OUTPUT; and sheer complexity that hides mistakes in review. It's fine for single-threaded ETL; for hot upsert paths many teams use explicit UPDATE/INSERT with appropriate locking.
IntermediateA multi-row INSERT hits a CHECK violation on its 7th row. What's in the table?
Nothing from that statement. A single SQL statement is atomic: the constraint failure rolls back all rows the statement had inserted so far. (The identity counter, however, may still have consumed values — gaps are normal.)
DAY 5 · FRI

JOINs: INNER, OUTER, CROSS, self joins and anti-joins

GoalCombine tables confidently: all five join types, the employee→manager self join, multi-table joins, where NULLs bite, and the right way to write “not in that table”.

Key definitions

JOIN
Combining rows from two tables by pairing rows that satisfy a condition (the join predicate).
Join predicate
The ON condition deciding which row pairs belong together, usually FK = PK.
INNER JOIN
Only pairs that match survive. Rows with no partner on the other side vanish.
LEFT (OUTER) JOIN
Everything from the left table, matched where possible; unmatched left rows get NULLs for the right side.
RIGHT (OUTER) JOIN
Mirror image: everything from the right table. Rarely written — most teams reorder tables and use LEFT.
FULL (OUTER) JOIN
Everything from both sides; unmatched rows from either side padded with NULLs.
CROSS JOIN
Every row paired with every row — the Cartesian product. No ON clause.
Self join
A table joined to itself under two aliases — e.g. employees to their managers.
Semi-join
“Rows that HAVE a match”, written with EXISTS — no columns from, and no duplicates caused by, the other table.
Anti-join
“Rows with NO match”, written with NOT EXISTS (or a LEFT JOIN … IS NULL check).
NOT IN + NULL trap
If the subquery list contains a single NULL, NOT IN returns no rows at all.
ON vs WHERE
For INNER joins they filter identically; for OUTER joins, ON decides what matches, WHERE filters the joined result — and can silently undo the OUTER part.
Quick notes
  • Modern syntax only: JOIN … ON. Comma joins with WHERE are 1989-style.
  • Start from the table you want ALL rows of, and LEFT JOIN the optional data onto it.
  • Alias every table (e, d, m) and qualify every column — mandatory in self joins.
  • An INNER JOIN can both drop rows (no match) and multiply rows (many matches). Know your cardinality.
  • Filter the preserved side in WHERE, the NULL-padded side in ON.
  • For “not in that table”, NOT EXISTS is the NULL-safe default.

The ON vs WHERE trap

01_on_vs_where.sql
-- Task: every department, with its Engineering-city employees if any.
-- ❌ Filtering the NULL-padded side in WHERE kills the OUTER behaviour:
SELECT d.dept_name, e.emp_name
FROM dbo.dept AS d
LEFT JOIN dbo.emp AS e ON e.dept_id = d.dept_id
WHERE e.salary > 80000;
-- R&D's row is (R&D, NULL): NULL > 80000 is UNKNOWN → row dropped.
-- The LEFT JOIN just became an INNER JOIN.

-- ✓ Conditions about the OUTER side belong in ON:
SELECT d.dept_name, e.emp_name
FROM dbo.dept AS d
LEFT JOIN dbo.emp AS e ON e.dept_id = d.dept_id AND e.salary > 80000
ORDER BY d.dept_id;
dept_name    emp_name
------------ ---------
Engineering  Asha
Engineering  Ravi
Sales        Meena
HR           Tara
R&D          NULL      ← still here
Remember. Rule of thumb: in a LEFT JOIN, put conditions on the LEFT (preserved) table in WHERE, and conditions on the RIGHT (nullable) table in ON. A WHERE condition on a right-side column that doesn't accept NULL quietly converts your outer join to an inner one — the single most common join bug in code review.

7. Anti-joins: NOT EXISTS vs NOT IN

03_anti_joins.sql
-- Departments with no employees — three spellings:

-- (a) NOT EXISTS: the recommended anti-join
SELECT d.dept_name
FROM dbo.dept AS d
WHERE NOT EXISTS (SELECT 1 FROM dbo.emp AS e WHERE e.dept_id = d.dept_id);
-- → R&D

-- (b) LEFT JOIN … IS NULL: same result, join-flavoured
SELECT d.dept_name
FROM dbo.dept AS d
LEFT JOIN dbo.emp AS e ON e.dept_id = d.dept_id
WHERE e.emp_id IS NULL;
-- → R&D

-- (c) NOT IN: THE TRAP
SELECT d.dept_name
FROM dbo.dept AS d
WHERE d.dept_id NOT IN (SELECT e.dept_id FROM dbo.emp AS e);
-- → 0 rows. Zero. Not even R&D.

Why (c) returns nothing: Imran's dept_id is NULL, so the list is (10, 10, 20, NULL, 30). For R&D the test is 40 <> 10 AND 40 <> 20 AND 40 <> 30 AND 40 <> NULL — and 40 <> NULL is UNKNOWN, which poisons the whole AND to UNKNOWN. Not TRUE → row dropped. One NULL in the list empties every NOT IN.

Tip. The positive direction is safer: IN with a NULL in the list still finds matches, and EXISTS is a clean semi-join (“employees who have a project in their department”: WHERE EXISTS (SELECT 1 FROM dbo.project p WHERE p.dept_id = e.dept_id)). Habit to build: EXISTS / NOT EXISTS by default; NOT IN only on columns declared NOT NULL.

Common mistakes

  • Filtering a LEFT JOIN's right side in WHERE and wondering where the NULL rows went.
  • NOT IN over a nullable column — one NULL and the query returns nothing.
  • Not noticing row multiplication from a 1-to-many join (sums double, next week's aggregates go wrong).
  • Self join without distinct aliases — SQL Server rejects the ambiguity, or worse, you join to the wrong copy.
  • Writing RIGHT JOINs that reviewers must mentally flip — reorder the FROM and use LEFT.

Self-check questions

An INNER JOIN returned fewer rows than the left table has. Why?Some left rows had no matching right row (unmatched FK or NULL join column) — inner joins drop them. The reverse surprise, MORE rows, means some left rows matched several right rows.
When does a LEFT JOIN behave exactly like an INNER JOIN?When the WHERE clause has a condition on a right-side column that NULL can't satisfy (e.salary > 80000, e.name = '…'). The padded rows fail the filter and vanish — move that condition into ON to keep outer behaviour.
Why prefer NOT EXISTS over NOT IN?NOT EXISTS is NULL-safe: it checks row existence per outer row and ignores NULL semantics in the values. NOT IN compares values, and a single NULL in the subquery result makes every comparison UNKNOWN, returning zero rows — a silent wrong answer, not an error.

BasicExplain the join types in one line each.
INNER: only matching pairs. LEFT: all left rows, right side NULL-padded where unmatched. RIGHT: the mirror. FULL: all rows from both sides, padded where unmatched. CROSS: every combination of rows (no ON). Self join: any of the above with the same table under two aliases.
BasicWhat is a self join and when do you need one?
Joining a table to itself under two aliases, needed when rows relate to other rows of the same table: employee→manager hierarchies, product→replacement-product, flight legs sharing an airport, finding duplicate rows. The aliases make one logical table act as two.
BasicWhat happens when the join column contains NULL?
NULL matches nothing — not even another NULL — because NULL = NULL is UNKNOWN. In an INNER join such rows disappear; in a LEFT join they survive from the preserved side with NULLs on the other. This is also the root of the NOT IN trap.
IntermediateIn an OUTER join, what's the difference between a condition in ON and in WHERE?
ON decides which rows count as matches, before the outer padding is applied — unmatched preserved rows still come back. WHERE filters the final joined result — a predicate a NULL-padded row can't pass removes it, effectively turning the outer join inner. For INNER joins the two placements are equivalent; for OUTER joins they're different queries.
IntermediateHow would you find rows in table A with no match in B, and which pattern do you avoid?
NOT EXISTS (SELECT 1 FROM B WHERE B.key = A.key) — the standard anti-join — or LEFT JOIN B … WHERE B.key IS NULL. Avoid NOT IN (SELECT key FROM B) unless B.key is NOT NULL: one NULL in the list makes the predicate UNKNOWN for every row and the query returns nothing.
IntermediateA query joining orders to order_items shows each order's total doubled after someone added a join to shipments. What happened?
Row multiplication: an order with 2 shipments now produces 2 copies of each item row, so any SUM over items counts everything twice. Fix by aggregating items before the join (derived table/CTE), joining shipments separately, or using EXISTS when shipments were only needed as a filter. Always know each join's cardinality before aggregating.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhy is the manager_id column nullable on the employees table?
The top of the hierarchy (CEO or single owner) has no manager. A nullable FK allows the value to be absent without pointing at a fake sentinel row. All other employees must have a manager_id once the company is properly modelled — an application business rule, not a database constraint (you'd use a trigger or CHECK to enforce 'everyone except CEO must have a manager').
BasicWhy store salary on both employees and salary_history?
Denormalization for read speed: the current salary lives on the row so every query doesn't need to aggregate history. salary_history records all revisions for auditability. The tradeoff is that updates must keep both in sync — which the seed script does explicitly with an UPDATE after each appraisal batch.
IntermediateThere is a potential circular foreign key between departments (manager_id → employees) and employees (department_id → departments). How did we handle it?
By inserting departments first without the manager_id FK, then adding the FK constraint after employees were inserted. The circular dependency only matters during inserts and alters; at query time it's just two normal FKs. SQL Server blocks CASCADE DELETE on circular paths but plain RESTRICT/NO ACTION FK pairs are fine.
IntermediateHow would you evolve this schema to support employees belonging to multiple departments?
Replace the single employees.department_id column with a junction table: hr.employee_departments (employee_id FK, department_id FK, is_primary BIT, effective_date) with a composite PK. Then make department_id on hr.employees nullable (or remove it) and join through the junction table. The junction lets you model matrix organisations, project-based assignments and department transfers with start/end dates.

BasicWhat does DATEDIFF(YEAR, hire_date, GETDATE()) measure?
The number of year boundaries crossed between the two dates — e.g. hire_date 2020-12-31 and today 2021-01-01 gives 1, even though only one day passed. For exact tenure in years use DATEDIFF(DAY, ...) / 365.25 or DATEDIFF(MONTH, ...) / 12. The choice depends on whether the business wants 'calendar years crossed' or 'actual time elapsed'.
BasicWhat is the purpose of the seed data in a development schema?
It gives the schema a realistic dataset so queries can be written, tested and reasoned about immediately without application code. Good seed data covers all relevant cases: nulls, boundary values, all join paths, and enough volume to tell if aggregate results look plausible.
IntermediateThe correlated subquery in Q4 runs once per row in the outer query. What is its time complexity and how would you replace it in production?
O(n²) in the worst case — for every employee, a scan of their department. On large tables this is slow. The production replacement is a window function: DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) in a CTE, then filter WHERE rnk <= 3. Window functions are computed in a single pass over the data.

At the database level: BACKUP DATABASE CompanyDb TO DISK = '/path/CompanyDb.bak' WITH COMPRESSION; then RESTORE DATABASE … WITH MOVE to adjust file paths. For just the schema and seed data: generate scripts in SSMS (right-click database → Tasks → Generate Scripts, include data).
