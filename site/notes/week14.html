DAY 1 · MON

Storage Internals: Pages, Heaps and B+-Trees

GoalUnderstand how SQL Server physically stores rows so that every index and query-plan decision you make for the rest of the phase is grounded in what the engine actually does.

Key definitions

Page
The 8 KB unit of I/O in SQL Server. All data, indexes and allocations are measured in pages.
Extent
Eight contiguous 8 KB pages (64 KB). Mixed extents serve multiple objects; uniform extents serve one.
Heap
A table with no clustered index. Rows are stored in insertion order across pages with no guaranteed sequence.
IAM page
Index Allocation Map: a page that tracks which extents belong to a table or index.
Clustered index
Organises the table rows themselves in B+-tree order on the clustered key. The leaf level IS the data.
B+-tree
Balanced tree where only leaf nodes hold data; internal nodes hold key values to route searches. Height rarely exceeds 4.
Root → intermediate → leaf
The three levels of a B+-tree; a seek walks from root to the matching leaf page.
Page split
When an INSERT targets a full page, SQL Server allocates a new page and moves roughly half the rows there, writing both pages.
Fill factor
The percentage of a leaf page left full at index creation/rebuild, leaving room for future inserts to avoid splits.
RID
Row IDentifier: (file:page:slot) used in a heap to reference a row from a nonclustered index.
Row locator
What a nonclustered index stores to point back to the base row: RID for heaps, clustered key value for clustered tables.
Forwarding pointer
When a heap row grows and can't fit on its original page, a 9-byte stub remains pointing to the new location.
Quick notes
  • An 8 KB page holds roughly 300–500 average order rows — plan tables around this, not individual rows.
  • Heaps are fast for bulk inserts but slow for range scans and suffer forwarding pointers after UPDATEs.
  • A clustered index physically orders rows; there can be only one per table.
  • Page splits happen during INSERT/UPDATE; fill factor pre-allocates free space to absorb them.
  • Wide or nullable clustered keys carry overhead into every nonclustered index — keep them narrow.
  • SQL Server reads and writes pages, not rows; a 'logical read' in STATISTICS IO means one page read from the buffer pool.

1. The 8 KB page — anatomy of storage

Every piece of data SQL Server manages lives in a page. The layout from top to bottom:

RegionSizeContent
Page header96 bytesPage id, type, free-space offset, row count, LSN
Row datavariableFixed-length columns, variable-length columns, NULL bitmap
Row offset array2 bytes × row countSlot array at the end of the page; each slot = offset of a row
page_usage.sql
-- How many pages does each table occupy? (run after the 1M-row Saturday load)
SELECT
    OBJECT_NAME(i.object_id)                AS table_name,
    i.name                                  AS index_name,
    i.type_desc,
    p.rows,
    au.total_pages,
    au.used_pages,
    au.data_pages,
    CAST(au.data_pages * 8.0 / 1024 AS decimal(10,2)) AS data_mb
FROM sys.indexes i
JOIN sys.partitions p
    ON  i.object_id = p.object_id
    AND i.index_id  = p.index_id
JOIN sys.allocation_units au
    ON  p.partition_id = au.container_id
WHERE OBJECT_NAME(i.object_id) IN ('orders','order_lines','customers','products')
ORDER BY table_name, i.index_id;

2. Heaps vs clustered tables

A heap has no inherent order; SQL Server finds its rows through IAM pages. A clustered table stores rows in the B+-tree leaf pages ordered by the clustered key.

    order_id   INT,

3. B+-tree structure

A clustered index on orders.order_id with 1 M rows at ~200 bytes/row occupies about 200 MB ≈ 25,000 pages. With a branching factor of ~400 keys per 8 KB internal page, the tree is only 3 levels: root → 1 intermediate level → ~25,000 leaf pages. Finding one row takes exactly 3 page reads regardless of table size.

btree_levels.sql
-- Inspect the B+-tree levels SQL Server built
SELECT
    index_level,
    page_count,
    record_count,
    avg_record_size_in_bytes
FROM sys.dm_db_index_physical_stats(
    DB_ID(), OBJECT_ID('sales.orders'), 1 /*clustered*/, NULL, 'DETAILED')
ORDER BY index_level DESC;
-- index_level 2 = root, 1 = intermediate, 0 = leaf

4. Page splits and fill factor

When an INSERT targets a page that is 100 % full, SQL Server splits it:

  1. Allocates a new page (possibly on a different extent — physical fragmentation).
  2. Moves roughly half the rows to the new page.
  3. Writes both dirty pages to disk.
  4. Updates the index tree above them.

Splits add log records, dirty cache pages and disk I/O. Fill factor pre-emptively leaves free space on each leaf page at rebuild time.

fill_factor.sql
-- Rebuild the clustered index with 80 % fill factor
-- Leaves 20 % free on every leaf page for future inserts
ALTER INDEX PK_orders ON sales.orders
    REBUILD WITH (FILLFACTOR = 80, ONLINE = ON);  -- ONLINE = ON requires Enterprise/Developer

-- Check fragmentation (avg_fragmentation_in_percent > 30 → REBUILD; 5–30 → REORGANIZE)
SELECT
    index_id,
    avg_fragmentation_in_percent,
    page_count
FROM sys.dm_db_index_physical_stats(
    DB_ID(), OBJECT_ID('sales.orders'), NULL, NULL, 'LIMITED')
WHERE page_count > 1000;
Tip. Fill factor is a one-time setting applied at REBUILD. It has no effect until the next reorganise or rebuild. Set it lower (70–80 %) on tables with heavy random inserts; leave it at the default 0 (= 100 %) on append-only tables like log tables.

clustered_key_choice.sql
-- Good: narrow, static, ever-increasing
CREATE TABLE sales.orders (
    order_id   INT           NOT NULL IDENTITY(1,1),
    customer_id INT          NOT NULL,
    order_date  DATE         NOT NULL,
    -- ...
    CONSTRAINT PK_orders PRIMARY KEY CLUSTERED (order_id)
);

-- Problematic: GUID clustered key causes random page splits
CREATE TABLE sales.orders_bad (
    order_id   UNIQUEIDENTIFIER NOT NULL DEFAULT NEWID(),   -- random → splits everywhere
    -- ...
    CONSTRAINT PK_orders_bad PRIMARY KEY CLUSTERED (order_id)
);
-- Fix: DEFAULT NEWSEQUENTIALID() generates ascending GUIDs within one server
Classic mistake. Using NEWID() as a clustered key on a high-insert table causes near-100 % page fragmentation within hours. Use NEWSEQUENTIALID() or switch to an INT/BIGINT identity.

Common mistakes

  • Using NEWID() as a clustered key — random GUIDs split pages on every INSERT.
  • Creating a clustered index on a wide or composite key — it inflates every nonclustered index.
  • Forgetting that there is no clustered index (heap) on a table that gets many point lookups.
  • Setting fill factor to 50 on an append-only log table — wastes half the storage for no benefit.
  • Assuming a 3-level B+-tree means 3 disk reads — the root and hot intermediate pages are usually cached.

Self-check questions

What is a page split?A page split occurs when SQL Server needs to insert a row into a full page. It allocates a new page, moves roughly half the existing rows there, then inserts the new row. This produces fragmentation and extra I/O.
What is fill factor?Fill factor is the percentage of a leaf-level page that is left full when an index is built or rebuilt. The remaining space is reserved for future inserts, reducing page splits. It is applied at rebuild time only.
Why prefer an IDENTITY over a GUID as a clustered key?IDENTITY generates ever-increasing integers that always append to the rightmost leaf page of the B+-tree, avoiding mid-tree page splits. Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is an 8 KB page in SQL Server?
The fundamental unit of storage and I/O. All data, indexes, and system metadata live in 8 KB pages. When SQL Server reads or writes data it always moves whole pages, never individual rows. STATISTICS IO counts logical reads in pages.
BasicWhat is a heap and when would you use one?
A table with no clustered index. Rows are stored wherever space exists, referenced by RID (file:page:slot). Heaps work well for staging tables used in bulk-insert-then-swap patterns, but are poor for OLTP tables that need frequent point lookups.
BasicWhat is a B+-tree and how does it help seek performance?
A balanced tree in which internal nodes hold only key values to route searches, and leaf nodes hold the actual data (for clustered indexes) or key + row-locator (for nonclustered). Because the tree stays balanced the height rarely exceeds 4, so a seek from root to leaf never takes more than 4 page reads regardless of table size.
IntermediateWhy does a wide clustered key hurt nonclustered indexes?
Nonclustered leaf pages store the clustered key value as the row locator. A 16-byte GUID as the CI key means every nonclustered index row is 12 bytes wider than it would be with a 4-byte INT. On a table with five NCI indexes and a million rows the extra storage can exceed 60 MB and slow every NCI range scan.
IntermediateWhat fragmentation percentage warrants a REBUILD vs REORGANIZE?
Below 5 %: ignore. 5–30 %: REORGANIZE (online, page-level defragment, low impact). Above 30 %: REBUILD (re-creates the index from scratch, optionally online on Enterprise). Check with sys.dm_db_index_physical_stats.
IntermediateWhat is a forwarding pointer in a heap and why is it harmful?
When an UPDATE increases a heap row's size beyond the current page's free space, SQL Server moves the row to a new page and leaves a 9-byte forwarding pointer stub. Subsequent reads must follow the pointer — two page reads instead of one. Forwarding pointers accumulate silently; rebuild the heap with ALTER TABLE … REBUILD to remove them.
DAY 2 · TUE

Nonclustered Indexes: Covering, Filtered and Composite

GoalDesign nonclustered indexes that eliminate key lookups, avoid write overhead, and answer the queries your application actually runs.

Key definitions

Nonclustered index (NCI)
A separate B+-tree ordered by the indexed key; leaf nodes point back to the base row via the clustered key (or RID for a heap).
Key lookup
When a nonclustered index seek cannot supply all columns the query needs, SQL Server follows the row locator back to the clustered index — one extra I/O per row.
INCLUDE columns
Non-key columns added to the NCI leaf level only; they satisfy column projections without widening the B+-tree key, eliminating key lookups.
Covering index
An NCI that provides every column a query needs (key + INCLUDE) so no key lookup is required.
Filtered index
An NCI with a WHERE clause, indexing only the rows that match the predicate, reducing size and improving precision.
Composite index
An NCI with two or more key columns; column order determines which queries it supports for seeks and range scans.
Index selectivity
The fraction of rows that match a predicate; high selectivity (few rows) makes an NCI worth using.
Write overhead
Every DML (INSERT/UPDATE/DELETE) must maintain all nonclustered indexes on the table — more indexes → slower writes.
Unique NCI
Enforces uniqueness on the indexed column(s), also improves the optimizer's cardinality estimates.
Missing index DMVs
sys.dm_db_missing_index_details and related views record columns the optimizer wished were indexed.
Quick notes
  • Lead with equality columns in composite keys, then range/ORDER BY columns, then cover with INCLUDE.
  • Always index foreign-key columns on the child table to avoid table scans during JOIN and CASCADE operations.
  • A filtered index on a sparse flag column (e.g. status = 'Pending') can be much smaller than a full NCI.
  • Keep the number of indexes to what queries actually need — each one costs writes on every DML.
  • INCLUDE adds columns only to leaf level; they cannot be seeked on and must not be large (avoid LOB columns).
  • Never add an index just because a DMV suggests it without checking its impact on write workloads.

1. How a nonclustered index works

The NCI is a separate B+-tree. Its leaf nodes store the indexed key plus the row locator (the clustered key value, or RID for a heap). To answer a query that needs columns not in the NCI, the engine follows each row locator back to the clustered index — a key lookup.

nci_basic.sql
-- NCI on orders.customer_id — supports seeks for a given customer
CREATE NONCLUSTERED INDEX IX_orders_customer
    ON sales.orders (customer_id);

-- Finding customer 42's orders: NCI seek → key lookup for each row
-- Execution plan shows: Index Seek + Key Lookup (Nested Loops)
SELECT order_id, order_date, total_amount
FROM sales.orders
WHERE customer_id = 42;

2. Covering indexes with INCLUDE

Add every column the SELECT list needs to INCLUDE, eliminating the key lookup entirely.

covering_index.sql
-- Covering: seek finds customer's rows AND supplies order_date and total_amount
CREATE NONCLUSTERED INDEX IX_orders_customer_covering
    ON sales.orders (customer_id)
    INCLUDE (order_date, total_amount);

-- Now the plan shows only: Index Seek (no Key Lookup)
SELECT order_id, order_date, total_amount
FROM sales.orders
WHERE customer_id = 42
ORDER BY order_date DESC;

-- The rule: key columns → WHERE / JOIN / ORDER BY; INCLUDE → SELECT list only
Tip. SSMS and Azure Data Studio can generate covering-index suggestions right from an execution plan. Right-click the green 'Missing Index' banner text in the plan XML.

3. Composite key column order

The first key column defines the sort of the entire NCI. Only predicates that match a leftmost prefix of the key can be seeked; the rest are scanned.

Index keyQuery predicateAccess type
(customer_id, order_date)WHERE customer_id = 42Seek — matches prefix
(customer_id, order_date)WHERE customer_id = 42 AND order_date >= '2026-01-01'Seek both columns
(customer_id, order_date)WHERE order_date >= '2026-01-01'Scan — no leading column
(order_date, customer_id)WHERE order_date >= '2026-01-01'Seek on order_date

composite_index.sql
-- Supporting "orders for customer X in date range"
CREATE NONCLUSTERED INDEX IX_orders_cust_date
    ON sales.orders (customer_id, order_date)
    INCLUDE (total_amount, status);

-- Seek: customer_id = equality (high selectivity), order_date = range
SELECT order_id, order_date, total_amount
FROM sales.orders
WHERE customer_id = 105
  AND order_date BETWEEN '2026-01-01' AND '2026-06-30'
ORDER BY order_date;

4. Filtered indexes

A filtered index is an NCI with a WHERE clause. It indexes only the qualifying rows, so it is smaller and faster when the matching rows are a small fraction of the table.

filtered_index.sql
-- Only pending orders (say 2 % of the table) need fast lookup for the dispatcher
CREATE NONCLUSTERED INDEX IX_orders_pending
    ON sales.orders (order_date, customer_id)
    INCLUDE (total_amount)
WHERE status = 'Pending';

-- Only active products
CREATE NONCLUSTERED INDEX IX_products_active_name
    ON sales.products (product_name)
WHERE is_active = 1;

-- SQL Server uses a filtered index automatically when the query predicate is compatible
SELECT order_id, customer_id, order_date, total_amount
FROM sales.orders
WHERE status = 'Pending'
  AND order_date >= CAST(GETDATE() AS DATE);
Avoid. Filtered indexes are only usable when the query's predicate is compatible with the filter. Parameterised queries need to have the matching literal or the index is skipped. Always verify with an actual execution plan.

5. Indexing foreign keys

SQL Server does not automatically create indexes on foreign-key columns. Without them every referential integrity check and JOIN to the parent table scans the child table.

fk_indexes.sql
-- After defining FKs, add NCI on each FK column
CREATE NONCLUSTERED INDEX IX_orders_customer_id
    ON sales.orders (customer_id);

CREATE NONCLUSTERED INDEX IX_order_lines_order_id
    ON sales.order_lines (order_id);

CREATE NONCLUSTERED INDEX IX_order_lines_product_id
    ON sales.order_lines (product_id);

-- Without IX_order_lines_order_id, deleting a customer cascades with a table scan
-- on order_lines for every deleted order — catastrophic at 1 M rows

6. Write overhead and index count

Every INSERT, UPDATE, or DELETE on the base table must maintain each nonclustered index on it. An UPDATE that changes an indexed column rewrites the NCI entry: delete old key, insert new key.

DML operationCost per NCI
INSERTInsert one row into every NCI (may cause NCI page split)
DELETEDelete one row from every NCI
UPDATE indexed columnDelete old key + insert new key in affected NCIs
UPDATE non-indexed columnNo NCI change (but INCLUDE columns must be updated)
index_usage.sql
-- View all indexes on orders with their fragmentation and usage
SELECT
    i.name,
    i.type_desc,
    ius.user_seeks,
    ius.user_scans,
    ius.user_lookups,
    ius.user_updates,       -- how many times this index was written
    ps.avg_fragmentation_in_percent
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats ius
    ON  ius.object_id = i.object_id
    AND ius.index_id  = i.index_id
    AND ius.database_id = DB_ID()
LEFT JOIN sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('sales.orders'),
    NULL, NULL, 'LIMITED') ps
    ON  ps.object_id = i.object_id
    AND ps.index_id  = i.index_id
WHERE i.object_id = OBJECT_ID('sales.orders');
-- user_updates >> user_seeks → the index costs more than it helps → consider dropping

Common mistakes

  • Adding too many indexes — a table with 15 NCIs can be slower on INSERT than a table with 3.
  • Leading with a low-selectivity column (e.g. status with only 3 values) — consider a filtered index instead.
  • Using INCLUDE for key columns that need to be seeked — INCLUDE columns cannot be used in seek predicates.
  • Not indexing FK columns — a DELETE on the parent table will scan every child table.
  • Dropping an index immediately when a DMV suggests it is unused — usage stats reset on service restart.

BasicWhat is a covering index?
A nonclustered index that contains all the columns a specific query needs — indexed key column(s) for the seek and additional columns in INCLUDE for the SELECT list — so the query engine never needs to follow a row locator back to the clustered index. Result: no key lookup, fewer I/Os.
BasicWhat is the difference between a key column and an INCLUDE column in an NCI?
Key columns form the B+-tree key: they determine the index order and can be used in seek predicates, range scans, and ORDER BY. INCLUDE columns are stored only at the leaf level: they satisfy SELECT-list column needs but cannot be seeked on and don't affect the index sort.
IntermediateHow do you pick the column order in a composite NCI?
Equality predicates first (highest selectivity first within equality), then range predicates, then ORDER BY columns. This maximises the number of queries that can seek the entire prefix before scanning the range portion.
IntermediateWhen is a filtered index better than a full NCI?
When the queries that need the index always filter on a small, well-defined subset of rows (e.g. status = 'Pending' covering 1 % of the table). The filtered NCI is smaller, cheaper to maintain, and more selective than a full index on the same column.
IntermediateHow does the optimizer decide when to use an NCI vs a clustered index scan?
It compares the estimated cost: for a selective predicate the NCI seek + key lookup is cheaper than a scan; for low-selectivity predicates the scan is cheaper (tipping point is roughly > 1 % of rows for random I/O storage). It also considers statistics, parallelism and covering.
AdvancedExplain the write amplification problem with many nonclustered indexes.
Every DML on the base table is replicated into each NCI: an INSERT generates N index-row inserts, an UPDATE to M indexed columns causes M delete+insert pairs across the NCIs. On a table with 10 NCIs, one base-table INSERT writes 11 B+-tree rows. This is called write amplification. Measure it with user_updates vs user_seeks in sys.dm_db_index_usage_stats.
DAY 3 · WED

Reading Execution Plans and I/O Statistics

GoalInterpret estimated and actual execution plans, decode the key operators, read SET STATISTICS IO/TIME output, and diagnose the classic key-lookup pattern.

Key definitions

Estimated plan
A query plan generated from statistics without executing the query. Useful for quick analysis; may differ from reality if statistics are stale.
Actual plan
The plan captured after the query runs, with actual row counts and execution times per operator. The definitive diagnostic tool.
Table Scan
Reads every page in a heap. Appears as a warning in plans — almost always signals a missing index.
Clustered Index Scan
Reads all leaf pages of the clustered index from left to right. Acceptable for large-range queries; a warning for OLTP point lookups.
Index Seek
Navigates the B+-tree to find only the qualifying rows. The goal for selective OLTP queries.
Key Lookup
A per-row trip from an NCI leaf back to the clustered index to fetch non-covered columns. High cost when row count is large.
Nested Loops Join
For each row of the outer input, seeks the inner input. Efficient when outer is small.
Hash Match Join
Builds a hash table from the smaller input, probes with the larger. Handles large unsorted inputs.
Merge Join
Advances two pre-sorted inputs in parallel. Very fast when both sides are ordered; requires a sort if they're not.
Sort operator
Spills to tempdb when memory is insufficient. Watch for a warning icon on this operator.
Logical reads
Pages read from the buffer pool (cache), reported by SET STATISTICS IO. The primary I/O cost metric.
Physical reads
Pages read from disk because they were not in the buffer pool. Only present on a cold cache.
Quick notes
  • Cost percentages in estimated plans are estimates — always use actual plans for diagnosis.
  • Thick arrows between operators = many rows flowing. Fat arrows after a seek usually mean the predicate is non-SARGable.
  • A key lookup in Nested Loops with thousands of rows is the clearest indicator that an INCLUDE column is missing.
  • SET STATISTICS IO ON measures logical reads per table, which is consistent regardless of cache state.
  • Physical reads vanish after the first run; logical reads are the repeatable, meaningful metric.
  • The Sort operator in a plan often means you're missing an ordered index — or ORDER BY is avoidable.

4. The key-lookup story

6. Useful plan-reading DMVs

plan_cache_top.sql
-- Last executed plan for a query (cached)
SELECT TOP 10
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count   AS avg_logical_reads,
    qs.total_elapsed_time  / qs.execution_count   AS avg_elapsed_us,

  • Reading only the estimated plan and not running the query — actual row counts reveal statistics problems.

Self-check questions

What is the difference between logical and physical reads?Logical reads are pages read from the buffer pool (in-memory cache). Physical reads are page reads from disk because the page was not cached. Logical reads are the repeatable performance metric; physical reads vanish after the first run as pages warm in cache.
How do you spot a stale statistics problem in an execution plan?Compare Estimated Rows vs Actual Rows on each operator. A large discrepancy (10× or more) means the optimizer worked from outdated histogram data, potentially choosing a suboptimal join or access method.
What does Scan count mean in STATISTICS IO?The number of times the scan or seek was initiated on that table. A Scan count greater than 1 usually means the table was accessed multiple times as the inner side of a Nested Loops join — once per row of the outer input.

BasicHow do you display an actual execution plan in SSMS?

BasicWhat does a Key Lookup operator mean and why is it expensive?

IntermediateWhen would you choose a Merge Join over a Hash Match?

Statistics, Parameter Sniffing and SARGability

GoalUnderstand how the query optimizer uses statistics to estimate row counts, what happens when it guesses wrong, how to detect and fix parameter sniffing, and how to write predicates the optimizer can seek on.

Key definitions

Statistics
Histograms and density vectors stored per column (or index) that the optimizer uses to estimate row counts for predicates.
Histogram
Up to 200 steps showing the distribution of column values: range, density and row count per bucket.
Cardinality estimate
The optimizer's prediction of how many rows a predicate will return. Wrong estimates produce wrong plans.
Parameter sniffing
SQL Server compiles a plan for the first parameter value used for a query and caches it; later executions with different parameters reuse that plan, which may be badly wrong for them.
OPTION(RECOMPILE)
A query hint that forces a fresh compilation for every execution, using the current parameter values. Eliminates sniffing at the cost of CPU for compilation.
OPTION(OPTIMIZE FOR (@p = value))
Hint to compile the plan as if @p equals a specific value, typically a representative middle value.
OPTION(OPTIMIZE FOR UNKNOWN)
Compile using average statistics instead of the sniffed value. Often a good default fix.
SARGable predicate
Search ARGument-able: a predicate the optimizer can resolve with an index seek (column compared to a value).
Non-SARGable predicate
A predicate that prevents an index seek: a function on the indexed column, a leading wildcard, or an implicit type conversion.
Implicit conversion
When a column's data type differs from the value compared against it, SQL Server silently converts every row value, forcing a scan.
Query Store
A per-database feature (SQL Server 2016+) that persists query plans, run-time stats and regressions across restarts.
Quick notes
  • Statistics are updated automatically at 20 % modification threshold by default (500 rows on small tables); after bulk loads, run UPDATE STATISTICS.
  • A plan that works for Ravi's 2 orders might be catastrophic for Meena's 50,000 orders if sniffed on Ravi first.
  • OPTION(RECOMPILE) is the strongest fix but adds CPU overhead; use it on queries whose optimal plan truly varies by parameter.
  • Wrapping an indexed column in a function (YEAR(order_date) = 2026) always causes a scan; rewrite as a range predicate.
  • Implicit conversion from NVARCHAR parameter to VARCHAR column is the most common invisible performance killer.
  • Query Store lets you force a good plan in production without changing application code.

4. SARGable predicates

A predicate is SARGable when SQL Server can translate it to a seek range on the index. The rule: the indexed column must be on its own on one side of the comparison.

-- Implicit conversion — the silent killer
-- Column definition: customer_code VARCHAR(20)
-- Application sends: WHERE customer_code = N'C001'  (NVARCHAR parameter)
-- SQL Server converts every VARCHAR row to NVARCHAR to compare → full table scan

-- Check for implicit conversion warnings in an actual plan:
-- Look for a yellow ! on the Index Scan; tooltip says "Type conversion in expression
-- (CONVERT_IMPLICIT) may affect "CardinalityEstimate" in query plan choice"

-- Fix: match parameter type to column type
-- In C#: use SqlDbType.VarChar (not NVarChar) for VARCHAR columns
-- In T-SQL: WHERE customer_code = 'C001'  (not N'C001')

-- SARGable date range (most common rewrite)
DECLARE @year INT = 2026;
-- ❌ Non-SARGable
SELECT * FROM sales.orders WHERE YEAR(order_date) = @year;
-- ✓ SARGable
SELECT * FROM sales.orders
WHERE order_date >= DATEFROMPARTS(@year, 1, 1)
  AND order_date <  DATEFROMPARTS(@year + 1, 1, 1);
Watch out. Implicit conversions from NVARCHAR to VARCHAR are the most common hidden performance issue in .NET applications because SqlClient defaults to NVARCHAR for string parameters. Always set SqlDbType.VarChar (or the equivalent in Dapper/EF Core) when the column is VARCHAR.

What is parameter sniffing?SQL Server compiles a stored procedure or parameterised query using the first parameter value it sees, then caches that plan. Subsequent calls with different parameters reuse the cached plan, which may be optimal for the original value but very slow for others.

Backups, Security and Watching ORM-generated SQL

GoalSet up a recoverable database with correct backup strategy, apply least-privilege security, and use SQL Server tooling to inspect and tune the SQL your ORM generates.

Key definitions

Full backup
A copy of the entire database at a point in time. The baseline for any restore.
Differential backup
Records all pages changed since the last full backup. Faster to take than a full; a restore needs: last full + last diff.
Transaction log backup
Backs up the active portion of the transaction log, allowing point-in-time recovery. Requires FULL or BULK_LOGGED recovery model.
Recovery model
Controls what SQL Server logs and how much data can be recovered. SIMPLE: log truncated at checkpoint (no log backups possible). FULL: everything logged; supports point-in-time restore.
RESTORE DATABASE
Restores data files from a backup chain; use WITH NORECOVERY for multi-step restores, WITH RECOVERY for the final step.
Login
A server-level security principal (SQL Server auth or Windows/Azure AD). Cannot access databases directly.
User
A database-level principal mapped to a login. Owns objects and receives permissions within the database.
Role
A named set of permissions. Fixed server roles (sysadmin, dbcreator) and fixed/user-defined database roles (db_datareader).
GRANT / DENY / REVOKE
GRANT gives a permission; DENY explicitly blocks it (overrides GRANT); REVOKE removes a previous GRANT or DENY.
Least privilege
Give every login/user/application only the minimum permissions required for their job.
Schema
A namespace for database objects (sales.orders). Permissions can be granted at schema level.
Quick notes
  • SIMPLE recovery model truncates the log at every checkpoint — no point-in-time restore is possible.
  • The backup chain is: last full → last differential (optional) → all log backups since the diff (or full).
  • Never connect an application with a sysadmin login; create a dedicated application user with minimal permissions.
  • DENY overrides GRANT even if the user is in a role that has GRANT — use it deliberately, rarely.
  • The public role every database user inherits should have no extra permissions.
  • ORM-generated SQL can be excellent or catastrophic; always check with SQL Server Profiler, Extended Events or EF Core logging.

What is the difference between FULL and SIMPLE recovery models?SIMPLE truncates the transaction log at every checkpoint, so no log backups are possible and you can only recover to the last full or differential backup. FULL logs all transactions continuously; combined with regular log backups it supports point-in-time recovery to any moment.
What is the difference between a login and a user?A login is a server-level security principal (SQL Server or Windows/Azure AD authentication). A user is a database-level principal created inside a specific database and mapped to a login. The login authenticates to the server; the user is what permissions are granted within the database.
What is DENY and when does it override GRANT?DENY explicitly refuses a permission. If a user has been GRANTed SELECT on a table through role membership but is also DENYed SELECT directly, the DENY wins. DENY overrides GRANT at any level, so it should be used deliberately and rarely — usually a schema redesign or separate role is cleaner.

BasicWhat is a full, differential and log backup?
Full: a copy of the entire database — the restore baseline. Differential: all pages changed since the last full — faster to take than a full; restoring needs last full + last diff. Log: the transaction log since the last log backup — restoring needs full + optional diff + all subsequent logs. Only FULL recovery model supports log backups.
BasicWhat is least privilege and why does it matter for database security?
Give every application login, database user, or service account only the permissions it actually needs — typically SELECT/INSERT/UPDATE/DELETE on the schemas it uses, and EXECUTE on stored procedures, not db_owner. If an account is compromised or the application has a SQL injection bug, an attacker cannot read billing data, drop tables, or run xp_cmdshell.
IntermediateExplain a full restore sequence using full + differential + log backups.
1. RESTORE DATABASE … WITH NORECOVERY (applies the full backup). 2. RESTORE DATABASE … WITH NORECOVERY (applies the most recent differential). 3. RESTORE LOG … WITH NORECOVERY for each log backup in sequence after the differential. 4. Final RESTORE LOG or RESTORE DATABASE WITH RECOVERY to bring the database online; optionally add STOPAT for point-in-time.

BasicWhy must you run UPDATE STATISTICS after a bulk load before benchmarking?
Statistics tell the optimizer how many rows a predicate returns. IntermediateHow did adding INCLUDE columns to the NCI produce a 616× logical-read reduction on the customer-history query?

IntermediateWhy did rewriting the product query from LIKE '%Electronics%' to category = 'Electronics' allow the filtered index to be used?

5. Mixed quiz — 8 questions

Q1. A query does an Index Seek on IX_orders_customer but still reads 8,000 pages. What is likely happening and how do you fix it? Key lookup. The NCI found the rows but cannot supply all selected columns, so for each matching row it follows the row locator to the clustered index. With many rows this causes thousands of random page reads. Fix: add the missing SELECT-list columns to INCLUDE on the NCI to make it covering.
Q2. What is the difference between OPTION(RECOMPILE) and OPTION(OPTIMIZE FOR UNKNOWN)? Recompile forces a fresh compilation on every execution using the actual runtime parameter — always optimal but adds CPU cost. OPTIMIZE FOR UNKNOWN compiles once using average statistics instead of the sniffed value — lower CPU cost, slightly suboptimal for extreme values, eliminates sniffing.
Q3. Why does WHERE YEAR(order_date) = 2026 prevent an index seek? Non-SARGable. The function YEAR() is applied to the indexed column, so SQL Server must evaluate it for every row in the table. Rewrite as order_date >= '2026-01-01' AND order_date < '2027-01-01' to get a range seek.
Q4. You send a string parameter from C# for a VARCHAR(20) column. What performance issue can arise? Implicit conversion. SqlClient defaults to NVARCHAR for C# string parameters. SQL Server must convert every VARCHAR column value to NVARCHAR for the comparison, forcing a full table scan. Fix: set SqlDbType.VarChar on the SqlParameter.
Q5. What recovery model must be in use to perform point-in-time recovery, and why? FULL recovery model. SIMPLE truncates the transaction log at every checkpoint, discarding the log records needed for point-in-time recovery. FULL keeps the log intact until a log backup is taken, allowing restore to any logged moment.
Q6. A table has a clustered index on order_id (INT IDENTITY) and 10 nonclustered indexes. How does an UPDATE to the total_amount column affect all these indexes? Only NCIs that include total_amount need to be updated. NCIs on other key columns are unaffected. If total_amount is in an INCLUDE column of some NCIs, those NCI leaf pages are rewritten. If it is a key column of an NCI, the old key is deleted and a new key is inserted (possibly causing a page split). The clustered index row is updated in place.
Q7. What does Scan count 9 mean in SET STATISTICS IO output? The scan or seek was initiated 9 times on that table. Usually this means the table was the inner side of a Nested Loops join and the loop iterated 9 times — once per outer row. It suggests either a very small outer input or a potential for a Hash/Merge join.
Q8. How does Query Store help recover from a plan regression after upgrading SQL Server? It persists query plans and their runtime statistics across restarts and upgrades. After an upgrade the new optimizer may choose a different (worse) plan. Query Store's Regressed Queries report identifies these automatically. You can force the previously good plan with sp_query_store_force_plan without changing application code, buying time to investigate a permanent fix.

IntermediateHow does fill factor relate to page splits?
Fill factor sets the percentage of a leaf page left full at the time of an index rebuild. A lower fill factor leaves more free space per page, so incoming inserts can fit on the existing page without splitting. Over time inserts fill the reserved space and splits resume; the next rebuild resets fill factor again.
IntermediateWhat is the difference between a scan and a seek in a clustered index?
A clustered index scan reads all leaf pages from left to right — it accesses the full table. A clustered index seek uses the B+-tree to navigate directly to the qualifying leaf page range, reading only the pages that contain the matching rows. The seek is O(log n + matched pages); the scan is O(total pages).
