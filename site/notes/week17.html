DAY 1 · MON

Program.cs, Kestrel and the Middleware Pipeline

GoalUnderstand what Program.cs does, how Kestrel serves HTTP, what the middleware pipeline is, and write both inline and class-based middleware that runs in the correct order.

Key definitions

Kestrel
The cross-platform HTTP server embedded in every ASP.NET Core app. It listens on TCP ports and translates bytes into HttpContext.
Minimal hosting model
The WebApplication.CreateBuilder + app.Run() pattern introduced in .NET 6 that removes Startup.cs.
WebApplicationBuilder
Returned by WebApplication.CreateBuilder(). Exposes Services (DI) and Configuration.
WebApplication
The built app. Exposes Use* methods to register middleware, then Run().
Middleware
A component that handles an HTTP request and optionally calls the next component.
RequestDelegate
Func<HttpContext, Task> — the signature every middleware ultimately is.
HttpContext
One instance per request, holding Request, Response, User, Items, etc.
Pipeline
The ordered chain of middleware components. The first registered runs first on the way in and last on the way out.
Use
Adds middleware and calls next() — both before and after the next component run.
Run
Adds a terminal middleware; never calls next().
Map
Branches the pipeline based on a URL path prefix.
launchSettings.json
VS/VS Code config for launch profiles — sets ports, environment, env vars. Not deployed.
ASPNETCORE_ENVIRONMENT
Env var that sets the environment name (Development / Staging / Production).
Quick notes
  • Middleware order matters: auth must come before authorisation, routing before endpoints.
  • Use without calling next() is effectively a Run — it short-circuits.
  • Kestrel is production-ready but can be fronted by Nginx/IIS for TLS termination.
  • app.Environment.IsDevelopment() is the idiomatic guard for dev-only middleware.
  • WebApplication.CreateBuilder already registers logging, configuration and DI.

1. Program.cs anatomy

Program.cs
// Program.cs — every line has a job
var builder = WebApplication.CreateBuilder(args);  // ① wire up config, DI, logging

builder.Services.AddControllers();                 // ② register services (later days)

var app = builder.Build();                         // ③ build — no more service registration after this

// ④ — MIDDLEWARE PIPELINE (order matters!)
app.UseHttpsRedirection();                         // redirect HTTP → HTTPS
app.UseRouting();                                  // match URL to an endpoint
app.UseAuthentication();                           // who are you?
app.UseAuthorization();                            // are you allowed?
app.MapControllers();                              // wire controller actions as endpoints

app.Run();                                         // ⑤ start Kestrel and block
Tip. The var app = builder.Build() line is the boundary: services before it, middleware after it.

2. How middleware executes

Think of a stack of functions. The pipeline runs in-order going in; then the same components run in reverse order on the way back out.

Program.cs
// Inline middleware with Use — runs both on the way in and the way out
app.Use(async (ctx, next) =>
{{
    Console.WriteLine($"→ {ctx.Request.Path}");   // executes on the WAY IN
    await next(ctx);                               // call the next middleware
    Console.WriteLine($"← {ctx.Response.StatusCode}"); // executes on the WAY OUT
}});

// Terminal middleware: never calls next
app.Run(async ctx =>
{{
    await ctx.Response.WriteAsync("नमस्ते! TodoAPI is running.");
}});

// Output for GET /:
//   → /
//   ← 200

3. Class-based middleware

Inline lambdas are fine for quick experiments, but for anything that needs DI or unit-testing, write a class.

Middleware/RequestTimingMiddleware.cs
// The middleware class — lives in /Middleware/RequestTimingMiddleware.cs
public class RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> logger)
{{
    public async Task InvokeAsync(HttpContext ctx)
    {{
        var sw = System.Diagnostics.Stopwatch.StartNew();
        await next(ctx);                               // inner pipeline runs here
        sw.Stop();
        logger.LogInformation("{Method} {Path} → {Status} in {Ms} ms",
            ctx.Request.Method, ctx.Request.Path,
            ctx.Response.StatusCode, sw.ElapsedMilliseconds);
    }}
}}

// Extension method (optional but idiomatic)
public static class RequestTimingExtensions
{{
    public static IApplicationBuilder UseRequestTiming(this IApplicationBuilder app)
        => app.UseMiddleware<RequestTimingMiddleware>();
}}
Program.cs (excerpt)
// Register in Program.cs — BEFORE MapControllers or MapGet
app.UseRequestTiming();
Tip. If the middleware needs a scoped service, inject it into InvokeAsync as a parameter — not into the constructor — because the middleware itself is a singleton.

4. Use / Run / Map

Program.cs
// Use — chains middleware
app.Use(async (ctx, next) => {{ /* before */ await next(ctx); /* after */ }});

// Run — terminal, nothing after it runs
app.Run(async ctx => await ctx.Response.WriteAsync("Done"));

// Map — branches on path prefix; each branch gets its own sub-pipeline
app.Map("/health", branch =>
{{
    branch.Run(async ctx =>
    {{
        ctx.Response.ContentType = "application/json";
        await ctx.Response.WriteAsync("""{{"status":"ok"}}""");
    }});
}});

// MapWhen — branches on any predicate (e.g. header value)
app.MapWhen(ctx => ctx.Request.Headers.ContainsKey("X-Internal"),
    branch => branch.Run(async ctx => await ctx.Response.WriteAsync("internal path")));

6. Correct middleware order

MiddlewareWhy its position matters
UseExceptionHandler / UseDeveloperExceptionPageMust be first so it catches exceptions from everything downstream
UseHsts / UseHttpsRedirectionEarly, before anything writes to the response
UseStaticFilesBefore routing — serves .css/.js without hitting the endpoint pipeline
UseRoutingPopulates RouteData; auth and policy need it
UseAuthenticationAfter routing (needs the matched endpoint metadata for some schemes)
UseAuthorizationAfter authentication
MapControllers / MapGet / …Last — the actual endpoint executers

Common mistakes

  • Registering UseAuthentication before UseRouting (some schemes rely on endpoint metadata).
  • Writing app.Use after app.Run — it's unreachable.
  • Calling await next(ctx) more than once per request.
  • Injecting a scoped service into middleware constructor instead of InvokeAsync.
  • Forgetting to call await next(ctx) in a Use middleware and silently short-circuiting.

Self-check questions

What does await next(ctx) do?It hands control to the next middleware in the pipeline. Code before it runs on the way in; code after it runs on the way out.
What is the difference between Use and Run?Both add middleware. Use chains to the next component (by calling next). Run is terminal — it never calls next and ends the pipeline.
What env variable controls the environment name?ASPNETCORE_ENVIRONMENT. Common values are Development, Staging, Production. app.Environment.IsDevelopment() checks it.

BasicWhat is Kestrel?
Kestrel is ASP.NET Core's built-in, cross-platform HTTP server. It listens on TCP, parses HTTP, and feeds requests into the middleware pipeline. It's production-capable and can sit behind a reverse proxy (Nginx, IIS, YARP) for TLS termination.
BasicWhat is middleware and how is the pipeline ordered?
Middleware is a function that processes an HttpContext and optionally calls the next function. Components are added in order — first registered runs first on the way in and last on the way out. Order is critical: exception handling must be first, auth before authorisation, routing before endpoints.
BasicExplain Use vs Run vs Map.
Use adds a middleware that may call next(). Run adds a terminal middleware that never calls next. Map branches the pipeline on a path prefix, giving the branch its own sub-pipeline.
IntermediateWhat is the minimal hosting model and why was Startup.cs removed?
Starting in .NET 6, WebApplication.CreateBuilder and WebApplication replace the separate Startup class. Services and middleware can be configured in one place (Program.cs), reducing boilerplate and aligning with C# top-level statements.
IntermediateHow do you inject a scoped service into middleware?
Add it as a parameter to InvokeAsync, not to the constructor. Middleware is a singleton; injecting a scoped service into the constructor would capture it for the application lifetime, causing bugs.
IntermediateHow does ASP.NET Core find the right appsettings file?
appsettings.json is always loaded. Then appsettings.{Environment}.json is loaded and merged on top. If a key exists in both, the environment-specific file wins.
DAY 2 · TUE

Dependency Injection Lifetimes

GoalMaster Singleton, Scoped and Transient lifetimes with concrete instance-ID demos, understand the captive dependency trap, and use IServiceScopeFactory and keyed services (.NET 8).

Key definitions

DI container
The built-in IServiceCollection / IServiceProvider that creates and manages objects.
Singleton
One instance for the entire app lifetime. Shared by every request and every thread.
Scoped
One instance per HTTP request (or per manually created scope). The right lifetime for DbContext.
Transient
A new instance every time it is resolved. Cheap, stateless services.
Service descriptor
An entry in IServiceCollection describing a service type, its implementation, and lifetime.
Captive dependency
A singleton that holds a scoped or transient service, keeping it alive longer than intended.
ValidateScopes
DI option that detects captive dependency bugs at startup in Development.
ValidateOnStart
Checks that every registered service can be resolved at startup, not on the first request.
IServiceScopeFactory
Lets you create a DI scope manually — useful inside background services or singletons.
IEnumerable<T> injection
Inject all registrations of an interface. Last AddX call wins the single-inject slot.
Keyed services
.NET 8: register multiple implementations of the same interface under different string/enum keys.
InstanceId
A Guid set at construction, useful to prove which instance is returned.
Quick notes
  • Scoped is the default for services that use DbContext — one per request = one transaction.
  • Singleton services must be thread-safe — they can be called by many threads concurrently.
  • builder.Services.AddScoped<T>() is the most common registration.
  • Use TryAdd* family to register a default that can be overridden (useful in libraries).
  • Calling provider.GetRequiredService<T>() throws if T isn't registered — good for startup failure.

1. Instance-ID demo — proving lifetimes

Services/Traceable.cs
// Services/Traceable.cs — base service with a visible instance ID
public interface ITraceable {{ Guid Id {{ get; }} }}

public class SingletonService : ITraceable
{{
    public Guid Id {{ get; }} = Guid.NewGuid();     // set once at construction
}}
public class ScopedService : ITraceable
{{
    public Guid Id {{ get; }} = Guid.NewGuid();
}}
public class TransientService : ITraceable
{{
    public Guid Id {{ get; }} = Guid.NewGuid();
}}
Program.cs
// Program.cs registrations
builder.Services.AddSingleton<SingletonService>();
builder.Services.AddScoped<ScopedService>();
builder.Services.AddTransient<TransientService>();

// Minimal API endpoint to inspect lifetimes
app.MapGet("/lifetimes", (
    SingletonService  s1,
    SingletonService  s2,   // same instance
    ScopedService     sc1,
    ScopedService     sc2,  // same instance within THIS request
    TransientService  t1,
    TransientService  t2    // different instances every time
) =>
{{
    return new
    {{
        singleton_same  = s1.Id == s2.Id,   // true
        scoped_same     = sc1.Id == sc2.Id, // true
        transient_same  = t1.Id == t2.Id,   // false
        singleton_id    = s1.Id,
        scoped_id       = sc1.Id,
    }};
}});
// Two requests in a row: singleton_id stays the same, scoped_id changes.

2. Captive dependency and ValidateScopes

Program.cs
// ❌ CAPTIVE DEPENDENCY — catches the scoped service in a singleton's lifetime
public class BadSingletonService(ScopedService scoped)
{{
    // The first request's ScopedService stays alive for the entire app lifetime
    // Every request after the first reuses stale state — including stale DbContext!

builder.Host.UseDefaultServiceProvider(o =>
{{
    o.ValidateScopes  = true;   // detect scoped-in-singleton at startup

3. IServiceScopeFactory — creating a scope manually

Background services (IHostedService) are singletons. They need IServiceScopeFactory to resolve scoped services per work item.

Services/GstReminderService.cs
// A hosted service that processes GST reminders on a schedule
public class GstReminderService(IServiceScopeFactory scopeFactory, ILogger<GstReminderService> logger)
    : BackgroundService
{{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {{
        while (!ct.IsCancellationRequested)
        {{
            await using var scope = scopeFactory.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();  // scoped!
            var dueCount = await db.Todos
                .Where(t => t.DueDate <= DateOnly.FromDateTime(DateTime.Today) && !t.IsDone)
                .CountAsync(ct);
            logger.LogInformation("{Count} GST/tax items are due today", dueCount);

            await Task.Delay(TimeSpan.FromHours(1), ct);
        }}
    }}
}}

5. Keyed services (.NET 8)

Program.cs
// Register under different keys — useful for strategy/factory patterns
builder.Services.AddKeyedScoped<INotifier, EmailNotifier>("email");
builder.Services.AddKeyedScoped<INotifier, SmsNotifier>("sms");
builder.Services.AddKeyedScoped<INotifier, WhatsAppNotifier>("whatsapp");

// Resolve by key in a minimal API endpoint
app.MapPost("/notify/{{channel}}", async (
    [FromKeyedServices("email")]    INotifier email,
    [FromKeyedServices("sms")]      INotifier sms,
    string channel, string message) =>
{{
    var notifier = channel switch
    {{
        "email" => email,
        "sms"   => sms,
        _       => throw new ArgumentException($"Unknown channel: {{channel}}")
    }};
    await notifier.NotifyAsync(message);
    return Results.Ok();
}});

// Or resolve programmatically from a scope
var notifier = scope.ServiceProvider.GetRequiredKeyedService<INotifier>("whatsapp");
Tip. Keyed services replace the common pattern of injecting a factory function or dictionary of implementations.

6. Lifetime summary

LifetimeCreatedSharedTypical useThread-safe?
SingletonOnce at first resolveAll requests, all threadsConfig, caches, HttpClient factoryMust be
ScopedOnce per request/scopeWithin one requestDbContext, unit-of-work, current userOnly within the scope
TransientEvery resolveNeverLightweight stateless helpers, formattersN/A (new each time)

Common mistakes

  • Injecting a scoped service into a singleton (captive dependency — DbContext in a singleton is a classic bug).
  • Making a singleton that caches per-request data (all requests share the same state).
  • Forgetting that transient instances aren't disposed until the scope ends (not immediately).
  • Using GetService<T> (returns null) where GetRequiredService<T> (throws) is safer.
  • Registering the same service twice with AddScoped when you meant to override with TryAddScoped.

Self-check questions

What is a captive dependency?When a longer-lived service (Singleton) holds a shorter-lived service (Scoped/Transient), keeping it alive beyond its intended scope, causing stale state and resource leaks.
Why is Scoped the right lifetime for DbContext?One DbContext per request = one database connection, one transaction, one change-tracker. Sharing it across requests would mix transactions.
How do you use a scoped service from a background service?Inject IServiceScopeFactory into the background service (which is a singleton), then call CreateAsyncScope() per work item and resolve the scoped service from scope.ServiceProvider.

Interview questions

BasicWhat are the three DI lifetimes in ASP.NET Core?
Singleton (one instance for the whole app), Scoped (one per HTTP request or manual scope), Transient (new instance every time it's resolved). Register with AddSingleton, AddScoped, AddTransient.
BasicWhy can't you inject a Scoped service into a Singleton?
The Singleton is created once and lives for the app's lifetime. The Scoped service's scope (the request) ends, but the Singleton still holds a reference to it, keeping it alive and stale. This is the captive dependency bug.
BasicHow do you register and resolve all implementations of an interface?
Register each with AddScoped/AddSingleton/AddTransient on the same interface. Inject IEnumerable<T> to get all of them. Direct injection of T returns only the last registration.
IntermediateWhat is ValidateScopes and when should you enable it?
A DI option that checks at Build() time that no Singleton captures a Scoped dependency. It's auto-enabled in Development but you should also enable ValidateOnStart to catch all resolution errors at startup, not on the first request.
IntermediateWhat are keyed services in .NET 8?
A way to register multiple implementations of the same interface under different string/enum keys, then resolve the right one by key using [FromKeyedServices(key)] in endpoints or GetRequiredKeyedService(key) programmatically. Replaces factory/dictionary patterns.
IntermediateWhen would you use IServiceScopeFactory?
When a singleton or background service needs to consume scoped services. Create a scope per unit of work (e.g. per message, per job), resolve scoped services from it, and dispose the scope when done.

GoalLayer configuration sources correctly, bind strongly typed options, choose between IOptions/IOptionsSnapshot/IOptionsMonitor, and validate at startup.

Key definitions

IConfiguration
The runtime view of all configuration sources merged together.
appsettings.json
Base configuration file, always loaded.
appsettings.{Environment}.json
Environment-specific overrides loaded on top.
Environment variables
Override any config key at deploy time. Double underscore __ acts as a nesting separator.
Command-line args
Override at run time: dotnet run --Smtp:Port=587.
User secrets
Development-only secrets stored outside the project, never committed to git.
Options pattern
Bind a config section to a typed POCO via Configure<T>.

Singleton. Reads config once at startup. Use for settings that never change.
IOptionsSnapshot<T>
Scoped. Re-reads config per request. Use for settings that reload at runtime.

Triggers validation at startup instead of first use.
Quick notes
  • Config key lookup is case-insensitive.
  • __ in env var names maps to : in config keys: Smtp__Port=587 sets Smtp:Port.
  • User secrets are keyed to the project's <UserSecretsId> in the .csproj.
  • Never put real credentials in appsettings.json — use user-secrets in dev, Key Vault / env vars in prod.
  • IOptions<T> is a singleton — the same instance is returned across the app lifetime.

Controllers

GoalUse [ApiController] attribute routing, understand automatic 400 validation, return ActionResult<T>, and choose between controllers and minimal APIs.

Key definitions

[ApiController]
Attribute that enables API-specific behaviour on a controller class: auto 400, binding inference, attribute routing required.
ControllerBase
Base class for API controllers. Provides helper methods like Ok(), NotFound(), BadRequest(), CreatedAtAction().
[Route] attribute
Defines the route template for a controller or action.
[ApiController] automatic 400
When model binding or validation fails, [ApiController] returns a 400 ProblemDetails automatically — before the action runs.
ModelState
The validation dictionary populated by model binding and data annotations.
ActionResult<T>
A union return type that can be either T (auto 200) or any IActionResult (NotFound, BadRequest, etc.).
[FromBody]
Explicitly bind a parameter from the JSON request body (implicit with [ApiController]).
[FromRoute] / [FromQuery]
Explicit source binding on action parameters.
CreatedAtAction
Returns 201 with a Location header pointing to the GET endpoint for the new resource.
ProducesResponseType
Documents expected status codes on an action for Swagger.
ControllerRoute token
[controller] in route templates is replaced by the controller class name minus 'Controller'.
Quick notes
  • [ApiController] requires attribute routing — no convention-based routing.
  • ModelState.IsValid is checked automatically; don't re-check it unless you have a reason.
  • Return ActionResult<T> (not IActionResult) so Swagger sees the response schema.
  • Keep controllers thin: they translate HTTP to service calls and back, nothing else.

        if (isDone.HasValue)
            q = q.Where(t => t.IsDone == isDone.Value);
        if (Enum.TryParse<Priority>(priority, ignoreCase: true, out var p))
            q = q.Where(t => t.Priority == p);

        var items = await q
            .OrderByDescending(t => t.CreatedAt)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(t => t.ToDto())
            .ToListAsync();

        return TypedResults.Ok(items);
    }}

    // GET /api/todos/{id}
    public static async Task<IResult> GetById(int id, AppDbContext db)
    {{
        var item = await db.Todos.FindAsync(id);
        return item is null ? TypedResults.NotFound() : TypedResults.Ok(item.ToDto());
    }}

    // POST /api/todos
    public static async Task<IResult> Create(CreateTodoDto dto, AppDbContext db)
    {{
        var item = new TodoItem
        {{
            Title    = dto.Title,
            DueDate  = dto.DueDate,
            Priority = dto.Priority
        }};
        db.Todos.Add(item);
        await db.SaveChangesAsync();
        return TypedResults.Created($"/api/todos/{{item.Id}}", item.ToDto());
    }}

    // PUT /api/todos/{id}
    public static async Task<IResult> Update(int id, UpdateTodoDto dto, AppDbContext db)
    {{
        var item = await db.Todos.FindAsync(id);
        if (item is null) return TypedResults.NotFound();

        item.Title    = dto.Title;
        item.DueDate  = dto.DueDate;
        item.Priority = dto.Priority;
        await db.SaveChangesAsync();
        return TypedResults.Ok(item.ToDto());
    }}

    // DELETE /api/todos/{id}
    public static async Task<IResult> Delete(int id, AppDbContext db)
    {{
        var item = await db.Todos.FindAsync(id);
        if (item is null) return TypedResults.NotFound();
        db.Todos.Remove(item);
        await db.SaveChangesAsync();
        return TypedResults.NoContent();
    }}

    // PATCH /api/todos/{id}/toggle
    public static async Task<IResult> Toggle(int id, AppDbContext db)
    {{
        var item = await db.Todos.FindAsync(id);
        if (item is null) return TypedResults.NotFound();
        item.IsDone = !item.IsDone;
        await db.SaveChangesAsync();
        return TypedResults.Ok(item.ToDto());
    }}
}}

BasicWhat is an EF Core migration?
A C# file (and snapshot) generated by dotnet ef migrations add that describes one schema change. MigrateAsync() applies all pending migrations to the database.
BasicWhy use DTOs instead of returning the entity directly?
DTOs decouple the API contract from the database model: you can reshape, omit, or rename fields without changing the entity, avoid exposing navigation properties, and prevent over-posting (extra fields being saved).
IntermediateHow does IsDevelopment() change the database provider?
We check app.Environment.IsDevelopment() in Program.cs and register UseSqlite for dev and UseSqlServer for other environments, keeping the development experience simple (file-based, no install) while using SQL Server in production.
IntermediateWhat does db.Database.MigrateAsync() do at startup?
It applies any pending EF Core migrations to the target database, creating tables if they don't exist. This eliminates the need to run dotnet ef database update manually on each deployment, though for production you may prefer a separate migration step.

1. Validation endpoint filter

Filters/ValidateFilter.cs
using System.ComponentModel.DataAnnotations;
using Microsoft.AspNetCore.Http;

namespace TodoApi.Filters;

// A generic filter that validates any DTO parameter with data annotations
public class ValidateFilter<T> : IEndpointFilter where T : class
{{
    public async ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {{
        // Find the first argument that is of type T
        var dto = ctx.Arguments.OfType<T>().FirstOrDefault();
        if (dto is null) return await next(ctx);

        var results  = new List<ValidationResult>();
        var valid    = Validator.TryValidateObject(dto, new ValidationContext(dto), results, validateAllProperties: true);
        if (!valid)
        {{
            var errors = results
                .GroupBy(r => r.MemberNames.FirstOrDefault() ?? "")
                .ToDictionary(
                    g => g.Key,
                    g => g.Select(r => r.ErrorMessage ?? "Invalid value").ToArray());
            return TypedResults.ValidationProblem(errors);
        }}
        return await next(ctx);
    }}
}}

BasicWhat does Swashbuckle do?
Swashbuckle reads your ASP.NET Core app's routing metadata and generates an OpenAPI (Swagger) JSON spec, then serves a Swagger UI at /swagger where you can explore and try every endpoint interactively.
BasicWhy do minimal API endpoints need an explicit validation filter while controllers don't?
[ApiController] hooks into the model binding pipeline and returns 400 automatically on invalid ModelState. Minimal APIs don't use controllers, so there's no automatic 400 — you must add it via an IEndpointFilter.
IntermediateHow do you apply a filter to every endpoint in a group?
Call group.AddEndpointFilter<TFilter>() on the MapGroup result. The filter runs for every endpoint registered on that group.
IntermediateHow does db.Database.MigrateAsync() differ from EnsureCreated()?
MigrateAsync applies all pending EF Core migrations in order, maintaining version history and supporting incremental schema changes. EnsureCreated creates the schema from the current model state in one shot, skipping migrations; it's simpler but cannot evolve the schema over time.
