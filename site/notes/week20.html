DAY 1 · MON

Authentication, Authorisation and JWT Fundamentals

GoalUnderstand the difference between AuthN and AuthZ, compare cookie vs token strategies, dissect a JWT, and reason clearly about where tokens should be stored and why HTTPS is non-negotiable.

Key definitions

Authentication (AuthN)
Proving who you are — verifying identity, e.g. entering a password or OTP.
Authorisation (AuthZ)
Deciding what you are allowed to do once identity is established.
Cookie-based session
Server stores session data, sends a session ID in a Set-Cookie header; browser resends it automatically.
Token-based (JWT)
Server issues a signed token; client stores it and sends it in the Authorization header.
JWT (JSON Web Token)
A compact, URL-safe token with three Base64Url parts: header.payload.signature.
Header
First JWT part: algorithm (alg) and type (typ).
Payload
Second JWT part: claims — standard (sub, exp, iat, iss, aud) plus custom.
Signature
Third JWT part: HMAC or RSA over header + payload using the secret or private key.
Claim
A statement about a subject, e.g. role: admin or mobile: +919876543210.
HMAC-SHA256 (HS256)
Symmetric signing — same secret signs and verifies. Good for a single service.
RS256
Asymmetric RSA signing — private key signs, public key verifies. Services can verify without the secret.
XSS (Cross-Site Scripting)
Injected script reads localStorage; a reason NOT to store tokens there.
CSRF (Cross-Site Request Forgery)
Tricks the browser into sending a cookie to your server from another site.
HTTPS
TLS over HTTP; encrypts the channel so tokens can't be intercepted in transit.
Quick notes
  • AuthN always comes before AuthZ — you must know who someone is before deciding what they can do.
  • JWTs are signed, not encrypted. Anyone can Base64-decode the payload. Never put secrets (Aadhaar number, CVV) in a JWT.
  • HMAC: single shared secret — fast, fine for a monolith. RSA: private key signs, public key verifies — needed when other services or mobile clients verify tokens without the secret.
  • exp (expiry) is a Unix timestamp in seconds, not milliseconds.
  • localStorage is XSS-vulnerable — an injected script can steal the token. HttpOnly cookies are immune to XSS but need CSRF protection. Many SPAs choose cookies for access tokens in production.
  • HTTPS is not optional. Without it, every token you issue travels in plaintext across the network.

1. AuthN vs AuthZ — why the distinction matters

When a customer of Ugaav Agro's ordering portal logs in, two checks happen in sequence:

StepQuestion answeredExample decision
AuthenticationIs this really Priya Sharma?OTP to +91 98765 43210 matches → identity confirmed
AuthorisationCan Priya access this route?Role = farmer → can place orders, cannot view admin dashboard

A bug that swaps these is catastrophic: authorisation without authentication lets anyone reach admin pages.

3. JWT anatomy

A JWT is three Base64Url-encoded JSON objects joined by dots: header.payload.signature.

jwt-anatomy.json
// --- Decoded header ---
{
  "alg": "HS256",    // HMAC-SHA256
  "typ": "JWT"
}

// --- Decoded payload (claims) ---
{
  "sub": "user_42",                     // subject (user ID)
  "name": "Priya Sharma",
  "mobile": "+919876543210",
  "role": "farmer",
  "iss": "ugaav-auth",                  // issuer
  "aud": "ugaav-orders",               // audience
  "iat": 1700000000,                    // issued-at (Unix seconds)
  "exp": 1700003600                     // expires-at (Unix seconds) — 1 hour later
}

// --- Signature ---
// HMAC_SHA256(
//   base64url(header) + "." + base64url(payload),
//   SECRET_KEY                        // server holds this; never send it to clients
// )
Avoid. The payload is Base64Url-encoded, NOT encrypted. Paste any JWT into jwt.io and you can read every claim. Never put a user's password, Aadhaar number, CVV, or any private data in a JWT claim.

4. HMAC vs RSA signing

// HMAC-SHA256 (HS256) — symmetric
// One secret: sign with it, verify with it
// If a second service needs to verify tokens, it must also have the secret → risk of exposure

// RS256 — asymmetric RSA
// Private key (server keeps safe): signs tokens
// Public key (can be published as JWKS endpoint): verifies tokens
// A mobile app or microservice downloads the public key and verifies locally — never touches the secret

// Choosing:
// Single API + single trust boundary  → HS256 is fine, simpler
// Multiple services or public clients → RS256 (or ES256 — ECDSA, same idea, smaller keys)
HS256RS256
Key typeSingle shared secretPrivate key (signs) + public key (verifies)
SpeedFasterSlower (RSA math)
Secret exposureEvery verifier needs the secretVerifiers only need the public key
Key rotationMust redistribute secret to all verifiersRotate private key, publish new public key
Use caseSingle API, internal servicesMicroservices, public JWKS, mobile clients

5. Token storage risks

// OPTION 1: localStorage / sessionStorage
// ✗ Readable by any JavaScript on the page
// ✗ XSS attack steals token with document.cookie is not needed; localStorage.getItem("token") works
// ✓ No automatic CSRF risk

// OPTION 2: HttpOnly Secure cookie
// ✓ Not readable by JavaScript at all (XSS can't steal it)
// ✓ Sent only over HTTPS (Secure flag)
// ✗ Browser sends it automatically → CSRF risk (mitigate with SameSite=Strict/Lax + CSRF token)

// OPTION 3: In-memory (JS variable)
// ✓ XSS can't survive a page reload (token is gone)
// ✗ Lost on refresh → needs silent re-auth (refresh token in HttpOnly cookie)

6. Why HTTPS is non-negotiable

Without TLS, an attacker on the same Wi-Fi (café, airport) can read your Authorization header and replay the JWT for the token's full lifetime. All traffic between the mobile app and Ugaav's API must be over HTTPS. Use app.UseHttpsRedirection() in development; ensure your hosting (Azure App Service, AWS ALB) terminates TLS in production.

Common mistakes

  • Saying 'JWT is encrypted' — it is signed. Tampered payloads are rejected, but anyone can read them.
  • Putting sensitive data (passwords, PAN numbers) in a JWT claim.
  • Using HS256 when multiple independent services verify tokens — they'd all need the secret.
  • Storing JWTs in localStorage in a production SPA facing real XSS risk.
  • Forgetting to set an expiry (exp) claim — the token is then valid forever.
  • Confusing authentication (who) with authorisation (can they?).

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is the difference between authentication and authorisation?
Authentication proves identity — are you who you claim to be? Authorisation decides what an authenticated identity may do. AuthN comes first; without it, AuthZ has no subject to evaluate.
BasicWhy are JWTs called 'self-contained'?
All the information needed to authorise a request (user ID, roles, expiry) is encoded in the token itself. The server doesn't need a database round-trip to validate — it just verifies the signature and reads the claims.
BasicName two risks of storing a JWT in localStorage.
(1) XSS — injected JavaScript can call localStorage.getItem and exfiltrate the token. (2) Persistent across tabs/sessions; a stolen token stays usable until expiry.
IntermediateWhat is CSRF and how does it relate to cookie-based auth?
CSRF tricks the browser into making an authenticated request to your server from a malicious page, because the browser automatically attaches cookies. Mitigations: SameSite cookie attribute (Strict or Lax), CSRF tokens in forms, or not using cookies and requiring an explicit Authorization header.
IntermediateYour company has an ASP.NET Core API, an iOS app, and a React SPA — all using the same auth service. Should you use HS256 or RS256? Why?
RS256. The iOS app and React SPA can verify tokens using the published public key (JWKS endpoint) without ever receiving the secret. With HS256 you'd need to give the secret to every verifier, increasing the blast radius if it leaks.
AdvancedA JWT's exp claim has passed but the user is still active. What are your options for keeping them logged in without asking them to re-enter their password?
Issue a short-lived access token (15 min) paired with a long-lived refresh token stored securely (HttpOnly cookie or secure storage). When the access token expires, the client exchanges the refresh token for a new access token silently. Rotate the refresh token on each use to detect reuse attacks. This is Thursday's topic.

ASP.NET Core Identity

GoalWire up ASP.NET Core Identity to your API — IdentityDbContext, ApplicationUser, password options, UserManager, SignInManager, RoleManager, and seeding roles and an admin account.

Key definitions

ASP.NET Core Identity
A membership system providing user storage, password hashing, roles, claims, lockout, and two-factor support — integrated with EF Core.
IdentityDbContext
An EF Core DbContext that includes all Identity tables (AspNetUsers, AspNetRoles, AspNetUserRoles, AspNetUserClaims, etc.).
ApplicationUser
Your custom user class inheriting from IdentityUser; add extra columns here (e.g. FullName, MobileNumber).
IdentityUser
The base Identity user with Id (Guid string), UserName, Email, PasswordHash, PhoneNumber, LockoutEnabled, etc.
UserManager<T>
Service for user CRUD: CreateAsync, FindByEmailAsync, CheckPasswordAsync, AddToRoleAsync, GetClaimsAsync.
SignInManager<T>
Service for sign-in flows: PasswordSignInAsync, SignOutAsync — also handles lockout and 2FA.
RoleManager<T>
Service for creating and querying roles: CreateAsync, RoleExistsAsync.
PasswordHasher
Hashes passwords with PBKDF2+SHA512 by default; never store plain-text passwords.
LockoutOptions
How many failed attempts trigger a lockout and for how long.
IdentityResult
Returned by most UserManager operations; has Succeeded, Errors.
Data protection
ASP.NET Core's key-ring for protecting tokens (email confirmation, password reset links).
NuGet packages
Microsoft.AspNetCore.Identity.EntityFrameworkCore and an EF Core provider like Microsoft.EntityFrameworkCore.SqlServer.
Quick notes
  • Identity is a library, not a middleware — you call it via UserManager/SignInManager, not via HTTP pipeline.
  • IdentityUser.Id is a string (GUID by default). If you need an int key, use IdentityUser<int>.
  • Never call SaveChangesAsync after UserManager.CreateAsync — Identity does it for you.
  • PasswordSignInAsync returns a SignInResult; check .Succeeded, .IsLockedOut, .RequiresTwoFactor.
  • Seeding roles and the admin account should run on startup — not in a migration — so it works in every environment.
  • Identity ships with PBKDF2 (100,000 rounds in .NET 8). Do NOT replace it with MD5 or SHA1.

public class AuthController(
    UserManager<ApplicationUser> userManager,

5. Seeding roles and an admin account

Seed on startup, not in a migration — migrations run on the developer's machine, not production.

Data/DbSeeder.cs
// Data/DbSeeder.cs
using AuthService.Models;
using Microsoft.AspNetCore.Identity;

namespace AuthService.Data;

public static class DbSeeder
{
    public static async Task SeedAsync(IServiceProvider sp)
    {
        var roleManager = sp.GetRequiredService<RoleManager<IdentityRole>>();
        var userManager = sp.GetRequiredService<UserManager<ApplicationUser>>();
        var cfg         = sp.GetRequiredService<IConfiguration>();

        string[] roles = ["Admin", "Farmer", "Buyer"];
        foreach (var role in roles)
            if (!await roleManager.RoleExistsAsync(role))
                await roleManager.CreateAsync(new IdentityRole(role));

        // Seed admin — credentials come from user-secrets or environment variables
        string adminEmail = cfg["Seed:AdminEmail"] ?? "admin@ugaav.in";
        string adminPass  = cfg["Seed:AdminPassword"]
            ?? throw new InvalidOperationException("Seed:AdminPassword not configured");

        if (await userManager.FindByEmailAsync(adminEmail) is null)
        {
            var admin = new ApplicationUser
            {
                UserName = adminEmail,
                Email    = adminEmail,
                FullName = "Super Admin",
                EmailConfirmed = true
            };
            var result = await userManager.CreateAsync(admin, adminPass);
            if (result.Succeeded)
                await userManager.AddToRoleAsync(admin, "Admin");
        }
    }
}

DAY 3 · WED

Issuing and Validating JWTs

GoalIssue signed JWTs with JsonWebTokenHandler, configure JwtBearer middleware to validate them, understand every TokenValidationParameters field, and handle 401 vs 403 correctly.

Key definitions

JwtBearer middleware
ASP.NET Core middleware (AddAuthentication().AddJwtBearer()) that extracts, validates, and sets the ClaimsPrincipal for each request.
JsonWebTokenHandler
The modern (.NET 6+) handler for creating and reading JWTs; faster than the legacy JwtSecurityTokenHandler.
JwtSecurityTokenHandler
The legacy handler; still works but Microsoft recommends JsonWebTokenHandler for new code.
TokenValidationParameters
A class holding all validation rules: issuer, audience, signing key, clock skew, lifetime.
ClockSkew
The allowed time difference between servers. Default is 5 minutes; set to TimeSpan.Zero for stricter tests.
SecurityTokenDescriptor
Describes the token to issue: subject (claims), issuer, audience, expiry, signing credentials.
SigningCredentials
Wraps the key and algorithm used to sign: new SigningCredentials(key, SecurityAlgorithms.HmacSha256).
SymmetricSecurityKey
A key created from a byte array; use a secret of 256+ bits for HS256.
RequireAuthorization
Extension on IEndpointConventionBuilder: requires auth on that route/group.
401 Unauthorized
The request has no valid credentials — not authenticated.
403 Forbidden
The user is authenticated but not authorised for this resource.
User-secrets
dotnet user-secrets set Jwt:Key "..." — keeps secrets out of source control in development.
Quick notes
  • RequireAuthorization() causes a 401 when no token is present. A valid token with wrong role causes 403.
  • Always validate issuer and audience in production — a token from a different service must not work on yours.
  • ClockSkew defaults to 5 minutes; set it to TimeSpan.Zero in tests to catch off-by-one errors.
  • The JWT signing key must be at least 256 bits (32 bytes) for HS256. A short key will throw a runtime exception.
  • Use dotnet user-secrets in development; use environment variables or Azure Key Vault in production. Never commit keys.
  • JsonWebTokenHandler is recommended over JwtSecurityTokenHandler for new code (.NET 6+).

// Services/TokenService.cs
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;
using AuthService.Models;

namespace AuthService.Services;

public interface ITokenService
{
    string CreateAccessToken(ApplicationUser user, IEnumerable<string> roles);
    string CreateRefreshTokenValue();   // secure random string — stored in DB (Thu)
}

public class TokenService(IConfiguration cfg) : ITokenService
{
    private readonly string _key      = cfg["Jwt:Key"] ?? throw new InvalidOperationException("Jwt:Key missing");
    private readonly string _issuer   = cfg["Jwt:Issuer"] ?? "ugaav-auth";
    private readonly string _audience = cfg["Jwt:Audience"] ?? "ugaav-api";
    private readonly int    _minutes  = int.TryParse(cfg["Jwt:AccessTokenMins"], out var m) ? m : 15;

    public string CreateAccessToken(ApplicationUser user, IEnumerable<string> roles)
    {
        var claims = new List<Claim>
        {
            new(JwtRegisteredClaimNames.Sub,   user.Id),
            new(JwtRegisteredClaimNames.Email, user.Email!),
            new(JwtRegisteredClaimNames.Jti,   Guid.NewGuid().ToString()),  // unique token ID
            new("name",                         user.FullName),
        };
        // Add a claim per role — the [Authorize(Roles="Admin")] attribute reads these
        foreach (var role in roles)
            claims.Add(new Claim(ClaimTypes.Role, role));

        var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_key));
        var descriptor = new SecurityTokenDescriptor
        {
            Subject            = new ClaimsIdentity(claims),
            Issuer             = _issuer,
            Audience           = _audience,
            Expires            = DateTime.UtcNow.AddMinutes(_minutes),
            SigningCredentials = new SigningCredentials(key, SecurityAlgorithms.HmacSha256)
        };

        var handler = new JsonWebTokenHandler();          // modern handler (.NET 6+)
        return handler.CreateToken(descriptor);            // returns the token string
    }

    public string CreateRefreshTokenValue() =>
        Convert.ToBase64String(System.Security.Cryptography.RandomNumberGenerator.GetBytes(64));
}

Refresh Tokens, Password Reset and Account Lockout

GoalIssue short-lived access tokens paired with long-lived refresh tokens, implement rotation with reuse detection, design a password-reset flow, and configure lockout correctly.

Key definitions

Refresh token
A long-lived opaque random string that lets a client get a new access token without re-entering credentials.
Token rotation
Issuing a brand-new refresh token every time the old one is used, invalidating the old one.
Reuse detection
Detecting when a refresh token that was already rotated (replaced) is used again — a sign of theft — and revoking the entire refresh-token chain.
Token family / chain
A set of refresh tokens linked by ReplacedBy that all trace back to one original login.
PBKDF2
Password-Based Key Derivation Function 2; used by ASP.NET Core Identity for password hashing.
Password reset flow
User requests reset → email with signed token (Identity DataProtectionTokenProvider) → user submits new password with token → token validated and invalidated.
Lockout
ASP.NET Core Identity's built-in brute-force protection: N failed logins → account locked for T minutes.
AccessFailedCount
Column on AspNetUsers tracking consecutive login failures, reset on success.
LockoutEnd
Nullable DateTimeOffset on AspNetUsers; if set and in the future, sign-in returns IsLockedOut.
RefreshToken (table)
Your own table: Token (hashed), UserId, ExpiresAt, RevokedAt, ReplacedBy, CreatedAt.
Quick notes
  • Store the hash of the refresh token in the database — not the plain value. If the DB is compromised, tokens are still useless.
  • Rotate on every use. The old token is immediately marked ReplacedBy = newTokenId.
  • Reuse detection: if a token that was already replaced is presented, revoke the entire chain — it means one copy was stolen.
  • Logout = revoke the refresh token in the DB (and all its chain if you like). The access token expires naturally.
  • Password reset tokens from Identity are single-use and time-limited (default 1 day) — do not roll your own.
  • Lockout applies to the sign-in action, not token refresh. Refresh reuse detection is a separate revocation mechanism.

3. Refresh flow with rotation and reuse detection

Services/AuthService.cs — refresh
// Services/AuthService.cs (refresh logic)
public async Task<AuthResult> RefreshAsync(string rawRefreshToken)
{{
    string hashed = tokenService.HashToken(rawRefreshToken);

    // Find the token in the DB (active or not — we need it even if revoked for reuse detection)
    var stored = await db.RefreshTokens
        .FirstOrDefaultAsync(r => r.Token == hashed);

    if (stored is null)
        return AuthResult.Fail("Invalid refresh token");

    if (stored.IsRevoked)
    {{
        // Token was already replaced/revoked — REUSE DETECTED
        // Revoke all tokens in the chain (tokens where ReplacedBy traces back to this user)
        await RevokeChainAsync(stored.UserId);
        return AuthResult.Fail("Refresh token reuse detected — all sessions revoked");
    }}

    if (stored.IsExpired)
        return AuthResult.Fail("Refresh token expired — please log in again");

    var user  = await userManager.FindByIdAsync(stored.UserId);
    if (user is null) return AuthResult.Fail("User not found");

    var roles       = await userManager.GetRolesAsync(user);
    string newAccess = tokenService.CreateAccessToken(user, roles);

    // Rotate: create a new refresh token and link the old one to it
    string newRaw    = tokenService.CreateRefreshTokenValue();
    string newHashed = tokenService.HashToken(newRaw);

    stored.RevokedAt  = DateTime.UtcNow;      // mark old token as used/replaced
    stored.ReplacedBy = newHashed;

    var newToken = new RefreshToken
    {{
        UserId    = user.Id,
        Token     = newHashed,
        ExpiresAt = stored.ExpiresAt          // keep the same expiry (sliding window is a design choice)
    }};
    db.RefreshTokens.Update(stored);
    await db.RefreshTokens.AddAsync(newToken);
    await db.SaveChangesAsync();

    return AuthResult.Ok(newAccess, newRaw);   // return the RAW token to the client
}}

private async Task RevokeChainAsync(string userId)
{{
    var allTokens = await db.RefreshTokens
        .Where(r => r.UserId == userId && r.RevokedAt == null)
        .ToListAsync();
    foreach (var t in allTokens) t.RevokedAt = DateTime.UtcNow;
    await db.SaveChangesAsync();
}}

Authorisation — Roles, Policies and Resource-Based Checks

GoalGo beyond [Authorize(Roles=...)] with custom requirements, handlers, and resource-based authorisation using IAuthorizationService.

Key definitions

Role-based authorisation
Granting access based on membership in a named role, e.g. [Authorize(Roles = "Admin")].
Policy-based authorisation
A named set of requirements registered in DI; more expressive and testable than raw role checks.
IAuthorizationRequirement
A marker interface for a requirement data class, e.g. MinimumAgeRequirement(18).
AuthorizationHandler<T>
Evaluates one requirement: calls context.Succeed(requirement) or leaves it pending.
IAuthorizationService
Injected service for imperative / resource-based checks inside controllers or services.
Resource-based authorisation
Authorising against a specific resource object (e.g. 'can this user edit THIS blog post?').
AuthorizationHandlerContext
Passed to handlers: contains User (ClaimsPrincipal), Requirements, and optional Resource.
RequireClaim
Built-in requirement: user must have a specific claim (optionally with a specific value).
RequireRole
Built-in requirement inside a policy: equivalent to [Authorize(Roles=...)] but composable.
Fallback policy
A policy applied to every endpoint that hasn't set its own. Set with options.FallbackPolicy.
Quick notes
  • Policies are composable — one policy can require both a role AND a minimum claim value.
  • An AuthorizationHandler that doesn't call Succeed or Fail just leaves the requirement pending; other handlers for the same requirement may still succeed it.
  • Calling context.Fail() short-circuits — even if another handler would succeed, the check fails.
  • Resource-based checks CANNOT use [Authorize] attributes because the resource isn't available at attribute-evaluation time — use IAuthorizationService.AuthorizeAsync in the action.
  • Set a fallback policy of AuthorizationPolicies.RequireAuthenticatedUser() to protect every endpoint by default; then use [AllowAnonymous] selectively.
  • Roles are just claims — ClaimTypes.Role — so role-based and claim-based auth are the same system.

BasicWhat is a policy in ASP.NET Core authorization?

AuthService.cs — the core orchestrator

Services/AuthService.cs
// Services/AuthService.cs
using AuthService.Data;
using AuthService.DTOs;
using AuthService.Models;
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;

namespace AuthService.Services;

public class UgaavAuthService(
    UserManager<ApplicationUser> userManager,
    SignInManager<ApplicationUser> signInManager,
    ITokenService tokenService,
    AppDbContext db)
{
    public async Task<AuthResult> RegisterAsync(RegisterDto dto)
    {
        var user = new ApplicationUser { UserName = dto.Email, Email = dto.Email, FullName = dto.FullName };
        var result = await userManager.CreateAsync(user, dto.Password);
        if (!result.Succeeded)
            return AuthResult.Fail(string.Join("; ", result.Errors.Select(e => e.Description)));

        await userManager.AddToRoleAsync(user, "Farmer");     // default role
        return await IssueTokenPairAsync(user);
    }

    public async Task<AuthResult> LoginAsync(LoginDto dto)
    {
        var user = await userManager.FindByEmailAsync(dto.Email);
        if (user is null) return AuthResult.Fail("Invalid credentials");

        var signIn = await signInManager.CheckPasswordSignInAsync(user, dto.Password, lockoutOnFailure: true);
        if (signIn.IsLockedOut)  return AuthResult.Fail("Account locked — try again later");
        if (!signIn.Succeeded)   return AuthResult.Fail("Invalid credentials");

        return await IssueTokenPairAsync(user);
    }

    public async Task<AuthResult> RefreshAsync(string rawRefreshToken)
    {
        string hashed = tokenService.HashToken(rawRefreshToken);
        var stored    = await db.RefreshTokens.FirstOrDefaultAsync(r => r.Token == hashed);
        if (stored is null) return AuthResult.Fail("Invalid token");

        if (stored.IsRevoked)
        {
            await RevokeChainAsync(stored.UserId);
            return AuthResult.Fail("Token reuse detected — all sessions revoked");
        }
        if (stored.IsExpired) return AuthResult.Fail("Refresh token expired");

        var user  = await userManager.FindByIdAsync(stored.UserId);
        if (user is null) return AuthResult.Fail("User not found");

        // Rotate
        string newRaw    = tokenService.CreateRefreshTokenValue();
        string newHashed = tokenService.HashToken(newRaw);
        stored.RevokedAt  = DateTime.UtcNow;
        stored.ReplacedBy = newHashed;
        db.RefreshTokens.Update(stored);
        db.RefreshTokens.Add(new RefreshToken
        {
            UserId    = user.Id,
            Token     = newHashed,
            ExpiresAt = stored.ExpiresAt
        });
        await db.SaveChangesAsync();

        var roles       = await userManager.GetRolesAsync(user);
        string newAccess = tokenService.CreateAccessToken(user, roles);
        return AuthResult.Ok(newAccess, newRaw);
    }

    public async Task RevokeAsync(string rawRefreshToken)
    {
        string hashed = tokenService.HashToken(rawRefreshToken);
        var stored    = await db.RefreshTokens.FirstOrDefaultAsync(r => r.Token == hashed);
        if (stored is not null && stored.IsActive)
        {
            stored.RevokedAt = DateTime.UtcNow;
            await db.SaveChangesAsync();
        }
    }

    private async Task<AuthResult> IssueTokenPairAsync(ApplicationUser user)
    {
        var roles  = await userManager.GetRolesAsync(user);
        string access  = tokenService.CreateAccessToken(user, roles);
        string rawRefresh = tokenService.CreateRefreshTokenValue();
        db.RefreshTokens.Add(new RefreshToken
        {
            UserId    = user.Id,
            Token     = tokenService.HashToken(rawRefresh),
            ExpiresAt = DateTime.UtcNow.AddDays(7)
        });
        await db.SaveChangesAsync();
        return AuthResult.Ok(access, rawRefresh);
    }

    private async Task RevokeChainAsync(string userId)
    {
        var active = await db.RefreshTokens
            .Where(r => r.UserId == userId && r.RevokedAt == null)
            .ToListAsync();
        foreach (var t in active) t.RevokedAt = DateTime.UtcNow;
        await db.SaveChangesAsync();
    }
}

    {
        var result = await authSvc.RegisterAsync(dto);
        return result.Succeeded ? Ok(result) : BadRequest(new {{ error = result.Error }});
    }

    [HttpPost("login")]
    public async Task<IActionResult> Login([FromBody] LoginDto dto)
    {
        var result = await authSvc.LoginAsync(dto);
        return result.Succeeded ? Ok(result) : Unauthorized(new {{ error = result.Error }});
    }

    [HttpPost("refresh")]
    public async Task<IActionResult> Refresh([FromBody] RefreshDto dto)
    {
        var result = await authSvc.RefreshAsync(dto.RefreshToken);
        return result.Succeeded ? Ok(result) : Unauthorized(new {{ error = result.Error }});
    }

    [Authorize]
    [HttpPost("logout")]
    public async Task<IActionResult> Logout([FromBody] RefreshDto dto)
    {
        await authSvc.RevokeAsync(dto.RefreshToken);
        return Ok(new {{ message = "Logged out" }});
    }

    [Authorize]
    [HttpPost("change-password")]
    public async Task<IActionResult> ChangePassword([FromBody] ChangePasswordDto dto)
    {
        string userId = User.FindFirstValue(System.Security.Claims.ClaimTypes.NameIdentifier)!;
        var user = await userManager.FindByIdAsync(userId);
        var result = await userManager.ChangePasswordAsync(user!, dto.CurrentPassword, dto.NewPassword);
        if (!result.Succeeded) return BadRequest(result.Errors);
        await authSvc.RevokeChainPublic(userId);   // helper that exposes RevokeChainAsync
        return Ok(new {{ message = "Password changed — please log in again" }});
    }
}

Q2. What prints / what happens?

// The same raw token value is presented again to POST /api/auth/refresh.
// What is the expected behaviour?
All active refresh tokens for that user are revoked. The reuse detection path: the token exists in the DB but is already marked RevokedAt (not null). The system interprets a revoked token being presented as a sign of theft and calls RevokeChainAsync for the user, logging them out everywhere.
Q3. Does this compile and run correctly? 
var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes("short"));
var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
Compiles but throws at runtime. HS256 requires a key of at least 128 bits (16 bytes for the minimum, 256 bits / 32 bytes recommended). The string "short" is 5 bytes → ArgumentOutOfRangeException: IDX10720: ... key size must be greater than 128 bits.
Q4. What is wrong with this token-storage strategy? 
// In a React SPA:
// 1. POST /api/auth/login  →  store accessToken in localStorage
// 2. Every fetch: Authorization: Bearer localStorage.getItem('accessToken')
XSS vulnerability. Any injected script on the page can call localStorage.getItem('accessToken') and exfiltrate the token to an attacker's server. Prefer an HttpOnly Secure cookie (not readable by JS) or in-memory storage with a silent refresh mechanism.
Q5. AuthorizationHandler — Succeed, Fail or neither? 
protected override Task HandleRequirementAsync(
    AuthorizationHandlerContext ctx,
    MinAgeRequirement req)
{
    var dob = ctx.User.FindFirstValue("date_of_birth");
    if (dob is null) return Task.CompletedTask;   // ← what happens here?

    if (DateTime.TryParse(dob, out var birth) && DateTime.Today.Year - birth.Year >= req.MinAge)
        ctx.Succeed(req);
    return Task.CompletedTask;
}
Leaving the requirement pending (neither Succeed nor Fail). When dob is null the handler returns without calling Succeed or Fail. Other handlers for this requirement may still succeed it. If no handler succeeds, the requirement fails. This is the correct behaviour — only call ctx.Fail() if you want to explicitly deny access regardless of other handlers.
