DAY 1 · MON

GROUP BY, HAVING and aggregates

GoalMaster multi-column grouping, choose the right aggregate, understand WHERE vs HAVING, and get a first look at GROUPING SETS and ROLLUP.

Key definitions

Aggregate function
Collapses many rows to one value per group: SUM, AVG, MIN, MAX, COUNT.
GROUP BY
Splits the result into groups and runs one aggregate per group.
COUNT(*)
Counts all rows in the group, including NULLs.
COUNT(col)
Counts non-NULL values in that column.
COUNT(DISTINCT col)
Counts distinct non-NULL values — deduplicated count.
SUM / AVG / MIN / MAX
Ignore NULLs automatically. SUM of an all-NULL column returns NULL.
HAVING
Filters groups after aggregation, the way WHERE filters rows before. Can reference aggregate results.
Multi-column GROUP BY
Groups on the unique combination of several columns.
GROUPING SETS
(SQL:1999) Lets one SELECT compute several grouping combinations at once; not covered in depth until DW week.
ROLLUP
Shorthand for a hierarchy of GROUPING SETS from most detailed to grand total.
Logical query order
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY; SELECT aliases are not visible in HAVING.
NULL in grouping
All NULLs form their own group — they don't match, they collect.
Quick notes
  • WHERE filters rows, HAVING filters groups — the difference is important for performance because WHERE reduces the data before grouping.
  • Column aliases defined in SELECT cannot be used in HAVING or GROUP BY in SQL Server; repeat the expression or use a derived table.
  • Every non-aggregated column in SELECT must appear in GROUP BY.
  • COUNT(DISTINCT col) scans a full sort pass; on large tables it can be slow — an index helps.
  • AVG of integers truncates to an integer in SQL Server; CAST one side to DECIMAL(18,4) first.
  • ROLLUP is awareness-level here; detail is in a later data-warehouse week.

2. WHERE vs HAVING

02_where_vs_having.sql
-- ❌ Syntactically wrong: WHERE can't see aggregates
-- SELECT department_id, COUNT(*) AS cnt
-- FROM hr.employees
-- WHERE COUNT(*) > 3
-- GROUP BY department_id;

-- ✓ HAVING filters groups, WHERE filters rows first (much cheaper)
SELECT   e.department_id,
         COUNT(*)   AS cnt
FROM     hr.employees AS e
WHERE    e.hire_date >= '2022-01-01'       -- filters rows BEFORE grouping
GROUP BY e.department_id
HAVING   COUNT(*) > 2;                     -- filters groups AFTER grouping

Tip. If a condition doesn't involve an aggregate, put it in WHERE. Only move a condition to HAVING when it references an aggregate (SUM, COUNT, AVG, etc.).

5. ROLLUP and GROUPING SETS (awareness)

ROLLUP adds subtotal and grand-total rows automatically. The GROUPING() function distinguishes a real NULL value from a "total" NULL produced by ROLLUP.

05_rollup.sql
-- Payroll by department, with a grand total row (awareness only — detail in the DW week)
SELECT   COALESCE(d.department_name, 'ALL DEPARTMENTS') AS dept,
         COUNT(*)                AS headcount,
         SUM(e.salary)           AS total_payroll
FROM     hr.employees   AS e
JOIN     hr.departments AS d ON d.department_id = e.department_id
GROUP BY ROLLUP(d.department_name);
-- Last row: dept='ALL DEPARTMENTS', headcount=total, total_payroll=grand total
dept              headcount  total_payroll
----------------  ---------  -------------
Engineering       12         1140000
Finance            5          440000
HR                 4          272000
Sales              8          580000
ALL DEPARTMENTS   29         2432000      ← ROLLUP grand total row
(example output)

Common mistakes

  • Putting a non-aggregated column in SELECT but not in GROUP BY — SQL Server error 8120.
  • Using a column alias from SELECT in HAVING (not allowed in SQL Server; repeat the expression).
  • Forgetting that AVG of INTs is integer division.
  • COUNT(*) vs COUNT(col) — the difference matters when that column has NULLs.
  • Using HAVING where WHERE would do — extra rows go through the aggregation engine unnecessarily.

Self-check questions

Why can't you use a SELECT alias in HAVING?SQL Server evaluates HAVING before SELECT aliases are computed (logical query order: FROM → WHERE → GROUP BY → HAVING → SELECT). Repeat the expression or wrap the query in a CTE/derived table.
What does COUNT(*) count that COUNT(col) doesn't?COUNT(*) counts every row including NULLs. COUNT(col) counts only non-NULL values in that column.
What is the logical query processing order?FROM, then WHERE (filter rows), then GROUP BY (form groups), then HAVING (filter groups), then SELECT (compute output columns), then ORDER BY.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is the difference between WHERE and HAVING?
WHERE filters individual rows before grouping; it cannot reference aggregates. HAVING filters groups after GROUP BY; it can reference aggregates. Putting a non-aggregate condition in HAVING instead of WHERE forces SQL Server to aggregate more rows unnecessarily.
BasicWhat does COUNT(DISTINCT col) return?
The number of distinct non-NULL values in that column within each group. It's useful for questions like 'how many different products were ordered per customer'. It costs more than COUNT(*) because it requires a sort or hash to deduplicate.
BasicEvery non-aggregated column in SELECT must appear in GROUP BY — why?
Because one group contains many rows with potentially different values for that column; without grouping it, there's no single value to show. SQL Server enforces this with error 8120.
IntermediateA query returns NULL rows from GROUP BY you didn't expect. What could cause it?
Two common reasons: (1) the grouping column contains actual NULL values — SQL Server groups them together; (2) an outer join produced NULL-padded rows on the outer side that you're now grouping. Add IS NULL checks in WHERE, or use INNER JOIN.
IntermediateHow would you calculate the percentage of total salary each department represents?
Either a window function (SUM(salary) OVER ()) in a derived table, or a subquery in HAVING/SELECT: SUM(salary) * 100.0 / (SELECT SUM(salary) FROM hr.employees).
IntermediateWhat is ROLLUP and when would you use it?
ROLLUP is shorthand for a hierarchy of GROUPING SETS that adds subtotals and a grand total. It's most common in reporting and dashboards: GROUP BY ROLLUP(dept, team) produces one group per dept+team, one per dept (summing teams), and one overall total. Full detail in the data-warehouse week.
DAY 2 · TUE

Subqueries

GoalWrite scalar, column, table, and correlated subqueries; understand when EXISTS wins over IN; and know the derived table pattern.

Key definitions

Subquery
A SELECT nested inside another SQL statement, enclosed in parentheses.
Scalar subquery
Returns exactly one row and one column; used wherever a single value is expected (SELECT list, WHERE, HAVING).
Column subquery
Returns one column but potentially many rows; used with IN / NOT IN / ANY / ALL.
Table subquery (derived table)
Returns a full table result; appears in FROM and must be aliased. Called an inline view in some databases.
Correlated subquery
References a column from the outer query. Re-executes once per outer row (usually replaced by EXISTS or a join).
EXISTS
Returns TRUE if the subquery produces at least one row. Short-circuits after the first match.
NOT EXISTS
Anti-join: TRUE when the subquery returns no rows. NULL-safe — preferred over NOT IN.
IN / NOT IN
IN is equivalent to = ANY; NOT IN has the NULL trap — one NULL in the list makes NOT IN return nothing.
ANY / ALL
Rarely needed: = ANY is IN, > ALL means greater than the max, < ALL means less than the min.
Semi-join
Filters rows using a match in another table but adds no columns from it — cleanest with EXISTS.
Anti-join
Filters to rows that have no match — cleanest with NOT EXISTS.
Inline view
Another name for a derived table: a subquery in FROM.
Quick notes
  • Scalar subqueries must return at most one row or SQL Server raises an error at runtime.
  • Correlated subqueries are often slow on large tables — test whether a join or window function is faster.
  • Use EXISTS/NOT EXISTS instead of IN/NOT IN when the inner column is nullable.
  • A derived table (subquery in FROM) can reference its own aggregates in WHERE — unlike the outer SELECT.
  • Name all derived table aliases clearly: 'dept_avg', 'top_earners', not 'x', 'y'.

3. NOT IN — the NULL trap

03_not_in_trap.sql
-- Managers (employees who manage at least one person)
-- ❌ NULL trap: if any employee has manager_id NULL, NOT IN returns zero rows
SELECT employee_id, first_name + ' ' + last_name AS name
FROM   hr.employees
WHERE  employee_id NOT IN (SELECT manager_id FROM hr.employees);  -- manager_id can be NULL!

-- ✓ NOT EXISTS is always NULL-safe
SELECT employee_id, first_name + ' ' + last_name AS name
FROM   hr.employees AS e
WHERE  NOT EXISTS
       (SELECT 1 FROM hr.employees AS m WHERE m.manager_id = e.employee_id);
Gotcha. If the column in the IN subquery can be NULL, NOT IN may silently return zero rows because NULL <> x is UNKNOWN, not FALSE. Use NOT EXISTS or add WHERE col IS NOT NULL to the inner SELECT.

4. EXISTS and NOT EXISTS

04_exists.sql
-- Departments that have at least one employee (EXISTS = semi-join)
SELECT d.department_id, d.department_name
FROM   hr.departments AS d
WHERE  EXISTS
       (SELECT 1 FROM hr.employees AS e WHERE e.department_id = d.department_id);

-- Departments with no employees (NOT EXISTS = anti-join)
SELECT d.department_id, d.department_name
FROM   hr.departments AS d
WHERE  NOT EXISTS
       (SELECT 1 FROM hr.employees AS e WHERE e.department_id = d.department_id);

The inner SELECT of an EXISTS only needs to return at least one row. Convention is SELECT 1 to make intent clear; SELECT * works too but looks like you care about the data.

5. Correlated subquery

05_correlated_to_join.sql
-- Employees earning more than their department's average
SELECT  e.employee_id,
        e.first_name + ' ' + e.last_name  AS employee_name,
        e.salary                           AS salary,
        dept_avg.avg_sal                   AS dept_avg_salary
FROM    hr.employees AS e
JOIN    (
            SELECT  department_id,
                    AVG(CAST(salary AS DECIMAL(14,4)))  AS avg_sal
            FROM    hr.employees
            GROUP BY department_id
        ) AS dept_avg ON dept_avg.department_id = e.department_id
WHERE   e.salary > dept_avg.avg_sal
ORDER BY e.department_id, e.salary DESC;
-- Note: rewritten as a join to derived table, which is faster than a correlated subquery
-- (the correlated version re-runs the subquery for every outer row)
-- ❌ Slow correlated version (re-executes per row):
SELECT  e.first_name + ' ' + e.last_name AS employee_name,
        e.salary
FROM    hr.employees AS e
WHERE   e.salary > (SELECT AVG(CAST(salary AS DECIMAL(14,4)))
                    FROM   hr.employees AS inner_e
                    WHERE  inner_e.department_id = e.department_id);  -- references outer e

6. Derived tables (table subquery in FROM)

06_derived_table.sql
-- Top 3 earners per department using a derived table (window functions tomorrow are cleaner)
SELECT  ranked.department_name,
        ranked.employee_name,
        ranked.salary
FROM    (
            SELECT  d.department_name,
                    e.first_name + ' ' + e.last_name  AS employee_name,
                    e.salary,
                    ROW_NUMBER() OVER (PARTITION BY e.department_id ORDER BY e.salary DESC)
                        AS rn
            FROM    hr.employees   AS e
            JOIN    hr.departments AS d ON d.department_id = e.department_id
        ) AS ranked
WHERE   ranked.rn <= 3
ORDER BY ranked.department_name, ranked.salary DESC;
Tip. Derived tables can reference their own aliases in WHERE but cannot be referenced more than once in the query. When you need to reference the same derived result twice, use a CTE (tomorrow).

Common mistakes

  • Scalar subquery returning more than one row — runtime error 512. Add TOP(1) or ensure uniqueness.
  • NOT IN over a nullable column — the classic NULL trap.
  • Correlated subqueries on millions of rows — test with execution plans; often replaceable by a window function or derived table join.
  • Forgetting to alias a derived table — SQL Server error: every derived table must have an alias.
  • Nesting more than two or three subquery levels — CTEs will make the same logic readable.

Self-check questions

Scalar vs column vs table subquery?Scalar returns one value (one row, one column); used where a value is expected. Column returns one column, many rows; used with IN/ANY/ALL. Table returns rows and columns; used in FROM as a derived table.
EXISTS vs IN for performance?EXISTS short-circuits after finding the first match and doesn't pull all values into memory. IN evaluates the whole subquery and builds a list. For large sets EXISTS is often faster, especially when the inner column is nullable.
Why alias a derived table?SQL Server requires every table in FROM to have a name (alias or its own name). A subquery has no name of its own, so an alias is mandatory: (...) AS alias_name.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is a correlated subquery?
A subquery that references a column from the outer query. It re-executes once per row of the outer query, making it logically like a function called per row. This is powerful but slow at scale — a join or window function is usually faster.
BasicWhen would you choose EXISTS over IN?
When the inner column may contain NULLs (NOT IN's NULL trap), when you only need to check existence (not use the value), and when the subquery returns many rows (EXISTS short-circuits). Use IN when the list is small, static and NULL-free.
BasicWhat is a derived table?
A subquery in the FROM clause, enclosed in parentheses and given an alias. It acts as a temporary named result set for that query only — not persisted like a view or temp table.
IntermediateHow do you rewrite a correlated subquery to avoid per-row re-execution?
Promote the inner query to a derived table or CTE grouped on the correlated column, then JOIN the outer query to that derived result once. The optimiser can then choose a hash join or merge join rather than a nested loop per row.
IntermediateWhat does ANY / ALL do?
ANY (synonym: SOME) makes a comparison true if it's true for at least one value; ALL requires it to be true for every value. salary > ALL (SELECT …) means salary is greater than every value returned — equivalent to salary > MAX. These are rarely written directly; using MAX/MIN with a plain comparison is more readable.
IntermediateCan a subquery appear in the SELECT clause?
Yes, as a scalar subquery — it must return at most one row and one column, and it's re-evaluated for every output row (similar to a correlated subquery). If the same value is needed in many columns, compute it once in a CTE or derived table.
DAY 3 · WED

Common Table Expressions (CTEs)

GoalWrite chained CTEs for readability, recursive CTEs for org charts, and understand when to use a CTE vs temp table vs derived table.

Key definitions

CTE (Common Table Expression)
A named temporary result set defined with WITH and usable in the query that follows. Scoped to that single statement.
Non-recursive CTE
A simple named derived table; can be chained (multiple CTEs in one WITH).
Recursive CTE
A CTE that references itself via UNION ALL, used for hierarchical or graph traversals.
Anchor member
The base case of a recursive CTE — the rows that start the traversal.
Recursive member
The part that JOINs the CTE to itself to find the next level.
MAXRECURSION
Query hint controlling the recursion depth limit; default 100. OPTION (MAXRECURSION 0) removes the limit.
WITH TIES
Used with TOP to include rows that tie for the last position (requires ORDER BY).
Chained CTEs
Multiple CTEs in one WITH clause, each building on those defined before it.
Hierarchy
A parent-child tree structure: employees and their managers, categories and subcategories.
Level / depth
Computed column in a recursive CTE tracking how deep in the tree the current row is.
Path
A string column accumulating the route from root to current node, useful for cycle detection.
Cycle detection
Ensuring a recursive CTE doesn't loop forever on a graph with cycles (SQL Server's default MAXRECURSION 100 stops it after 100 levels).
Quick notes
  • CTEs do not create any physical object — they're scoped to the single statement they precede.
  • You can reference a CTE more than once in the query that follows (unlike a derived table).
  • The anchor and recursive members must have the same number of columns with compatible types.
  • UNION ALL is required in recursive CTEs; UNION would deduplicate and is disallowed.
  • Keep recursion depth reasonable in production; a cycle in the data can hit MAXRECURSION 100.
  • CTEs do not auto-materialise — SQL Server may evaluate them multiple times; use a temp table if the same data is needed repeatedly in a large batch.

1. Single CTE for readability

01_chained_cte.sql
-- Departments where average salary exceeds the company-wide average
WITH dept_averages AS (
    SELECT  department_id,
            AVG(CAST(salary AS DECIMAL(14,4))) AS avg_sal
    FROM    hr.employees
    GROUP BY department_id
),
company_avg AS (
    SELECT AVG(CAST(salary AS DECIMAL(14,4))) AS overall_avg
    FROM   hr.employees
)
SELECT  d.department_name,
        da.avg_sal               AS dept_avg,
        ca.overall_avg           AS company_avg,
        da.avg_sal - ca.overall_avg AS difference
FROM    hr.departments AS d
JOIN    dept_averages  AS da ON da.department_id = d.department_id
CROSS JOIN company_avg AS ca
WHERE  da.avg_sal > ca.overall_avg
ORDER BY da.avg_sal DESC;
department_name  dept_avg    company_avg  difference
---------------  ----------  -----------  ----------
Engineering      95000.00    88000.00      7000.00
Finance          88800.00    88000.00       800.00
(example output)
Tip. Chain CTEs in a single WITH clause separated by commas. Each CTE can reference CTEs defined earlier in the same WITH. The final SELECT (or INSERT/UPDATE/DELETE) uses all of them.

2. Recursive CTE — org chart

02_recursive_cte.sql
-- Walk the management hierarchy from the top down, tracking level and path
WITH org_chart AS (
    -- Anchor: employees with no manager (top of the tree)
    SELECT  e.employee_id,
            e.first_name + ' ' + e.last_name           AS employee_name,
            e.manager_id,
            e.salary,
            e.department_id,
            0                                          AS level,
            CAST(e.first_name + ' ' + e.last_name AS NVARCHAR(1000))
                                                       AS path
    FROM    hr.employees AS e
    WHERE   e.manager_id IS NULL              -- anchor: the CEO / top-level managers

    UNION ALL

    -- Recursive member: direct reports of the rows already in the CTE
    SELECT  e.employee_id,
            e.first_name + ' ' + e.last_name           AS employee_name,
            e.manager_id,
            e.salary,
            e.department_id,
            oc.level + 1                               AS level,
            CAST(oc.path + ' > ' + e.first_name + ' ' + e.last_name AS NVARCHAR(1000))
                                                       AS path
    FROM    hr.employees AS e
    JOIN    org_chart    AS oc ON oc.employee_id = e.manager_id
)
SELECT  REPLICATE('    ', level) + employee_name  AS indented_name,
        level,
        path
FROM    org_chart
ORDER BY path;
indented_name                           level  path
--------------------------------------  -----  ----------------------------------------
Priya Sharma                            0      Priya Sharma
    Asha Joshi                          1      Priya Sharma > Asha Joshi
        Karan Mehta                     2      Priya Sharma > Asha Joshi > Karan Mehta
        Riya Desai                      2      Priya Sharma > Asha Joshi > Riya Desai
    Vikram Nair                         1      Priya Sharma > Vikram Nair
        Meena Pillai                    2      Priya Sharma > Vikram Nair > Meena Pillai
(example output)
Watch out. The default MAXRECURSION is 100. Add OPTION (MAXRECURSION 200) at the end of the statement for deeper trees, or MAXRECURSION 0 to remove the limit entirely (risk on cyclic data). Data cycles (A manages B who manages A) are stopped only by MAXRECURSION — add a cycle-guard path check in production.

3. MAXRECURSION and cycle guard

03_maxrecursion.sql
-- Query hint at the end of the whole statement (not inside the CTE):
WITH org_chart AS (
    -- ... same as above ...
    SELECT employee_id, first_name + ' ' + last_name AS nm, manager_id, 0 AS lvl,
           CAST(employee_id AS VARCHAR(500)) AS id_path
    FROM   hr.employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.employee_id, e.first_name + ' ' + e.last_name, e.manager_id, oc.lvl + 1,
           CAST(oc.id_path + ',' + CAST(e.employee_id AS VARCHAR(10)) AS VARCHAR(500))
    FROM   hr.employees e
    JOIN   org_chart    oc ON oc.employee_id = e.manager_id
    WHERE  CHARINDEX(',' + CAST(e.employee_id AS VARCHAR(10)) + ',',
                     ',' + oc.id_path + ',') = 0  -- cycle guard: stop if already visited
)
SELECT indented = REPLICATE('  ', lvl) + nm, lvl FROM org_chart ORDER BY id_path

Self-check questions

What's the difference between a CTE and a temp table?A CTE lives for one statement only and may be re-evaluated by the optimiser; it has no statistics or indexes. How do you stop a recursive CTE from looping?Either by SQL Server's MAXRECURSION setting (default 100), or by adding a WHERE guard in the recursive member that checks the path string doesn't already contain the current row's ID. BasicWhat is a CTE and when would you use it instead of a subquery?
A CTE is a named temporary result defined with WITH before the main query. Use it instead of a nested subquery when: (1) the same derived result is referenced more than once; (2) a subquery would be deeply nested; (3) you need recursion. CTEs improve readability without changing the execution plan.
BasicExplain the structure of a recursive CTE.
A recursive CTE has two parts joined by UNION ALL: the anchor member (the base case returning the starting rows) and the recursive member (a SELECT that JOINs the CTE to itself to find the next level). SQL Server executes the anchor once, then repeatedly executes the recursive member against the latest level's rows until it returns no more rows or hits MAXRECURSION.
BasicWhat happens if MAXRECURSION is exceeded?
SQL Server raises error 530: 'The statement terminated. The maximum recursion 100 has been exhausted before statement completion.' You can raise the limit with OPTION (MAXRECURSION n) or remove it with OPTION (MAXRECURSION 0). The latter is risky on cyclic data.
IntermediateCan a CTE be referenced more than once in the same query?
Yes — that's one advantage over derived tables. All CTEs in the WITH block are in scope for the main query and for each other (each can reference any CTE defined before it). However, SQL Server may still re-evaluate the CTE once per reference unless it chooses to spool; if single-evaluation is essential, use a temp table.
IntermediateHow would you delete duplicate rows using a CTE?

IntermediateCTE vs view: what's different?
A CTE exists only for the duration of one statement; it cannot be reused by other queries or stored in the database. A view is a named persistent object others can query. Use a CTE for query-local clarity; use a view for a reusable, security-layer, or join shorthand needed across the codebase.

Window functions

GoalUse ROW_NUMBER, RANK, DENSE_RANK, NTILE, LAG, LEAD, running totals and moving averages without collapsing your rows.

Key definitions

Window function
A function applied over a 'window' of rows related to the current row. Unlike GROUP BY, it does not collapse rows.
OVER clause
Defines the window: PARTITION BY (grouping), ORDER BY (sorting within partition), and optional frame.
PARTITION BY
Resets the window calculation for each group, like GROUP BY but without collapsing rows.
ORDER BY (in OVER)
Determines the order within each partition for ranking and running calculations.
Frame clause
Specifies which rows of the partition are included in the calculation relative to the current row: ROWS BETWEEN / RANGE BETWEEN.
ROW_NUMBER()
Unique sequential number per row within the partition, based on ORDER BY.
RANK()
Same number for ties, then skips (1,1,3 for two ties at first).
DENSE_RANK()
Same number for ties, no skip (1,1,2 for two ties at first).
NTILE(n)
Divides rows into n equal buckets and assigns each row its bucket number.
LAG(col, n, default)
Value of col from n rows before the current row in the partition.
LEAD(col, n, default)
Value of col from n rows after the current row in the partition.
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
Classic running total frame.
RANGE vs ROWS
RANGE groups ties into the same frame boundary; ROWS is strict position. ROWS is almost always what you want.
Quick notes
  • Window functions run after WHERE and GROUP BY but before SELECT expressions — they see aggregated rows.
  • You can use a window function in ORDER BY or in a derived table/CTE but not directly in WHERE or HAVING.
  • RANK leaves gaps; DENSE_RANK does not — pick based on how ties should read.
  • ROWS BETWEEN is strict (physical position); RANGE BETWEEN treats ties as a group (less predictable). Default when ORDER BY is specified: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
  • LAG/LEAD default to NULL when there's no preceding/following row — supply a default if needed.
  • NTILE distributes rows as evenly as possible; with uneven distribution the first buckets get one extra row.

Views, table-valued functions and APPLY

GoalCreate views with SCHEMABINDING, compare inline vs multi-statement TVFs, understand scalar function cost and when SQL Server can inline them, and use CROSS/OUTER APPLY.

Key definitions

View
A named stored SELECT query. Used as a table in queries; does not store data (unless indexed).
SCHEMABINDING
Prevents DROP or ALTER on any base object the view depends on. Required for indexed views.
Indexed view
A view with a unique clustered index physically materialising the result. Needs SCHEMABINDING and several restrictions.
Inline TVF (ITVF)
A table-valued function returning a single SELECT; equivalent to a parameterised view. Zero overhead — optimiser treats it as a macro.
Multi-statement TVF (MSTVF)
A TVF with BEGIN/END and multiple statements, populating a table variable and returning it. Costly — acts like a black box, row estimate always 1 (before SQL 2019).
Scalar UDF
A function returning one value. Pre-SQL Server 2019 it blocks parallelism and re-executes per row. Post-2019, SQL Server may inline it.
Scalar UDF inlining
SQL Server 2019+ automatically converts eligible scalar UDFs to inline expressions, restoring performance.
CROSS APPLY
Like CROSS JOIN but the right side can be a function or subquery that uses a column from the left side. Returns only rows where the right side returns a result.
OUTER APPLY
Like LEFT JOIN equivalent of CROSS APPLY — also keeps left rows where the right side returns nothing (NULL-padded).
TVF
Table-valued function: a function you can query in FROM.
Deterministic
A function that always returns the same result for the same inputs — required for use in computed columns and indexed views.
Quick notes
  • SCHEMABINDING on a view prevents schema changes to its base tables without dropping the view first — a protection and a commitment.
  • Always prefer an ITVF over a scalar UDF when you need per-row calculation on a set of rows; the optimiser can reason about it.
  • MSTVF: think of it as a temp table returned — the row count estimate is usually wrong, leading to bad plans.
  • CROSS APPLY is the natural fit when calling a TVF once per row, or when a correlated derived table needs an alias.
  • OUTER APPLY preserves rows from the left side even when the right side returns nothing — mirrors LEFT JOIN.
  • Check sys.sql_modules or the Object Explorer for a view's definition; never rely on the view alone without verifying the base tables.

Both call a right-side expression once per left-side row. CROSS APPLY drops left rows where the right side returns no rows (like INNER JOIN). OUTER APPLY keeps them with NULLs on the right (like LEFT JOIN). The key capability: the right side can reference columns from the left, which a plain JOIN cannot.
BasicWhat is a table-valued function?
A user-defined function that returns a table result instead of a scalar value. It can be used in FROM, JOINed to other tables, and filtered with WHERE. Inline TVFs (single RETURN SELECT) have no performance overhead; multi-statement TVFs (BEGIN/END, table variable) have poor cardinality estimates.
IntermediateCan you UPDATE through a view?
Yes, with restrictions: the view must map each output row to exactly one base table row (no DISTINCT, no aggregates, no GROUP BY, no UNION). SQL Server traces the update back to the base table. With INSTEAD OF triggers you can make arbitrary views updatable.
IntermediateWhat is an indexed view and when would you create one?
An indexed view has a unique clustered index physically storing the view's result. It updates automatically when base tables change (write overhead). Use it for large aggregation queries that run constantly and can tolerate the extra storage and write cost. Requirements include SCHEMABINDING, no non-deterministic functions, and two-part names.
AdvancedWhen would CROSS APPLY beat a correlated subquery?
CROSS APPLY lets you use the full power of a FROM clause (JOINs, aggregates with ORDER BY, TOP n) in ways a correlated subquery can't express — particularly TOP n per group. Execution is similar (nested loops), but APPLY can reference TVFs that the optimiser can partially unfold.

Interview questions

Answer out loud first, then open each one to compare.

BasicWhat is the difference between WHERE and HAVING?
WHERE filters rows before grouping; HAVING filters groups after aggregation. HAVING can reference aggregate functions; WHERE cannot. For performance, use WHERE whenever the condition doesn't involve an aggregate.
BasicExplain the NOT IN NULL trap with an example.
If the subquery inside NOT IN returns any NULL value, the predicate becomes UNKNOWN for every row (NULL <> x is UNKNOWN, not FALSE), so NOT IN returns zero rows. Fix: use NOT EXISTS, or add WHERE col IS NOT NULL to the inner SELECT.
IntermediateWhat is PERCENTILE_CONT and how is it different from AVG?
PERCENTILE_CONT computes the interpolated median (or any percentile) of a column. For an even count it averages the two middle values. AVG sums all values and divides by count — it is sensitive to outliers. For skewed salary distributions, median (PERCENTILE_CONT(0.5)) is a more representative 'typical' salary.
IntermediateHow does ROW_NUMBER differ from RANK when there are salary ties?
ROW_NUMBER gives every row a unique number regardless of ties (1,2,3,4). RANK gives tied rows the same number and skips subsequent numbers (1,2,2,4). DENSE_RANK doesn't skip (1,2,2,3). For top-N filtering DENSE_RANK ensures ties at boundary position are all included.

Q3. Which FRAME clause gives a strict 3-row moving average regardless of ties? ROWS BETWEEN 2 PRECEDING AND CURRENT ROW. ROWS counts physical row positions. RANGE would group tied ORDER BY values together, possibly including more than 3 rows at a boundary.
Q4. What is the maximum recursion depth for a recursive CTE by default, and how do you change it? 100 levels. Change it with the query hint at the end of the statement: OPTION (MAXRECURSION 500). Set to 0 for unlimited (risk on cyclic data).
Q5. A CROSS APPLY returned fewer rows than the FROM table. Why? Because CROSS APPLY drops rows from the left side when the right side returns no rows — the same behaviour as INNER JOIN. Use OUTER APPLY to keep all left rows with NULLs when the right side is empty.

BasicWhat is the difference between ROW_NUMBER and DENSE_RANK?
ROW_NUMBER gives each row a unique sequential number, never ties. DENSE_RANK gives tied rows the same number and does not skip the next number (1,1,2 for a two-way tie). Use ROW_NUMBER for de-duplication, DENSE_RANK for leaderboards where ties should share a position.
BasicWhat is PERCENTILE_CONT and when is it more useful than AVG?
PERCENTILE_CONT computes the interpolated value at a given percentile (0.5 for median). Unlike AVG it is not distorted by extreme outliers — a CEO salary at ₹1.8 crore barely moves the median but triples the average. Use it when reporting 'typical' values in skewed distributions like salaries.
IntermediateExplain when you would use a CTE vs a temp table.
CTE: single-statement scope, great for readability and recursive queries, no indexing. Temp table: persists for the session, can be indexed, has statistics, ideal for large intermediate results used multiple times. When a CTE is referenced twice in a query and the intermediate result is expensive to compute, materialise it in a temp table first.
IntermediateHow do you calculate the second-highest value without a window function?
SELECT MAX(col) FROM table WHERE col < (SELECT MAX(col) FROM table). The inner subquery finds the maximum; the outer query finds the maximum among all values strictly less than it, which is the second-highest. Using DENSE_RANK = 2 in a CTE handles ties more cleanly.
